# 已知限制与勘误：静态工具、模拟器和版本语义

> 导航：返回 `SKILL.md` 查看技能总入口；案例研究见 `08-case-study-abyss-stars.md` 与 `09-case-study-aseu.md`；实例分类见 `10-instance-mod-compatibility-matrix.md`；代理执行模板见 `11-agent-prompts-and-task-playbooks.md`。本页是内部证据边界和勘误记录，不是 Rusted Warfare 官方规范，也不替代目标版本的原始加载器源码与实际运行。

## 1. 这页为什么存在

Rusted Warfare 模组工程同时面对三种容易混淆的对象：磁盘上的解包目录、压缩包中的虚拟路径、游戏加载器实际看到的资源系统。工具可以很擅长列目录、搜索字段和展开文本，却仍然不能证明引擎会按同样方式读取、合并、缓存、解析或调度。大型模组又常把版本标签、模板、事件、资源、地图和多语言文本交织在一起，任何一个未经声明的假设都会在报告中放大成错误结论。

本页强制执行三条优先级：

1. **原始加载器源码优先于整理文档、经验性规则和模拟器便利行为。**
2. **目标版本引擎日志和可复现运行结果优先于静态推断。**
3. **在没有足够证据时保留未知，不能以“常见做法”填空。**

“原始加载器源码”在这里指与目标 Rusted Warfare 版本相匹配、能说明入口发现、路径解析、段落解析、模板继承、字段语义或资源加载的真实实现及其测试；不是只凭类名猜测的反编译片段，也不是另一个版本的示例。若只能得到相邻版本源码，应标记为版本邻近证据，而不是目标版本事实。

## 2. 证据等级和 provenance 标记

每个重要结论都应带 provenance。这个词在本页中指结论的来源、时间、工具、版本、范围和可复核路径。没有 provenance 的“通过”“兼容”“修复”在大型模组审计中不具备足够的工程价值。

### 2.1 推荐证据等级

| 标记 | 来源 | 可以支撑的结论 | 不可以支撑的结论 |
| --- | --- | --- | --- |
| P0 | 文件名、目录名、手工描述 | 存在某个名字或路径 | 内容语义、运行行为 |
| P1 | 原始条目/文本只读读取 | 文件存在、段落/键可见、编码问题 | 引擎接受、模板合并、动作执行 |
| P2 | 静态引用图和解析器结果 | 某条显式路径可达、某个字段有消费者/缺消费者 | 动态字符串、隐式枚举、运行时顺序 |
| P3 | 与目标版本对齐的加载器源码/测试 | 某字段、根布局或解析规则的实现依据 | 所有实际内容都遵守该路径，除非闭包已检查 |
| P4 | 目标版本日志或最小引擎复现 | 指定档案、根、场景和操作的观察行为 | 未测试的其他场景、其他客户端、所有地图 |
| P5 | 重复运行和跨场景回归 | 记录范围内的稳定行为 | 永久兼容、未来版本不漂移 |

P0-P2 主要是静态证据，P3 是规则权威，P4-P5 是运行证据。静态报告可以同时写多个标记，例如“P1 文件存在，P2 显式引用可达，P4 未执行”。不要为了让表格好看而把所有结果压成一个 `pass`。

### 2.2 provenance 最小字段

建议每个报告、审计行或自动检查结果包含：

```text
provenance:
  source_root: <绝对路径或受控标识>
  source_kind: <解包根/原始rwmod/打包产物/加载器源码>
  observed_at: <时间>
  tool: <工具及版本>
  target_version: <目标游戏/加载器版本或未知>
  rule_version: <静态检查规则版本>
  path_basis: <解包物理路径/档案虚拟路径/候选根>
  evidence: <P0-P5>
  scope: <覆盖的文件、入口、场景、功能>
  excluded: <未覆盖内容>
```

`source_kind` 和 `path_basis` 必须同时出现。一个工具在解包目录上得到的结果，不能直接套用到档案虚拟根；一个在旧客户端日志中通过的结果，不能省略目标版本字段。`scope` 还要说明是全档案、一个候选根、一个单位或一个最小场景。

### 2.3 负面结论的写法

“没有找到”至少有三种含义：真的不存在、搜索规则没有识别、读取被阻断。报告必须区分：

| 不严谨写法 | 应改为 |
| --- | --- |
| 没有 manifest | 在当前候选根、编码和识别规则下未发现可识别 manifest；读取状态为…… |
| 没有单位 | 未在指定入口/扫描范围发现候选定义；其他领域、动态入口或未知语法未覆盖 |
| 没有引用 | 静态字符串搜索未发现显式引用；动态拼接、模板隐式枚举和运行时访问未证明 |
| 资源无效 | 发现静态缺失/路径模式；尚无目标引擎拒绝证据 |
| 版本不兼容 | 版本字段或加载器规则存在差异；兼容性尚未由目标版本复现 |

负面结论比正面结论更需要范围。代理应始终写“在什么根、用什么规则、检查了什么、没检查什么”。

## 3. 解包物理路径与引擎虚拟 ZIP 的差异

### 3.1 工具实际看到的是什么

多数只读审计工作在物理文件系统上执行：解包工具将压缩条目展开为目录，操作系统提供目录枚举、文件大小、时间戳、规范化路径和普通文本读取。这个环境便利，却可能改变引擎看到的输入。引擎可能直接把 `.rwmod` 当作虚拟 ZIP 或同类容器，通过自有索引、路径规范化、条目查找、缓存和资源解码逻辑读取内容。

因此，解包目录能证明“该条目被解出并可由当前工具读取”，不能自动证明“原档案虚拟根中的相同路径能被引擎访问”。差异来源包括：

- 压缩包是否保留外层目录以及入口根如何选择；
- 路径分隔符、重复分隔符、`.`、`..` 和大小写的处理；
- 重复条目由归档工具如何写入、由引擎如何选择；
- 文件名编码和规范化形式是否在解包时被改写；
- 空目录、零字节文件、时间戳和权限是否保留；
- 归档条目顺序是否影响候选入口或覆盖顺序；
- 文本流、音频、地图和图片是否走不同的虚拟资源 API；
- 引擎是否提供内置资源、模组优先级或共享路径回退；
- 解包工具是否静默跳过加密、损坏或不支持的条目。

### 3.2 两层路径检查

可靠的打包检查至少要做两次。第一层使用物理解包根，验证文本和资源的相对路径闭包；第二层对最终 `.rwmod` 重新列条目并解到新的隔离目录，再以该隔离结果重复检查。第二层能发现打包器没有包含文件、包装层改变、路径大小写变化和临时文件混入，但仍不能完全模拟引擎。

如果有目标版本加载器或引擎，第三层使用真实档案而不是解包副本。报告应明确三层结果：

| 层 | 输入 | 结果可表达为 |
| --- | --- | --- |
| L1 | 开发/解包目录 | 物理文件和静态引用状态 |
| L2 | 最终档案重新解包 | 打包条目和虚拟结构的近似检查 |
| L3 | 目标引擎直接打开档案 | 指定版本的入口和运行观察 |

L1 通过而 L2 失败，通常是打包或路径问题；L2 通过而 L3 失败，可能是加载器规则、字段语义、资源解码或运行时机制问题。不要用 L1 结果填充 L3。

### 3.3 不能用解包目录修正虚拟档案

外部来源目录和原始 `.rwmod` 必须保持只读。即使发现某个解包文件路径有问题，也不要在原档案旁边用脚本批量重命名来“验证”。应在隔离复制品中创建一个最小修复候选，记录输入摘要、变更清单和重新打包结果。否则无法知道行为变化来自配置修复，还是来自解包/打包工具的隐式改变。

## 4. 只读模拟器的已知限制

本技能可使用的只读模拟器或静态加载工具适合帮助代理查看路径、段落、引用和局部结构，但它不是 1.14/1.15 游戏引擎的替代品。它的输出应被视为 P1/P2，除非特定功能已有与目标版本加载器对齐的实现和测试。

### 4.1 当前至少应明确的缺口

| 缺口 | 模拟器能做什么 | 不能据此宣称什么 |
| --- | --- | --- |
| 物理解包而非引擎虚拟 ZIP | 展开条目、递归列路径、读普通文本 | 引擎对原档案根、条目顺序和编码的行为 |
| 未完整复现 `all-units.template` 自动默认层 | 显示模板文件或显式条目 | 静态工具自身已算出引擎的有效继承字段或已注册对象集合 |
| 无 `@copyFromSection` 完整语义 | 找到字面引用或提示未知字段 | 段落复制后的最终字段和覆盖顺序 |
| 不保证正确 `title` | 读取/显示候选标题键 | 游戏 ModInfo 页实际显示标题 |
| 不保证正确 `minVersion` | 抽取版本字段并比较字符串 | 客户端会接受、拒绝或提示哪个版本 |
| 不完成资产验证 | 检查路径存在、后缀和静态引用 | 图像、音频、地图在引擎内可解码和使用 |
| 不完成音乐验证 | 列出音乐条目和引用 | 实际播放、循环、音量、编解码和停止时机 |
| 不完成地图验证 | 列出地图/预览文件和路径 | 地图能打开、对象正确、触发器正常 |
| 不完成本地化验证 | 读取文字、键、编码、疑似换行 | 字体、转义、语言回退和 UI 排版 |
| 不完成运行时交叉引用 | 建立显式文本边 | 动态名称、事件调度、隐式对象查找 |
| 不实现完整解析器语义 | 轻量分段、键值和启发式检查 | 注释、重复段、继承、默认值和异常处理等全部等价 |

表中“无”是能力边界，不是说任何未来工具永远不能实现。只有在工具版本、规则和测试得到明确证明后，才可将某一行升级。技能文档不能通过一句“模拟器支持”替代实现证据。

### 4.2 `all-units` 不应自动脑补

对已检验的目标加载器，`all-units.template` 是目录 walker 识别的自动默认层：它会为所在目录及后代单位补充缺失字段，较近目录的模板形成更近的默认上下文。模拟器没有完整复现这一语义，因此不能把“发现了一个模板文件”或“列出了递归配置”写成有效继承结果。它尤其不能把模板文件本身伪造为已注册单位，也不能凭文件名自动得出所有冲突字段的最终值；需要原始加载器行为、目标版本日志或完整等价实现来确定祖先链、显式 `copyFrom` 与段级复制组合后的结果。

### 4.3 `@copyFromSection` 不应展开成猜测

段落复制、多个 `copyFrom`、同名段落和本层覆盖是配置语义的高风险部分。若工具不具备目标版本完整实现，应保留原始声明顺序和边，输出“可能继承字段”和“冲突候选”，不要输出一个貌似确定的最终配置。特别不能把一般 INI 库的“后者覆盖前者”当成引擎行为。

### 4.4 元数据显示不等于元数据语义

工具显示一个名为 `title` 的字段，只能说明它找到一个候选键或将另一个字段映射到显示模型。不能据此证明游戏的 ModInfo 页使用该键，也不能证明标题、描述、最低版本、缩略图、地图和音乐的所有字段都按相同解析路径工作。元数据测试要逐字段设计最小档案，并在目标版本观察。

## 5. 原始加载器源码优先规则

### 5.1 权威来源排序

遇到语义争议，按以下顺序取证：

1. 目标版本原始加载器源码和与其一起维护的测试。
2. 目标版本实际日志、错误信息和最小可复现运行。
3. 与目标版本明确对应的官方/项目内部字段说明。
4. 同一项目的已验证样例，并仅把它当使用模式而非语法规范。
5. 相邻版本源码、社区经验和静态工具行为。
6. 目录名、文件名、搜索结果和代理常识。

第 5 项可以帮助提出假设，第 6 项只能提出检查方向。若第 1 项与第 4 项冲突，源码优先；若源码和运行日志表现不一致，记录版本、构建差异、开关和复现条件，不能静默选择一个。

### 5.2 阅读源码时要定位什么

代码代理阅读加载器时，不应只搜关键字。至少定位：

- 模组根和虚拟档案入口如何确定；
- manifest/ModInfo 文件名、段落和键如何识别；
- `title`、`name`、`description`、`minVersion` 等键实际由哪个对象读取；
- 根目录、包装目录和同名文件如何选择；
- 文本编码、注释、重复段落和重复键如何处理；
- `copyFrom`、`@copyFromSection`、模板和默认值在哪里合并；
- `all-units` 或同类入口是否自动发现、排序和去重；
- 资产、地图、音乐和本地化通过哪种虚拟资源 API 查找；
- 动作、标签、资源、内存、事件和动态引用何时解析；
- 解析失败是硬错误、警告、跳过还是回退；
- 版本检查发生在入口、文件、功能或运行时哪个阶段。

每个结论都要保存源码路径、行号/方法、版本标识和与样例的对应关系。源码存在不等于所有代码路径都被覆盖；还要确认实际构建是否包含该实现。

### 5.3 源码与静态规则的关系

静态检查规则应注明它是在模拟源码规则、近似源码规则，还是纯启发式。近似规则可以对路径、字段和命名做覆盖统计，不能冒充引擎一致性。若规则是字段朴素的，例如不区分大小写、不了解上下文或不能展开动态字符串，结果应称为“候选命中”。

## 6. ModInfo 整理文档的勘误

内部整理的 ModInfo prose 曾把 `[mod]` 的 `name` 直接称为“ModInfo name”，并声称存在 `include`、`exclude`、`loadorder` 等字段或机制可以代表通用的模组依赖和加载顺序。这种整理说法必须更正。经对原始加载器来源的复核，当前可采纳的事实是：**原始来源中的 `[mod]`、标题/名称相关键以及其他字段必须按各自真实读取位置解释；不能因为整理文档把某个键写成“ModInfo name”，就把它提升为引擎统一名称契约。** 同样，未在原始加载器来源中确认的 `include`、`exclude`、`loadorder`，不能被写成 Rusted Warfare 通用的依赖系统、排除系统或模组加载顺序配置。

### 6.1 修正前后的表述

| 不应继续使用的表述 | 应使用的表述 |
| --- | --- |
| `[mod]` 的 `name` 就是 ModInfo name | `[mod]` 中出现名称相关键；其显示/身份用途须按目标版本读取路径核验 |
| `include` 会包含其他模组 | 若原始加载器和目标版本测试未证明，只能记录为未确认键/项目自定义字段 |
| `exclude` 可排除某些模组或单位 | 不把整理 prose 的字段名当作通用排除语义；需要源码和最小复现 |
| `loadorder` 控制模组加载顺序 | 未经目标加载器确认，不宣称存在通用依赖/排序系统 |
| 设置了字段就能管理依赖 | 当前技能范围不确认通用模组依赖系统；字段存在与被消费是两件事 |

这里不是建议代理盲目删除这些键。若项目源确实含有它们，应保留原样、标注来源和解析状态，并在审计中说明“未被当前权威来源确认”。修复任务若要移除或改写，必须有明确目标和回归测试。

### 6.2 为什么这一勘误重要

错误的 prose 会产生连锁误判。代理可能在一个模组中加入不存在的依赖声明，认为客户端会按 `loadorder` 排序；可能把 `include` 当作资源自动合并，漏掉显式模板；可能把 `exclude` 当作安全边界，却没有任何实际排除效果。更糟的是，静态工具会根据整理文档生成“通过”结果，掩盖引擎完全没有读取这些字段。

因此所有关于 ModInfo 的内部说明都要拆成：原始键名、原始读取位置、目标版本行为、当前工具映射、未验证语义。若只知道字段名称，不知道谁读取，就不能给它加上“控制”“包含”“排除”“排序”等动作性动词。

## 7. no dependency system 的范围结论

在当前技能范围内，不确认存在一个通用、独立、可由任意模组声明的依赖系统。这里的“未确认”不是说某个项目一定没有自己的前置检查、模板引用、资源共享、打包顺序、脚本约定或人工安装说明；它是说代理不能凭 `include`、`exclude`、`loadorder` 等整理字段宣称一个普适引擎依赖机制。

实际项目仍可能有：

- 配置文件对其他文件的显式 `copyFrom` 或路径引用；
- 全局模板或局部模板枚举；
- 共享资源目录和同一档案内部的路径约定；
- 地图、事件或单位通过名称/标签间接依赖；
- 作者在发布文本中要求某个顺序、版本或安装组合；
- 启动器、外部工具或平台层提供的排序/依赖能力。

这些都要各自取证，不能汇总成“游戏拥有通用 dependency API”。审计报告应把“档案内部显式引用”“作者安装说明”“外部工具约定”“引擎源码已证实”分成四列。没有一列能自动代替其他三列。

## 8. 静态分析的限制

### 8.1 路径和字段启发式

静态审计器常用字符串、正则、后缀、basename、大小写归一化和简单路径拼接。这些技术对发现候选问题很有价值，但不理解完整上下文时会有假阳性和假阴性。例如：

- 资源名可能由变量、标签、动作或事件动态构成；
- `copyFrom` 路径可能依赖当前段、当前文件或虚拟根；
- 同名单位可能因为命名空间、模板作用域或不同档案而不冲突；
- 一个“缺失资源”可能是内置资源、运行时生成资源或大小写规则差异；
- 重复段落可能被引擎合并、覆盖、拒绝或按特殊段处理；
- 空引用可能是可选字段、默认行为或故意的占位；
- 文件名中出现 `unit` 不表示文件是可建造单位；
- 没有 `units/` 不表示没有可加载单位。

所以启发式输出必须使用“模式”“候选”“信号”“需复核”，而不是“无效”“必崩”“已证明不兼容”。`10-instance-mod-compatibility-matrix.md` 中的实例统计同样遵守此规则：资产缺失、资产路径、`copyFrom` 缺失和重复名称计数只表示检查器覆盖命中，不能评价模组有效性。

### 8.2 交叉引用不完备

静态工具容易处理显式文本边，却难以覆盖动态交叉引用。字符串可能通过拼接、变量替换、标签映射、事件参数、地图对象属性、资源名或用户输入构造；一个定义可能由全局扫描、内置注册或运行时生成进入系统。搜索无命中只能说明当前搜索规则未发现显式边。

为了诚实，报告可以把边分为：确定显式、可能文本、动态候选、未解析。对动态候选，应给出来源行和可能的值域；不应把一个猜测值写入自动修复。高风险的动态路径需要目标版本日志、插桩或最小引擎测试补齐。

### 8.3 条件和时序不可从文本保证

隐藏动作、资源比较、标签条件和事件链可能有复杂的生命周期、更新频率、目标选择和并发时序。静态图能显示“动作 A 写入标签，动作 B 读取标签”，不能证明 A 先于 B，也不能证明 A 在每次所需场景都会触发。动作字段合法也不能证明条件可达。

任何报告涉及“只触发一次”“永远清理”“不会重复生成”“一定在死亡前执行”等时序话语，都必须附运行证据或源码级证明。没有证据时，改为“文本中存在相应分支/清理候选，时序未验证”。

### 8.4 性能只能先找放大器

静态分析可以指出每实体周期动作、全局搜索、动态生成、复制和无上限资源积累等放大器，不能量化真实帧率、内存峰值、解码耗时或多人同步成本。不同地图、单位数量、客户端设备和图形设置会改变结果。性能任务必须保留基线、测量条件和波动，不能用配置复杂度直接下结论。

## 9. 版本漂移规则

Rust​ed Warfare 1.14、1.15 以及同系列补丁不应被视为一个没有差异的语法集合。字段可能新增、弃用、改名、改变大小写处理、改变默认值、改变路径根或改变错误等级。更高版本能读取某字段，不代表旧版本能读取；旧版本曾接受某写法，也不代表新版本继续保持同一语义。

### 9.1 版本信息四分法

对每个项目同时记录：

| 版本来源 | 例子 | 处理原则 |
| --- | --- | --- |
| 目录/档案标签 | 文件夹或档案名中的版本 | 只作 P0 线索 |
| 元数据展示 | 标题、描述中的版本 | 只作 P1 文本事实 |
| `minVersion` 等字段 | 配置声明的最低版本 | 需按加载器验证 |
| 实际客户端 | 运行测试所用构建 | 是 P4 的环境条件 |

版本冲突不能通过“取最高”或“取最新”解决。案例 `AbyssStars` 的文件夹标签和元数据标题就是应分栏记录的典型；`ASEU` 的最低版本字段也只能说明文本声明，不能自动证明所有资源、模板和动作都符合该版本。

### 9.2 版本矩阵模板

```text
功能/字段：<名称>
来源文件：<绝对路径或虚拟路径>
项目声明版本：<值/无>
目标客户端：<值/未知>
原始加载器证据：<路径、方法、版本>
静态结果：<解析/未知/冲突>
运行结果：<场景、操作、日志、未执行>
兼容结论：<仅限 scope，不外推>
```

若无法填入原始加载器或目标客户端，结论必须停在静态层。迁移任务应先选择少量代表字段做双版本最小实验，而不是全局替换所有相似键。

## 10. 勘误登记格式

每次发现技能文档、整理 prose、检查器规则或案例摘要与权威来源冲突，建立勘误条目。勘误不是为了隐藏历史，而是让旧结论可追踪。

```text
勘误编号：ERR-<日期>-<序号>
发现位置：<文档/脚本/报告绝对路径>
原表述：<最小必要摘录或准确概括>
问题类型：<来源误引/版本漂移/解析器近似/范围过度/路径混淆>
权威证据：<原始加载器路径、日志或复现>
修正表述：<可直接替换的句子>
影响范围：<哪些章节、规则、任务>
状态：<待验证/已更正/需要版本分叉>
复核者与时间：<记录>
```

原表述只保留足以定位问题的短语，不把受保护的第三方配置或大量源码复制进文档。若权威证据本身属于另一个版本，要把版本写入勘误编号或正文，不能用无版本的“源码显示”。

### 10.1 本章已登记的关键勘误

| 编号 | 旧风险 | 修正 |
| --- | --- | --- |
| ERR-MODINFO-01 | 将 `[mod]` 的 `name` 直接称为通用 ModInfo name | 记录原始键和实际读取位置，不把整理名称提升为契约 |
| ERR-MODINFO-02 | 将 `include`、`exclude`、`loadorder` 说成通用包含/排除/加载顺序 | 未经原始加载器确认，不宣称通用依赖系统 |
| ERR-ROOT-01 | 把物理解包根当作引擎虚拟 ZIP 根 | 分开 L1/L2/L3，并记录包装候选 |
| ERR-TEMPLATE-01 | 看到 `all-units.template` 就自动合并全树 | 只列候选入口，等待加载器/引擎语义 |
| ERR-SECTION-01 | 用普通 INI 合并规则推断 `@copyFromSection` | 未实现/未验证时输出冲突候选，不展开最终值 |
| ERR-VERSION-01 | 从目录名或标题版本选择唯一真实版本 | 分栏记录目录、元数据、字段和客户端版本 |
| ERR-HEURISTIC-01 | 启发式命中等于模组无效 | 只写审计覆盖信号，升级结论需引擎证据 |

## 11. 无引擎访问时的替代交付

没有目标引擎不意味着任务只能停止；它意味着交付目标必须降级且写清边界。

### 11.1 可以完成的工作

代理可以在只读或白名单写入条件下完成：

- 递归列出解包根和档案重新解包结果；
- 统计配置、模板、地图、音乐、图像和其他文本候选；
- 识别入口候选、包装层和 manifest-less 状态；
- 建立显式 `copyFrom`、段落、动作、标签、资源和资产引用图；
- 检查静态相对路径存在性、重复名字、编码和明显循环；
- 比较变更前后条目清单和精确 diff；
- 生成目标版本运行测试清单、最小复现和观测点；
- 标记启发式命中并列出人工复核所需上下文；
- 在隔离副本打包、重新解包并核对条目。

### 11.2 不能宣称的工作

没有目标引擎时，不能宣称模组已加载、单位在 UI 出现、地图可进入、音频可播放、图像能渲染、动画/AI/动作时序正确、多人同步正常、资源收支平衡、性能改善、版本兼容或所有跨引用有效。模拟器空白、解析器通过和重新解包成功都不能自动升级这些结论。

### 11.3 无引擎报告模板

```text
静态结论：<P1/P2 可证明的事实>
目标环境：未提供/不可用 <版本>
已完成：<扫描、图、打包、差异、检查>
未完成：<入口运行、资源解码、地图、动作时序等>
候选风险：<按严重度排序>
最小运行测试：<步骤、场景、预期观察>
停止原因：<无引擎/版本未知/语义未实现>
```

## 12. 何时必须暂停并请求证据

代理不应因为任务描述带有“修好”“兼容”“全部扫描”就无限猜测。遇到以下情形应暂停或降级：

- 目标版本未给出且字段行为可能跨版本变化；
- 入口存在多个候选，无法用源码或日志选定；
- 解包目录和档案根布局不一致；
- 重复段落、多个 `copyFrom` 或段落复制的覆盖顺序未证实；
- manifest-less 档案的内容是否属于旧式入口未知；
- 资源路径包含动态字符串、大小写冲突或多个同名候选；
- 动作、事件、标签、内存或资源没有明确生命周期；
- 任务要求删除、批量重命名或写入外部源；
- 模拟器给出结果但没有目标引擎对应实现；
- 整理 prose 与原始加载器来源冲突；
- 静态启发式命中可能有明显上下文依赖。

暂停报告应给最小问题，而不是一长串泛泛请求。例如：“请提供目标客户端构建和一个能复现对象不出现的地图；当前静态结果只到 P2，无法判断入口还是条件问题。”

## 13. 最终限制清单

- [ ] 本工具处理的物理解包目录不等于引擎读取的虚拟 ZIP 根。
- [ ] 没有 `all-units` 自动合并能力时，不脑补全量枚举。
- [ ] 没有 `@copyFromSection` 完整语义时，不生成最终合并值。
- [ ] 不把候选键当成正确的 `title`、`minVersion` 或 ModInfo 显示语义。
- [ ] 资产、音乐、地图和本地化检查只做静态或包级检查时，明确未做运行验证。
- [ ] 不把静态交叉引用图当作动态运行时闭包。
- [ ] 不把字段启发式命中当成模组无效或引擎不兼容。
- [ ] 不把目录版本、元数据版本和客户端版本合并成一个真值。
- [ ] 不把 `include`、`exclude`、`loadorder` 当作已证实的通用依赖系统。
- [ ] 原始加载器源码、目标版本日志和最小复现优先于整理 prose。
- [ ] 所有重要结论都带 provenance、范围和未覆盖项。
- [ ] 无引擎时输出静态结果与运行测试计划，不输出虚假的通过结论。

## 14. 结语

限制不是让代理少做工作，而是让每一项工作落在它真正能够证明的层面。一个好的静态审计可以非常有用：它能发现包装根、入口候选、模板冲突、资产断链、重复命名、编码风险、生命周期缺口和性能放大器；它还能为目标版本引擎生成最小而高价值的测试计划。它不能凭目录和字符串取代加载器，也不能凭模拟器便利行为代替真实客户端。

在 Rusted Warfare 1.14/1.15 这样的版本敏感环境中，最可维护的结论通常不是一句“支持”或“不支持”，而是一条有来源的链：哪个根、哪个版本、哪个文件、哪条显式边、哪个工具、哪个测试、哪个未覆盖范围。只要这条链被保留，未来当原始加载器、打包器、模组结构或客户端版本发生变化时，团队就能修正一个具体假设，而不必重新猜整套系统。

## 15. 冲突决策树

当静态结果、整理文档、模拟器和引擎行为不一致时，代理应按决策树处理，而不是选择最方便的答案。

```text
发现冲突
  -> 是否有目标版本原始加载器源码/测试？
       是 -> 定位实际读取路径和构建版本
              -> 与目标版本日志/最小复现对照
       否 -> 是否有目标版本可复现日志？
              是 -> 缩小到档案、根、场景和操作
              否 -> 是否只是静态启发式与目录观察冲突？
                     是 -> 保留候选信号，降低结论
                     否 -> 标记未知，提出最小证据请求
```

如果源码显示一个字段被忽略，而样例中恰好能运行，不要立刻判定源码错；先检查样例是否通过默认值、另一个字段或内置资源获得同样结果。如果日志显示加载成功，而静态工具报告缺失，检查工具是否不认识虚拟资源、动态路径或大小写规则。冲突记录需要保留双方事实和版本条件，直到产生可以解释差异的新证据。

### 15.1 典型冲突处理表

| 冲突 | 第一反应 | 暂时结论 |
| --- | --- | --- |
| 目录有文件，游戏不出现 | 查入口、包装根、条件和日志 | 文件存在不等于注册 |
| 静态缺资源，游戏能启动 | 查内置资源、可选字段和规则上下文 | 启发式可能是假阳性 |
| 模拟器能显示标题，游戏标题不同 | 查目标版本读取键和字段映射 | 模拟器显示不是 ModInfo 语义 |
| 解包根可读，原档案失败 | 查虚拟路径、打包条目和压缩差异 | 物理根不等于虚拟根 |
| 整理 prose 说有排序字段，源码未读取 | 建勘误并停止使用该语义 | 未确认通用依赖系统 |
| 相邻版本通过，目标版本失败 | 比较版本源码、字段和错误等级 | 不跨版本外推 |

## 16. 静态报告的可复核性标准

一个报告即使不修改文件，也应能被另一代理重跑。最低标准包括：固定输入清单或来源摘要；写出扫描根和候选根；写出规则版本；列出实际读取文件；保存错误而非静默跳过；对每个聚合数字给出分母；区分 P0-P2 与 P3-P5；为未覆盖动态引用和运行时语义列出下一步。

### 16.1 复跑协议

1. 在同一来源快照或同一摘要档案上重建输入清单。
2. 使用同一工具版本和规则版本；若改变，生成新结果而不覆盖旧结果。
3. 比较条目数量、候选根、入口状态、错误类别和聚合统计。
4. 对发生变化的行记录原因：输入变化、规则变化、编码环境变化或非确定性排序。
5. 若结论升级到 P4/P5，附客户端构建、场景和操作；静态复跑不能冒充运行复跑。

复跑协议能发现很多假稳定：同一个档案在不同解包工具下路径编码不同，检查器在不同大小写环境下得到不同资产结果，或规则升级后把原本“未知”变成“缺失”。这些差异应进入勘误或工具限制，而不是被抹平。

## 17. 修复建议的证据门槛

不同风险需要不同证据。路径拼写的精确修复通常可以在静态反向引用确认后进行；模板覆盖顺序、重复段落、动作时序和版本迁移则需要更高门槛。建议按下表决定是否可以编辑：

| 变更 | 最低建议门槛 | 没有门槛时的交付 |
| --- | --- | --- |
| 修正明确错拼的相对路径 | P1 文件存在 + P2 引用闭包 | 报告候选，不自动改 |
| 补充入口条目 | 入口规则有 P3 或已复现样例 | 生成实验 diff |
| 抽取共享模板 | 多个消费者 + 字段覆盖分析 | 只交模板设计，不迁移 |
| 改重复段落 | 目标加载器 P3 或最小 P4 | 报告重复和冲突 |
| 改隐藏动作/状态 | 状态图 + 至少一条正负测试 | 给出待测补丁候选 |
| 改版本字段 | 目标版本源码/日志 | 分栏记录版本差异 |
| 删除历史/复制文件 | 无入边、无动态候选、回滚 | 保留并标风险 |
| 批量重命名资产 | 完整反向引用 + 成品重解包 | 只生成映射表 |

“最低建议门槛”不是法律规则，而是降低误修改的工程门槛。任务发起者可以授权更高风险的实验，但代理必须在交付中说明缺少了哪项证据。

## 18. 限制内容的维护

本页也会过时。引擎升级、加载器源码补齐、模拟器新增语义、档案审计规则改进和案例复现都可能改变限制。维护时不要把已验证的一个字段写成所有字段已验证；应新增具体版本、具体路径、具体测试，并保留旧版本分支的限制。

限制条目的生命周期建议为：提出未知 -> 找到权威来源 -> 创建最小复现 -> 更新证据等级 -> 修改正文 -> 在勘误表保留旧表述和变更原因。若只删除旧句子，未来读者无法知道为什么规则变化，也无法判断旧报告是否需要重跑。

## 19. 交付前限制检查

- [ ] 报告说明输入是解包目录、原始档案还是重新打包产物。
- [ ] 报告区分物理路径、虚拟 ZIP 根和目标引擎行为。
- [ ] `all-units`、`@copyFromSection`、`title`、`minVersion`、资产、音乐、地图、本地化和动态引用未被过度模拟。
- [ ] 使用了 `[mod]`、`include`、`exclude`、`loadorder` 的表述已按本章勘误校正。
- [ ] 没有把启发式统计写成模组无效或引擎拒绝。
- [ ] 版本标签、元数据字段和客户端构建分别记录。
- [ ] 每个重要结论有 provenance、证据等级、范围和未覆盖项。
- [ ] 无引擎时提供最小运行测试，而不是虚构通过。
- [ ] 冲突有决策树、复现条件和待补证据。
- [ ] 修复建议的证据门槛与变更风险相称。
