# 打包、发布与回归

> 入口：先阅读 [SKILL.md](../SKILL.md)。发布前同时复查 [04-行动、逻辑、资源、效果与状态](04-actions-logic-resources-effects-and-state.md)、[05-素材、音频、本地化与地图](05-assets-audio-localization-and-maps.md)、[06-交叉引用、验证与调试](06-cross-references-validation-and-debugging.md)。
>
> **来源与权威性。** 本章是内部发布工程指南，不是引擎官方规范。所有兼容、路径与加载结论必须在目标 Rusted Warfare 1.14/1.15 版本及最终归档中验证。历史模组实例可用于测试旧包、新包与缺 manifest 包的兼容表现，但不是新项目的规范模板。不得从 `W:\mao\tx\模组加载器` 发布任何文件或文档内容，其 README 已标记为内部且不可公开；也不要复制第三方单位配置、地图或受保护加载器反编译内容。

## 本章目标

发布不是把开发目录随手压缩后改扩展名。`.rwmod` 是 ZIP 归档，且归档内的路径、根结构、文本条目名、manifest、地图二级资源、图片、音频、locale 和单位扫描路径共同决定它是否真能安装和运行。源目录通过并不能证明发行包通过，因为开发机可能意外提供根外文件、旧资源、未压缩依赖或不同目录层级。

本章定义一条可复现发布链：

`可审计源树 -> 干净 staging 根 -> 归档清单 -> UTF-8 ZIP -> 归档内容检查 -> 引擎安装/加载 -> 回归矩阵 -> 版本与发布说明一致`

目标不是制造繁琐流程，而是避免四类高成本事故：

1. 包能解压却不是引擎可识别的 mod；
2. 开发目录正常，`.rwmod` 因缺资源或根层级错误失效；
3. 版本、文档、manifest 和实际内容不一致；
4. 修复一个配置或素材时破坏已有单位、地图、语言或性能。

## 一、归档模型：`.rwmod` 是可验证的 ZIP

### 1. 基本结构

`.rwmod` 本质上是 ZIP，不是“任意解压目录”。构建工具应生成一个可以按 ZIP 读取、列出、检查并由游戏载入的归档。不要使用依赖操作系统特殊属性、快捷方式、外部软链接、绝对路径或只在开发工具可理解的容器形式。

最低要求：

| 属性 | 发布要求 | 为什么 |
|---|---|---|
| 容器 | 标准 ZIP，可改名为 `.rwmod` | 引擎按归档读取，不保证理解其它格式 |
| 条目名 | UTF-8 编码 | 中文或非 ASCII 名称跨工具不应乱码 |
| 根 | 一个明确、预期的模组根 | manifest 和相对资源才能稳定解析 |
| 文件集 | 仅运行必需内容 | 降低泄漏、体积和歧义 |
| 路径 | 相对、规范化、位于模组根内 | 防止开发机偶然依赖和根外访问 |
| 可读性 | 构建后可列出并抽查内容 | 及早发现损坏或意外空包 |

“能用压缩软件打开”只是最弱检查。构建完成后还要用至少一个独立读取路径列出条目，并把同一归档交给目标游戏安装、启用、加载单位和地图。

### 2. 包根与包装目录

引擎可以接受一层包装目录，但构建时仍推荐恰好一个预期的 mod root。它使 manifest、相对引用、问题定位和后续自动审计都有稳定基准。不要依赖“引擎会猜出第二层或第三层目录才是真根”的偶然宽容。

以下结构用于说明差异，文件名均为新写的示意：

```text
合格目标：
archive.rwmod
  mod-info.txt
  units/signal_pylon.ini
  assets/images/signal_pylon.png
  maps/echo_valley.tmx

可接受但不推荐依赖的单层包装：
archive.rwmod
  EchoValley/
    mod-info.txt
    units/signal_pylon.ini

高风险的多层或混杂根：
archive.rwmod
  export/
    EchoValley/
      mod-info.txt
  assets/...
```

包装目录被接受不代表任意布局被接受，也不代表相对素材、地图缩略图和 TSX 的解析基准会按作者愿望变化。构建脚本应明确设置归档根，不要从一个上级工作目录盲目压缩。

### 3. 根完整性检查

归档完成后应执行以下只读审计：

1. 列出全部 ZIP 条目，确认不存在空的意外前缀。
2. 找到 manifest，确认只有一个预期的模组根候选。
3. 检查单位、素材、locale、maps 与 manifest 路径相对于该根一致。
4. 检查没有以 `/`、盘符、`..` 或不规范重复分隔符开始的条目。
5. 检查条目文件名 UTF-8 可读，不发生乱码或同名冲突。
6. 将关键资源清单与归档条目逐项比对。
7. 在不依赖源目录的位置安装该归档。

最后一步不可省略。若游戏运行时仍能访问开发目录或旧包，同一台机器可能给出假阳性。使用新的安装位置、临时移走源目录或以独立测试设备验证，才能发现漏包。

## 二、发布源树：只交付运行时所需内容

### 1. staging 是发布边界

不要直接把整个项目目录压缩。应从经过选择的 staging 根构建；staging 根只包含引擎运行所需文件。它可以是构建过程中的临时目录或明确白名单的文件集，重点是构建输入可审计、输出可复现。

| 应进入 staging | 不应进入 staging |
|---|---|
| manifest 与单位配置 | `.git`、`.github`、本地 hooks |
| 实际引用的图片、音频、locale | `node_modules`、依赖缓存、构建缓存 |
| TMX、TSX、图块、预览、音乐 | 编辑器临时文件、自动保存、锁文件 |
| 发布所需脚本数据或文档，若引擎/发行明确需要 | `.bak`、`.tmp`、`~` 结尾备份 |
| 必要许可或署名文本，若发布政策需要 | Photoshop、音频工程、原始导出工程 |
| 经验证的兼容资源 | `copy (1)`、`最终版2`、废弃内容副本 |

“也许以后有用”的源文件不属于运行时包。将它们留在版本控制或资产源库中。发布包越像一个完整但最小的运行时根，越容易证明没有多余内容、没有许可证意外泄漏，也越容易在别的机器上复现。

### 2. 删除而非隐藏废弃物

发布根中常见的残留包括 `unit.ini.bak`、`old/`、`copy/`、`new folder/`、`map (1).tmx`、空目录、输出 ZIP 的自我嵌套、和只供作者预览的 PNG。不要把这些内容当作“无害”。它们会造成：

- 误扫描到旧单位或旧地图；
- 相对路径引用错到同名旧资源；
- 包体积增长与发布内容不可审计；
- 许可不明或内部笔记被分发；
- 用户或后续代理无法判定哪个文件才是权威版本。

构建应该采用允许列表，不要靠一长串排除规则期待永远跟上新工具产生的垃圾。若项目确需保留多个版本资源，给每个资源一个运行时用途与唯一引用，而不是依赖“作者知道该选哪个”。

### 3. 文件名和 ZIP 条目名

归档的文件名应稳定、可跨平台比较。推荐使用 ASCII、小写、短横线或下划线作为内部路径；玩家展示文本可以通过 locale 使用中文。若必须存放非 ASCII 文件名，构建后必须验证 ZIP 条目名为 UTF-8，且目标游戏、目标设备能读取。

| 风险 | 例子 | 处理 |
|---|---|---|
| 大小写冲突 | `Gun.png` 与 `gun.png` | 统一为一个小写路径并改全引用 |
| 复制残留 | `laser (1).ogg` | 重命名为表达用途的唯一名称 |
| 非标准编码 | 解压后显示乱码 | 使用支持 UTF-8 条目名的 ZIP 工具，重新构建 |
| 路径逃逸 | `../shared/x.png` | 拒绝进入 staging，修正为根内资源 |
| 隐藏扩展名 | `unit.ini.txt` | 在构建清单中按真实扩展名审计 |
| 同名不同位置 | 多处 `icon.png` | 采用语义路径和显式引用 |

文件名整理不等于大规模重构。只在修改或新增相关资源时修正明显歧义，随后使用搜索和归档清单更新所有调用方。

## 三、manifest、版本与发布身份

### 1. 版本必须是一个事实，不是四段不同文字

模组的可识别版本至少出现在 manifest；它可能也会出现在发布文件名、变更说明、兼容性表和用户可见描述。采用文档化的 semver 风格版本，例如 `1.4.0`，并确保这些位置一致。这里不强制某一种语义版本政策，但必须让团队能解释每一段含义。

| 位置 | 应匹配什么 |
|---|---|
| manifest | 权威发布版本 |
| 归档文件名 | 同一版本，方便用户和测试者识别 |
| 发布说明 | 同一版本、日期、目标游戏版本和变更摘要 |
| 回归报告 | 测试的是哪一个构建号 |
| 游戏内显示 | 若可见，应能与 manifest 对照 |

不要发布“最新版”“final”“修复版”而没有可比较的版本号。也不要仅修改归档文件名而忘记 manifest；这会使用户报告无法对应真实内容。

### 2. 版本递增的决策表

可以采用下列工程约定，并在项目内保持一致：

| 变化类型 | 示例 | 建议版本意图 |
|---|---|---|
| 修复 | 修正一个缺图片或错误 `canBuild` 引用 | 补丁级递增 |
| 向后兼容内容 | 新增独立单位、地图、locale | 次级递增 |
| 不兼容修改 | 删除/改名公开单位、改变地图约定、放弃旧版本支持 | 主级递增或明确兼容标记 |
| 仅构建元数据 | 重打同内容包或内部测试 | 追加构建标识，不伪装为玩法版本 |

这不是引擎依赖解析机制。经检查的引擎不提供可供模组声明的依赖/加载排序功能；不得在发布说明里声称“版本号会自动解决模组依赖”或“按顺序加载其他模组”。版本号只帮助人和测试流程识别内容。

### 3. 发布身份最小清单

每个候选包应有一份与其并行的发布记录，包含：

- 模组名称与 manifest 版本；
- 归档文件名与哈希或构建时间；
- 目标 Rusted Warfare 版本及实际测试版本；
- 是否含地图、音乐、非 ASCII 条目名；
- 关键新增/修复与已知限制；
- 运行时回归覆盖范围与未覆盖项；
- 资产和许可状态；
- 构建人或自动化步骤的可重复说明。

这份记录不必被打进 `.rwmod`。它属于发布工程证据，帮助区分“包内容错误”“用户安装错版本”“引擎版本差异”和“未覆盖行为”。

## 四、构建流程：从白名单到可复现包

### 1. 推荐的构建阶段

1. **冻结输入。** 确认计划发布的版本、目标游戏版本、已批准变更和干净或已记录的工作树状态。
2. **生成 staging。** 依据允许列表复制运行时文件，保留预期根结构。
3. **静态审计。** 检查 manifest、单位目录深度、引用、素材、locale、地图依赖和排除项。
4. **创建 ZIP。** 用明确的根目录、UTF-8 条目名和稳定排序生成 `.rwmod`。
5. **归档审计。** 列出条目、验证关键文件、拒绝嵌套包和垃圾文件。
6. **安装测试。** 在不依赖源目录的位置启用该包，确认 manifest 和版本。
7. **运行回归。** 执行本章矩阵以及 [06-交叉引用、验证与调试](06-cross-references-validation-and-debugging.md) 的关键运行时测试。
8. **发布门禁。** 只有所有阻断项关闭、已知风险清楚记录、版本一致时才发布。

构建脚本的价值在于固定这些步骤，不在于使用某个特定语言或工具。对于无法自动化的游戏 UI 步骤，脚本仍应输出准备好的清单、版本和包路径，避免人工挑错文件。

### 2. 允许列表示例

以下是概念性清单，路径和文件名均为新写示意；它不是要求每个模组都拥有相同目录：

```text
include:
  mod-info.txt
  units/**/*.ini
  assets/images/**/*.png
  assets/audio/**/*.ogg
  assets/audio/**/*.wav
  locale/**/*.properties
  maps/**/*.tmx
  maps/**/*.tsx
  maps/**/*.png

exclude:
  .git/**
  node_modules/**
  **/*.bak
  **/*.tmp
  **/* (1).* 
  **/thumbs.db
  **/.ds_store
```

生产实现不要只复制上面的排除表达式。更稳健的方式是从 `include` 生成 staging，再拒绝未知文件。若地图实际使用 JPEG、对象模板或额外数据，也必须显式加入允许列表和依赖审计。允许列表应从真实引用图演化，而不是把整个资源盘放行。

### 3. 可复现性与时间戳

若构建工具支持，保持条目排序、根路径和压缩策略稳定，避免同一输入产生结构随机的归档。是否需要字节级一致取决于项目政策，但至少应能回答：“这个包从哪些文件、通过什么命令、在哪个版本号下构建”。

时间戳、压缩级别和平台差异可能使哈希不同；这不妨碍内容可审计。关键是归档清单、版本、资源路径和运行时结果一致。不要为了追求哈希一致而牺牲 UTF-8 条目名或目标游戏兼容性。

### 4. 构建后的独立读取

每次构建后至少用独立于打包工具的读取方式检查：

| 检查 | 目的 |
|---|---|
| ZIP 完整性测试 | 确认归档没有损坏或截断 |
| 条目列表 | 确认根、manifest、路径、大小写和垃圾文件 |
| 关键文件提取/读取 | 确认文本和图片不是零字节或错误副本 |
| UTF-8 名称显示 | 确认非 ASCII 条目不乱码 |
| 依赖清单对比 | 确认图片、音频、locale、TMX/TSX 均在包内 |
| 安装后的游戏显示 | 确认引擎识别的是当前包 |

不要只检测“压缩命令退出码为零”。它只能说明工具生成了一个文件，不能说明文件集或根结构正确。

## 五、兼容性：旧包用于测试，不用于定义新规范

### 1. 观察遗留实例的正确方式

模组实例可能展示了无 manifest 包、旧目录层级、新旧命名方式、根包装、过时字段或历史素材布局。它们适合帮助建立兼容测试问题：游戏是否识别一个包装根？缺 manifest 时用户看到什么？旧版地图路径会怎样失败？它们不适合成为新模组的复制模板。

| 观察到的遗留形态 | 应转化为的测试 | 不应得出的结论 |
|---|---|---|
| 一层包装目录 | 最终包是否仍被目标引擎识别 | 新项目应无限增加包装层 |
| 缺 manifest 的旧包 | 引擎错误与用户体验如何 | manifest 可以省略 |
| 旧字段仍被加载 | 目标版本的兼容性行为 | 旧字段永远推荐或无风险 |
| 相对路径奇特 | 打包后是否仍可解析 | 可随意使用根外跳转 |
| 同时有全局和局部资源 | 两类资源如何被案例使用 | 某个具体经济模式是规范 |

兼容承诺必须是明确的：“已在版本 X 的最终 `.rwmod` 测试 Y 场景”，而不是“参考了旧模组所以应该兼容”。

### 2. 不宣称不存在的依赖/排序特性

检查到的引擎没有可依赖的模组依赖或加载排序功能。发布文本、README、安装说明和配置注释都不得声称“本包会自动先于某包加载”“某包作为硬依赖会被解析”或“版本号决定加载顺序”。

对于外部内容的关系，采用保守表述：

- 若内容必须单独存在，说明它不是可保证的内置依赖，并把本包设计为在缺失时仍可加载或不提供该入口；
- 若只是在某些环境被测试过，写为“测试环境包含……”而非“引擎要求并加载……”；
- 若替换核心或其它 ID，按目标版本明确验证 `overrideAndReplace`，不把它包装成通用跨模组依赖系统；
- 若无法保证关系，去掉未验证的跨包引用，而不是让用户靠加载顺序碰运气。

### 3. 版本矩阵

对 Rusted Warfare 1.14/1.15 的支持应以矩阵记录。1.15p11 的 memory 相关支持不自动说明 1.14、其它 1.15 补丁或第三方运行环境也有相同行为。

| 功能 | 1.14 | 1.15 基线 | 1.15p11 | 说明 |
|---|---|---|---|---|
| 基础单位与素材 | 实测/未测 | 实测/未测 | 实测/未测 | 写具体构建日期和包版本 |
| memory 相关状态 | 实测/不支持/未测 | 实测/未测 | 实测/未测 | 不从文档推断兼容性 |
| locale 回退 | 实测/未测 | 实测/未测 | 实测/未测 | 覆盖中文、英文和默认 |
| 地图与 TSX | 实测/未测 | 实测/未测 | 实测/未测 | 从最终包加载 |
| 音频解码 | 实测/未测 | 实测/未测 | 实测/未测 | 覆盖 `.ogg`/`.wav` 实用路径 |
| 压力场景 | 实测/未测 | 实测/未测 | 实测/未测 | 记录单位数、地图和设备 |

未测不是失败，也不是支持。将未测保留为未测，能让发布决策者清楚判断风险。

## 六、回归测试：以用户路径而非文件列表为中心

### 1. 为什么每次发布都需回归

模组的交叉引用广：改一个 `copyFrom` 模板、投射物、资源名、图片路径、locale key 或地图 tileset，可能影响多个未直接编辑的单位。打包还引入第二次变换：源树正确而归档错误。回归用来证明已有工作路径没有被新变化破坏。

回归不是“逐文件打开一次”。它应覆盖玩家从启用包到玩一局的路径：模组被识别、文本可读、单位可生产、动作可执行、战斗可发生、地图可加载、存档可恢复、最终包无开发机依赖。

### 2. 分级测试集

| 级别 | 触发条件 | 最少覆盖 | 失败处理 |
|---|---|---|---|
| 烟雾 | 任意配置/资源变更 | 安装、启用、加载、一个单位、一个地图或默认图 | 阻断发布 |
| 定向 | 改到某个功能域 | 相关单位、动作、资源、素材、locale 或地图链 | 阻断相关发布 |
| 全量 | 发布候选、大范围模板变更、版本升级 | 所有公开单位族、地图、语言、AI、存读档、压力 | 阻断正式发布 |
| 兼容 | 声称支持多版本或遗留包 | 版本矩阵中的关键路径 | 未覆盖必须写明 |
| 打包 | 每次生成 `.rwmod` | 独立归档清单、安装、最终包运行 | 阻断发布 |

烟雾测试速度必须足够快，才能每次构建执行。全量测试可以较慢，但发布候选不应跳过。

### 3. 核心回归矩阵

| 功能域 | 基本用例 | 边界/失败用例 | 通过证据 |
|---|---|---|---|
| manifest | 启用后显示正确名称和版本 | 根包装、错误版本、旧包未混入 | 游戏内显示与归档一致 |
| 单位扫描 | 所有公开单位被发现 | 深度、坏编码、复制来源缺失 | 无解析错误或未解释警告 |
| 生产 | `canBuild` 入口可见、能完成 | 缺资金、锁定、取消、AI | 菜单、资源和产物正确 |
| `builtFrom` | 每个单位有预期来源 | strict 1、来源缺失、菜单位置冲突 | 无未解释告警，入口可用 |
| action | 可见、可点、费用/冷却正确 | 连点、资源不足、自动重入 | 状态与文本一致 |
| 战斗 | 炮塔和投射物正确 | 空陆水目标、友军、无目标 | 伤害、效果、声音正确 |
| 状态/资源 | 计数、模式、memory 正确 | 上下界、转化、死亡、读档 | 不变量仍成立 |
| 图片 | 主体、队色、阴影、帧正确 | 缺图、错误模式、缩放 | 无加载错误与视觉异常 |
| 音频 | 文件/内建音实际播放 | 解码失败、群集频率 | 无非预期回退/噪声 |
| locale | 中文、英文、默认可读 | 区域回退、缺键、动态文本 | 无键名泄漏和溢出 |
| 地图 | 预览、列表、进入、重开 | 缺 TSX、图块、不同队伍、音乐 | 最终包完整加载 |
| 存读档 | 保存、退出、恢复 | 状态机中间态、队列、地图对象 | 状态语义可接受 |
| 性能 | 常规单位数 | 密集单位、粒子、循环与长局 | 无明显无界增长 |

这张表不表示每次都可人工覆盖所有组合。它要求每个发布候选选定基线、记录覆盖、针对改动扩展定向用例，并在高风险变更时跑全量。

### 4. 变更类型到回归范围

| 改动 | 不足的测试 | 最少扩展回归 |
|---|---|---|
| 仅改一个 PNG | “文件存在” | 主体/炮塔/队色/缩放与最终 ZIP |
| 改音频 | 本地播放器试听 | 目标游戏解码、调用点、群集频率、最终 ZIP |
| 改 locale | 一个语言截图 | 中文、英文、默认、回退、动态文本、按钮宽度 |
| 改 action | 点一次成功 | 费用不足、连点、重入、冷却、AI、状态边界 |
| 改资源/内存 | 数值显示一次 | 初始化、上限、转换、死亡、存读档、版本矩阵 |
| 改 projectile/effect | 单位加载 | 所有调用炮塔、生成/递归、性能和音效 |
| 改 `canBuild`/`builtFrom` | 一个工厂菜单 | 全部入口、strict 1、AI、升级、目标存在 |
| 改 `copyFrom` 模板 | 被编辑单位 | 所有继承者的关键字段和运行场景 |
| 改地图/TSX | 编辑器预览 | 地图列表、最终包、外部依赖、重开、音乐、多队伍 |
| 改打包脚本 | ZIP 可打开 | 条目清单、UTF-8、根、干净安装、全量烟雾 |

## 七、发布门禁和风险分级

### 1. 阻断项

以下任一项未关闭，不应发布正式 `.rwmod`：

- manifest 缺失、根结构不明确、ZIP 损坏或条目名乱码；
- mod 解析错误或未解释的严重警告；
- 任何未知/未使用字段、错误 LogicBoolean、重复命名；
- 缺失 `canBuild` 目标，或 strict 1 下未解释的 `builtFrom` 问题；
- 关键图片加载失败、无 `[graphics]image`、`total_frames < 1`、不兼容队色组合；
- 自有音频扩展名或解码错误导致非预期回退；
- 关键 locale 键缺失、玩家看到内部键或文本不可读；
- TMX、TSX、图块、预览或音乐的必要依赖漏入最终包；
- 源目录通过但最终 `.rwmod` 安装/加载失败；
- 发布内容含内部不可公开材料、无授权素材或明显敏感文件；
- manifest、归档名和发布记录版本不一致。

### 2. 可记录但不能伪装为已验证的风险

有些风险不能在当前环境完全消除，例如未拥有某个旧版本设备、未完成多人压力或未能覆盖每种语言。它们可以被记录，但发布记录必须准确：

| 风险 | 可接受的记录方式 | 不可接受的写法 |
|---|---|---|
| 未测 1.14 | “仅在 1.15p11 实测；1.14 未验证” | “支持 1.14+” |
| 未测多人 | “单人和 AI 已测，多人未测” | “多人稳定” |
| 未测低端设备 | “未做低端设备压力” | “无性能问题” |
| 历史包行为不确定 | “旧包仅作对照，未作为兼容承诺” | “兼容所有旧模组” |
| 翻译待审 | “英文已审，日文未覆盖” | “全部本地化完成” |

风险记录不是免责文字。它应指导下一次测试优先级，也帮助用户或发布负责人判断是否接受候选包。

### 3. 候选包签核清单

- [ ] staging 从允许列表构建，未直接压缩开发根。
- [ ] `.rwmod` 作为 ZIP 可读取，条目名 UTF-8，根结构为一个预期 mod root。
- [ ] manifest、归档文件名、发布记录和游戏内显示版本一致。
- [ ] 无 `.git`、`node_modules`、编辑器缓存、`.bak`、复制残留、源工程或嵌套归档。
- [ ] 关键单位、图片、音频、locale、地图和二级依赖在归档中。
- [ ] 归档在干净位置安装并被目标游戏识别。
- [ ] 烟雾、定向、打包测试全部通过；高风险变更已跑全量或记录未覆盖。
- [ ] 无解析错误、未知键、重复 ID、缺 `canBuild` 目标或未解释 strict 问题。
- [ ] 未从内部不可公开目录或受保护内容引入材料。
- [ ] 已知风险、目标版本和未覆盖场景写入发布记录。

## 八、回滚、热修与发布后观察

### 1. 不可用包的处理

若发布后发现 manifest 不识别、加载失败、地图缺资源或严重运行时回归，优先停止分发该归档，保留原始候选包、归档清单、版本和错误日志。不要就地覆盖同名文件又不改变版本号；这会使用户报告与实际二进制内容脱节。

热修流程应是：

1. 固定失败包的版本和哈希；
2. 创建最小复现，确认根因属于打包、配置、资源还是运行时；
3. 修复最小范围，增加针对性回归；
4. 递增文档化版本，更新 manifest、归档名和发布记录；
5. 从 staging 重建，重复归档和游戏测试；
6. 发布明确的修复说明和已知影响范围。

### 2. 发布后观察项

即使候选包通过回归，仍应收集可行动的外部反馈：

| 信号 | 可能说明 | 下一步 |
|---|---|---|
| 用户看不到模组 | 根、manifest、安装路径或版本问题 | 索取归档清单与游戏版本 |
| 仅地图失败 | 漏 TSX/位图/音乐或地图注册差异 | 递归检查地图依赖与最终包 |
| 仅某语言异常 | locale 键、回退或动态文本问题 | 按语言矩阵复现 |
| 仅战斗时卡顿 | 生成链、效果、声音或轮询放大 | 用密集测试地图量化 |
| 仅旧版本失败 | 字段或 memory 支持差异 | 更新版本矩阵与兼容声明 |
| 用户报告版本不一致 | 同名包被覆盖或 manifest 未同步 | 固定版本、哈希和发布通道 |

反馈必须能关联到一个具体 `.rwmod` 版本和目标游戏版本；否则先要求这些信息，再进入代码层排查。

## 九、面向编码代理的发布工作流

### 发布前一天或变更冻结时

- [ ] 确定版本号、兼容范围、目标游戏版本和发布窗口。
- [ ] 记录工作树基线，不清理或还原其他代理的改动。
- [ ] 确认所有批准变更已经有定向测试计划。
- [ ] 审查资产来源和发布边界，排除内部 `W:\mao\tx\模组加载器` 内容。
- [ ] 更新引用清单和地图依赖图，特别是新增图片、音频、TSX、locale 与单位 ID。

### 构建候选包时

- [ ] 从白名单生成 staging，保持一个预期根。
- [ ] 生成具有 UTF-8 条目名的 ZIP `.rwmod`。
- [ ] 独立读取归档，检查根、manifest、关键文件、大小写、零字节、垃圾和嵌套归档。
- [ ] 将归档条目与资产、地图、locale、单位依赖清单比较。
- [ ] 更新 manifest、归档名、发布记录中的同一 semver 风格版本。

### 验收时

- [ ] 在不依赖源目录的安装位置启用候选包。
- [ ] 运行烟雾、定向、打包回归；根据风险运行全量与兼容矩阵。
- [ ] 使用 [06-交叉引用、验证与调试](06-cross-references-validation-and-debugging.md) 的分层证据记录所有失败与修复。
- [ ] 明确写出未测版本、多人、设备和语言；不作超出证据的兼容承诺。
- [ ] 确认静态审计不被误写成运行时保证。

### 发布后

- [ ] 保存发布归档、条目清单、版本、构建信息和测试记录。
- [ ] 将用户报告绑定到实际包版本和游戏版本。
- [ ] 对任何热修递增版本并重新执行完整打包门禁。
- [ ] 定期移除废弃的构建输入和未引用资产，保持下一次 staging 可审计。

## 十、最终提问

1. 这个 `.rwmod` 是否真的可作为 ZIP 读取，且含有一个明确的模组根？
2. 最终包中的 manifest、版本、路径和资源是否与源树及发布记录一致？
3. 是否只从允许列表构建，而不是将开发目录和内部材料一并压缩？
4. 图片、声音、locale、TMX、TSX、位图、预览和音乐的直接与间接依赖是否全在归档中？
5. 是否在干净位置、目标游戏版本中加载了最终包，而不只是测试源目录？
6. 本次改动对应的回归范围是否覆盖所有受影响用户路径？
7. 是否存在未经证实的“模组依赖”“加载顺序”或“全部版本兼容”宣称？若有，必须删除或改为准确限制。
8. manifest、归档名、发布说明和游戏显示的 semver 风格版本是否相同？
9. 是否明确记录了静态审计无法证明的运行时风险？
10. 若用户报告失败，团队能否用包版本、游戏版本、归档清单和最小步骤可靠复现？

一个可发布的模组包不是“压缩成功的文件夹”，而是经过根结构、内容边界、引用完整性、引擎安装和用户路径回归共同证明的交付物。只要这条链保持可重复，后续单位、地图、语言或素材变更都可以在不牺牲可靠性的前提下持续发布。

## 十一、候选包可追溯性与可重复发布

### 1. 从源变更到候选归档的链条

发布审核需要能够逆向回答：这个归档中的某个文件来自哪里、为什么进入包、由哪个变更引入、在哪些版本和场景测试过。没有这条链，包体错误、用户反馈和热修都会变成猜测。

| 链条环节 | 应记录 | 用途 |
|---|---|---|
| 变更集 | 文件列表、逻辑 ID、资源 ID、地图依赖变化 | 判断影响面与回归范围 |
| staging 清单 | 允许的运行时条目和排除的开发项 | 证明没有随手压缩整个工作区 |
| 归档清单 | ZIP 条目、根结构、UTF-8 名称与大小 | 定位漏包、嵌套和乱码 |
| manifest 身份 | 名称、版本、兼容范围 | 将游戏内包与发布记录对应 |
| 测试记录 | 游戏版本、平台、用例、结果和未覆盖项 | 区分已证实与假设 |
| 发布渠道 | 上传的归档名、时间、哈希或构建号 | 处理用户安装错包和回滚 |

可追溯并不要求引入沉重的构建服务。一个可重复的本地脚本、稳定的 staging 规则、归档清单和简洁测试记录已足够显著降低风险。最重要的是同一输入在明确步骤下不依赖作者机器的隐藏目录。

### 2. 干净环境的定义

“干净安装”不是只关闭编辑器后再点一次运行。它至少意味着目标测试不再从开发树、旧构建、未打包素材或另一个同名模组意外读取内容。可采用以下任一实际可行策略：

- 将候选 `.rwmod` 复制到单独测试位置，临时移走或重命名源目录；
- 使用独立游戏配置/模组目录，只启用候选包；
- 在另一台设备或虚拟环境中安装归档；
- 对地图和资源测试，确认 ZIP 内条目而不是外部路径满足引用；
- 在候选包升级前删除旧同名候选，确认游戏内显示的版本匹配 manifest。

| 假阳性来源 | 如何排除 |
|---|---|
| 源目录仍在扫描路径 | 暂时隔离源目录或使用独立模组目录 |
| 同名旧 `.rwmod` | 只保留一个候选，并核对 manifest 版本 |
| 核心资源偶然同名 | 对模组自有资源使用唯一根内路径和归档检查 |
| 编辑器缓存 | 完整重启/重新加载，记录载入步骤 |
| 本机已装 TSX/图片 | 在隔离环境或只含归档的环境测试 |
| 旧 locale 键仍可回退 | 在独立包中测试默认与目标语言 |

干净环境可将“开发者说能用”转化为“交付物可独立运行”。对于发布阻断问题，优先相信干净环境失败，而不是在源树里寻找解释。

### 3. 内容指纹与差异审阅

候选包之间可以保存条目清单、大小和哈希，帮助识别不应该变化的资源。哈希并不替代引擎测试，但能回答“本次热修是否意外替换了地图”“上传的包是否真是通过测试的候选”。

| 比较对象 | 预期 | 异常信号 |
|---|---|---|
| manifest | 版本、描述和兼容范围按计划变化 | 文件名变了但 manifest 未变 |
| 单位配置 | 仅计划内单位或模板变化 | 大量无关单位被重新导出 |
| 资源文件 | 新增/替换资源符合变更表 | 出现 `copy (1)` 或废弃图片 |
| 地图链 | TMX、TSX、位图、预览同步变化 | TMX 改了但缩略图/TSX 仍为旧版本 |
| locale | 新键与各语言值同步 | 只更新中文或留下内部键 |
| 归档根 | 保持一个预期根 | 新增多层包装或嵌套 ZIP |

差异审阅尤其适用于热修：如果修复的是一个 `canBuild` ID，却发现归档中多了数百张未知图片，应停止发布并检查 staging 规则，而不是把它当作正常构建噪声。

### 4. 发布前删除测试包与自我嵌套

构建输出若放在模组源根或 staging 所扫描的目录，很容易被下一次构建再次包含，形成 `.rwmod` 内嵌 `.rwmod` 或多个旧候选。它既浪费体积，又可能让用户误以为内部包是可安装内容。构建输出应位于源根外或明确排除的发布目录，且构建完成后检查归档中没有以下项目：

- 任何 `.rwmod`、`.zip`、`.7z` 等构建产物；
- 旧发布版本或临时导出；
- 编辑器自动备份、日志和屏幕截图；
- node/npm 等依赖目录；
- 版本控制目录、私钥、令牌、环境文件或内部工具；
- 任何来自 `W:\mao\tx\模组加载器` 的文件。

不要依赖“用户不会打开内部目录”作为理由。发布包本身是分发边界，包含即意味着可能被读取、复制或误用。

### 4.1 桌面应用发行包与用户模组归档是两层边界

本工作区同时会产生两类 ZIP 相关产物，不能混用它们的规则：

| 产物 | 发行输入 | 外部研究语料的规则 |
| --- | --- | --- |
| `ohmytx` Electron 桌面应用 | `electron-builder` 的显式应用文件白名单 | 绝不携带 `W:\mao\tx\AbyssStars深渊星辰0.7.10`、`W:\mao\tx\ASEU深渊星辰-深渊扩展DLCX`、`W:\mao\tx\模组加载器`、`W:\mao\tx\模组实例\**` 或 `特殊\**` |
| 用户主动生成的 `.rwmod` | 用户当前选择的项目根与该项目的 staging 规则 | 这是独立的用户工作流；本 skill 不通过名称拒绝项目根，但仍要求发布者从干净 staging 根构建 |

因此，不要因为“应用没有携带样本”就声称用户主动选择的项目根不会被模组打包器处理；也不要因为应用有“打包模组”功能，就把外部参考语料误当作 Electron 应用资源。两层验证分别做：桌面应用检查 `package.json` 的 `files`、`extraResources`、`extraFiles` 与最终 ASAR；模组发布检查当前项目的 staging 与最终 `.rwmod` 条目。

桌面应用的发布门禁应拒绝将外部研究来源复制或映射到 `public/`、`dist/`、`dist-electron/`、`extraResources` 或 `extraFiles`。`模组实例\特殊` 只是父语料的镜像子集，也同样受此规则约束。发布记录应保存对最终 ASAR/便携包的条目扫描结果，但不保存或分发任何第三方 archive 内容。

### 5. 归档可移植性试验

在不同工具和平台上，路径分隔、大小写、UTF-8 名称和压缩方法可能产生差异。发布前至少做一次可移植性试验：用独立工具列出 ZIP，用目标游戏读取，用操作系统正常解压检查条目名，并在可能时在第二环境重复加载。

| 检查点 | 失败表现 | 修正方向 |
|---|---|---|
| UTF-8 条目名 | 中文文件或地图名乱码/找不到 | 更换支持 UTF-8 的归档工具，减少非 ASCII 内部名 |
| 路径分隔符 | 资源在 ZIP 中看似存在却无法解析 | 统一归档内 `/`，重建相对路径 |
| 大小写 | Windows 通过、其它环境找不到 | 统一小写并修所有引用 |
| 空目录依赖 | 本机可扫描、ZIP 内没有内容 | 不依赖空目录作为配置语义 |
| 绝对路径残留 | 仅作者机器可加载 | 修为根内相对路径 |
| 压缩损坏 | 包可见但游戏拒绝或读取中断 | 独立完整性测试后重建 |

这类试验不等于承诺支持所有操作系统；它确保发行物至少不会因可避免的归档歧义而只在作者机器工作。

### 6. 发布说明的工程最低内容

发布说明不是营销文案，也不是把所有内部测试日志粘进去。它应使玩家和维护者能确定安装对象、变化、兼容范围与已知限制。

| 字段 | 说明 |
|---|---|
| 名称与版本 | 与 manifest 完全一致 |
| 文件名 | 用户可找到的候选归档名 |
| 目标版本 | 实测 Rusted Warfare 版本，未测范围不得伪装支持 |
| 变化 | 面向玩家的新增、修复与移除；不公开内部敏感路径 |
| 安装 | 明确这是 `.rwmod`，不声称不存在的依赖/加载排序功能 |
| 地图/音乐 | 是否包含以及必要的用户可见说明 |
| 已知限制 | 未测版本、多人、性能或翻译范围 |
| 反馈信息 | 报告需附带模组版本、游戏版本、复现步骤和错误文本 |

不要把内部证据路径、不可公开目录或反编译细节写入公开发布说明。面向用户的准确限制比夸大“全版本兼容”更能减少无效反馈。

### 7. 回滚决策矩阵

回滚不是失败，它是保护已安装用户和维护团队的一种发布操作。应预先定义哪些问题立即停止分发，哪些可在下一常规版本修复。

| 问题 | 建议动作 | 原因 |
|---|---|---|
| 模组整体无法识别/加载 | 立即撤回或替换为新版本 | 用户完全无法使用 |
| 地图缺 TSX/关键位图 | 立即撤回地图包或发布修复 | 关键内容不可部署 |
| `canBuild` 断裂导致核心单位不可生产 | 紧急热修 | 玩法主路径中断 |
| 严重无界生成/性能崩坏 | 立即停止分发 | 会影响整局和设备稳定性 |
| 单一语言有错字但可读 | 记录并排期修复 | 不阻断核心玩法 |
| 非关键图标轻微偏移 | 评估影响后常规修复 | 可用性通常不受阻 |
| 未证实旧版兼容 | 修正发布表述并安排测试 | 不能以猜测发布承诺 |

每次回滚或热修都要新版本、新归档和新测试记录。覆盖同名旧文件会破坏可追溯性，也让已经下载的用户无法判断自己持有哪个内容。

### 8. 最终交付证据包

发布完成后，维护侧可保留一个不公开的证据包，内容最小且可审计：归档、版本记录、归档清单、目标版本矩阵、定向回归结果、已知风险和构建步骤。它不应包含受保护反编译、第三方未经许可素材、私密路径或内部不可公开工具。

这个证据包与玩家 `.rwmod` 分离。前者支持维护、复现和审核；后者只包含引擎运行需要的内容。分离二者能同时提高发布安全性和后续问题定位效率。

## 十二、发布覆盖判定与跨版本降级

### 1. 覆盖不是用例数量，而是风险闭环

“运行了二十个测试”没有说明是否覆盖了本次最危险的变化。发布候选应把每个改动映射为受影响的解析层、资源链和玩家路径，再确认至少有一条正例与一条反例。这样既不会因为文件多而机械测试，也不会因一个功能点过于局部而漏掉加载后链接或最终归档。

| 改动类型 | 受影响层 | 正例 | 反例 | 最终包要求 |
|---|---|---|---|---|
| 新增行动 | 解析、LogicBoolean、状态机、UI | 条件满足时正确提交 | 资源不足/连点/重入时不提交 | 从 `.rwmod` 执行动作 |
| 改局部资源 | 声明、写入、读取、存读档 | 边界内增减正确 | 零、上限、越界状态安全 | 最终包读写和恢复 |
| 改全局资源 | 队伍经济、构建、AI | 正确获得和消费 | 多队伍不串资源、不无限累积 | 目标模式下复测 |
| 改图片 | 路径、图集、队色、绘制 | 单位可见且帧正确 | 缺图/错队色/远景不退化 | ZIP 中路径一致 |
| 改声音 | 路径、解码、触发频率 | 单次事件声音正确 | 群集或快速操作不爆发 | 最终包无非预期回退 |
| 改 locale | 键、回退、动态文本 | 目标语言显示正确 | 缺区域/缺键不泄漏内部名 | 独立安装下回退正确 |
| 改 TMX/TSX | 注册、递归资源、对象 | 地图进入且图块正确 | 缺二级资源不被源目录掩盖 | 从归档重开通过 |
| 改模板/替换 | 继承、跨引用、菜单 | 受影响单位保持正确 | 改名/缺目标被加载器阻止 | 全量或影响面回归 |

覆盖判定的输出应是一张“改动 -> 风险 -> 用例 -> 证据”的表，而不是一句“已测试”。若某项没有反例或最终包证据，就标为未闭环，并决定是补测、缩小变更还是不发布。

### 2. 配置解析、模拟验证与真实运行的区别

静态解析或内部模拟器可快速发现文本、路径、符号、引用和部分逻辑问题，但它们不是目标游戏的行为替身。原始加载器行为的结论必须来自目标版本的实际加载；模拟器或审计脚本的结论应明确标为辅助证据。不能把“模拟器接受配置”写成“游戏支持该配置”，也不能把“静态路径检查通过”写成“地图已可部署”。

| 证据来源 | 可以可靠支持的结论 | 不能单独支持的结论 |
|---|---|---|
| 文本/ZIP 审计 | 条目存在、根结构、引用候选、重复名候选 | 引擎会接受字段或资源格式 |
| 自建模拟器 | 已实现规则在模型中的结果、批量结构检查 | 原始加载器的完整语义、多人/渲染/音频行为 |
| 目标游戏加载日志 | 当前版本对字段、类型、符号和加载后引用的实际处理 | 长时间平衡、压力和所有用户设备行为 |
| 目标游戏运行 | 当前场景的 UI、战斗、地图、声音、存读档结果 | 未覆盖版本或未覆盖事件序列 |
| 用户报告 | 某环境下的失败线索 | 根因和所有版本普遍性 |

发布记录可同时保留多种证据，但表述应匹配来源。例如：“归档审计发现全部已知地图依赖；目标游戏 1.15p11 实测通过地图重开；1.14 未测。”这种表述可审计，也不会把工具边界隐藏起来。

### 3. 最小兼容承诺

跨版本支持不应由“同一包在某台设备上没有报错”推断。为每个发布版本写最小兼容承诺：明确支持的引擎版本、已测试功能、降级行为和明确不支持项。1.15p11 的 memory 相关支持需要单独列出；不能从该补丁的成功测试外推到所有 1.15 或 1.14。

| 能力 | 已支持时的表述 | 未确认时的表述 | 降级设计方向 |
|---|---|---|---|
| 基础单位/图片 | “在 X 版本最终包加载通过” | “X 版本未测” | 使用基础字段、保留简化外观 |
| memory 状态 | “在 1.15p11 完成写入/读取/存读档测试” | “不承诺较早版本” | 用资源或标签表达有限状态，或移除该功能 |
| locale 动态值 | “在目标语言矩阵实测” | “其它地区回退未测” | 提供可理解的默认静态文本 |
| 地图外部 TSX | “最终 ZIP 与重开实测” | “旧版本未测” | 合并或简化依赖，或停止宣称支持 |
| 音频文件 | “目标设备解码实测” | “其它设备解码未测” | 使用已验证格式或内建声音 |

降级不是偷偷删掉功能。它应在发布说明或兼容表中说明，且依旧通过其目标版本的完整包回归。对于必须依赖新行为的内容，更诚实的选择是提高最低支持版本，而不是向旧版本提供一个会静默失效的包。

### 4. 发布候选的停止条件

构建和测试应有明确停止条件，避免在错误状态下反复追加修补。以下任一项触发时，暂停候选并回到问题最小化：

- 原始加载器报告新的解析、类型、重复 ID 或加载后引用错误；
- 最终包与源目录的行为不一致；
- 关键地图需要开发目录中的 TSX、位图、预览或音乐才可加载；
- 资源、单位、效果、声音或 action 链出现无法给出上界的累积；
- 已知错误只能通过降低 strict、隐藏警告或把条件改成常量来“修复”；
- 所有权、许可或内部不可公开来源无法确认；
- 兼容声明超过现有证据，且无法在发布前补测。

停止条件保护的是发布质量，不是开发速度。继续叠加修补会让归档清单、错误日志、版本号和回归结果失去一一对应关系。先恢复可解释的最小状态，再重新走 staging、归档审计和目标游戏验证，通常比在脏候选上继续试错更快。

### 5. 发布门禁的简短决策记录

每次候选最终给出一个明确决定，而不是模糊的“看起来可以”：

```text
候选：example-mod-1.4.2.rwmod
决定：发布 / 阻断 / 限制发布
阻断项：无 / 列出首个未关闭项
实测：目标游戏版本、源目录与最终包、关键地图与单位
辅助证据：归档审计、引用扫描、模拟器（若有，明确非引擎证明）
兼容声明：已测范围；未测范围；降级或不支持项
风险：多人/性能/语言/设备等未覆盖项
下一步：发布、补测、最小复现或回滚
```

这种记录让协调方、发布者和未来代理能判断为什么一个候选被放行或阻断，同时保持原始加载器事实与静态/模拟工具结论的区别。
