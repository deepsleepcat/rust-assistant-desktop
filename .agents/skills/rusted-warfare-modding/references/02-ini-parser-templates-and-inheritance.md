# INI 解析、模板与继承

导航：证据等级与版本门槛见 [00-source-authority-and-versioning.md](00-source-authority-and-versioning.md)；模组源根、归档和 `mod-info.txt` 见 [01-mod-discovery-rwmod-and-metadata.md](01-mod-discovery-rwmod-and-metadata.md)；区段和字段应如何路由到字段目录见 [03-unit-architecture-and-field-catalog-routing.md](03-unit-architecture-and-field-catalog-routing.md)。执行任务前还应阅读 `../SKILL.md`。

本页描述 `1.14`/`1.15` 自定义单位配置的解析与继承边界。它面向会批量改写 INI、生成模板、修复加载错误、审查第三方补丁或实现静态检查器的编码代理。不要把 INI 当作“键值文本只要格式像就行”：引擎会解析、展开、类型读取、建立对象引用、消费键、检查重复，并在最后检查未使用键。一个文件能被读入不代表它已成为有效单位。

本文的示例均为自写、最小化的示意片段，故意不构成完整可运行单位，也不复制任何内部或第三方配置。字段的确切有效性、拼写、默认值和版本限制仍须回到字段目录再对原始引擎实现核对。

## 1. 三种不同的“读取”

很多错误源于把以下三个动作混为一谈：

| 动作 | 发生内容 | 成功意味着什么 | 不意味着什么 |
|---|---|---|---|
| 文本解析 | 行、节、键值、多行文本进入 INI 数据结构 | 基本语法可被读入 | 键名合法、值类型正确、资源存在 |
| 字段读取 | 某个单位加载阶段按类型读取一个键 | 该字段的值能转换为预期类型 | 其他键已被读取、跨字段约束成立 |
| 键消费审计 | 引擎检查所有应被使用的键是否已消费 | 未使用键规则通过 | 运行期行为、图像显示、联机一致性正常 |

例如，`speed: fast` 可能在文本层完全无问题；当相应字段按浮点数读取时才失败。另一个字段即使拼写合法，也可能从未被任何加载阶段读取，最终在未使用键审计中报错。代理不能只用“没有括号错误”判断 INI 正常。

### 解析生命周期

```text
原始字节
  -> 去除起始 BOM
  -> 按行与多行状态识别
  -> 注释、节、分隔符和键值解析
  -> 记录重复键及书写位置
  -> 变量与引用相关的预处理/读取
  -> 文件级 copyFrom 合并
  -> 自动目录模板合并
  -> 节级 @copyFromSection 合并
  -> 按区段读取类型化字段并建立对象
  -> 重复键与特定命名空间校验
  -> 未消费键审计
  -> 运行期构造与行为
```

不同版本或字段加载顺序可能使具体内部调用不同，但诊断必须保留这类阶段区分。报错中若有节名、键名、源路径或“while loading”上下文，应把它们保留到问题单里，不能只摘取最后一句自然语言。

## 2. 文件编码、行和节的基础语义

### UTF-8 BOM

INI 读取会剥离文件开头的 BOM。也就是说，一个带 BOM 的 UTF-8 文件不应因第一个节名前多出不可见字符而直接失败。这个兼容行为不是让代理随意混用编码的许可：

- 新文件统一保存为 UTF-8；是否带 BOM 要与项目现有工具链一致。
- BOM 只应位于文件开头；中间插入不可见字符仍会污染键或值。
- 如果首个 `[core]` 看似正确却无法匹配，检查不可见字符、编辑器编码和实际打包条目，而不是立刻改字段名称。
- 不要用 BOM 来解决压缩包文件名的编码问题；文件内容编码与 ZIP 条目名编码是不同层次。

### 节头

节以方括号命名，例如 `[core]`、`[graphics]`、`[turret_main]`、`[template_common]`。节名不是纯注释：加载器会按精确前缀和命名约定路由到不同对象。以下两类错误尤其常见：

| 表面写法 | 真实问题 | 排查路径 |
|---|---|---|
| `[turretMain]` 代替 `[turret_main]` | 前缀或引用约定不一致，可能不会进入炮塔解析 | 查字段目录的节名模式，再查引擎枚举前缀 |
| `[template-weapon]` | 不具备 `template_` 前缀的豁免语义 | 改为正确模板命名，或作为普通节处理 |
| `[core ]` | 空格是否成为节名的一部分取决于解析规范和写入形式 | 不依赖修剪猜测，统一无空格 |
| 同一语义拆成两个略有不同的节 | 后续引用只会命中其中一节 | 合并并显式检查引用 |

对新增节，先回答“谁会列出它、谁会读取它、它是否属于可重复前缀集合”。如果答案只是“我觉得格式像”，不要写入生产文件。

### 键值分隔符

解析器支持两种键值分隔符：冒号 `:` 与等号 `=`。以下写法在文本层均属于同类意图：

```ini
name: harbor_probe
maxHp=180
```

工程上建议在一个模组中保持一种主风格，通常使用冒号，因为字段目录和常见单位写法以冒号呈现。统一风格的好处是减少自动编辑器误把条件表达式、资源值或文本内容切错。不要写一行多个键；每个键单独一行，便于重复键定位和版本控制审阅。

分隔符支持不代表值内的任意 `:` 或 `=` 都无需留意。复杂值可能自身包含小语法、资源对、逻辑表达式或文本。代理在做机械替换时应只修改行首键与第一个有效分隔符，绝不可对全行做盲目替换。

### 空白、空行与行尾

空行可用于分组，但不会建立作用域。视觉缩进不改变 INI 层级。为了避免资源路径、标签和逻辑表达式被意外改变，建议：

- 键名左侧不缩进；节头单独置行。
- 值的前后空白只在已知读取器会修剪时才可忽略；不要让重要标识依赖空白容忍。
- 不要把同一键分成多行，除非明确使用三引号多行规则。
- 不要用行尾注释的存在与否来推断值是否被读取；先按注释规则处理。

## 3. 注释与三引号多行文本

### `#` 注释的边界

`#` 注释在非多行文本状态下生效。它适合写简短理由、版本约束或待验证标记：

```ini
minVersion: 1.15p11 # 内存数组的最低已知门槛
```

但不能把它当作通用字符串转义规则。若值确实需要包含 `#`，应先确认它处在三引号多行文本或字段特有的允许语境；不要仅凭某个编辑器的语法高亮判断。对于自动格式化器，以下原则最稳妥：解析器状态不在多行文本中时，`#` 后的内容不可作为业务值；在多行文本内，应保留其文本含义。

### 三引号多行文本

解析器支持三引号的多行内容。多行文本适合单位描述、较长提示或需要保留多行结构的字符串，而不适合隐藏复杂配置。示意：

```ini
[core]
displayDescription: """
第一段说明可以包含 # 号。
第二段仍是同一个值。
"""
```

使用多行文本时要注意：

1. 进入和退出三引号状态要成对。缺少结束符会吞掉后续配置并把错误定位得很远。
2. `#` 在多行状态下不应按普通行尾注释理解；写文案时不要意外删掉带井号的内容。
3. 三引号内的换行属于值的一部分。不要同时依赖描述字段的字面 `\n` 替换和三引号，除非明确知道该字段在该阶段如何消费。
4. 多行文本只解决文本承载，不让其中的字段名、路径或逻辑自动生效。
5. 模板中放入长多行描述会扩大所有子单位的继承表面，除非确实是统一文案，否则更适合由子文件显式定义。

### 文本字段的最小化原则

对面向玩家的文本使用自写内容，避免把调试日志、内部路径、受限材料说明或第三方文本带进发布包。对面向代理的注释使用短、可行动的理由，例如：

```ini
# 仅 1.15p11+：该单位动作使用内存数组
```

不要在配置里写“参考某第三方模组第几行”；这种引用不利于发布，也无法在其他工作区稳定复现。溯源信息应放在内部任务记录，且只能写行为摘要与允许共享的路径线索。

## 4. 重复键：最后值、诊断记录与致命命名空间

在一般映射语义中，同一节的重复键以最后一次出现的值为准。这不等于重复键是安全写法。解析器保留重复信息，后续加载与严格级别会将部分重复升级为错误；某些命名空间即使不依赖一般宽容规则也会被强制拒绝。

### 先区分“最终值”与“文件是否可接受”

```ini
[core]
maxHp: 100
maxHp: 180
```

若只看映射，最终 `maxHp` 是 `180`。但代理不能据此保留重复，因为：

- 前一行可能是遗留值，隐藏了编辑误操作。
- 不同读取阶段可能在重复检测前后记录不同上下文。
- `strictLevel: 1` 会让一些本可被警告的情况升级。
- `hiddenAction_` 和 `canBuild_` 的重复会触发更强的专门检查。
- 模板合并与源文件重复不是同一件事；前者是“只补缺失”，后者是同一输入层重复。

正确实践是：一个节中一个键只写一次；如需覆盖，应通过子文件、明确模板层或字段特定机制表达，而不是在同一节末尾偷改。

### 特别致命的重复：`hiddenAction_` 与 `canBuild_`

加载器会专门检查以 `hiddenAction_` 或 `canBuild_` 开头的重复定义。这类重复不是“最后一个覆盖第一个”的可接受技巧，而是致命问题。原因在于它们同时承担命名、可引用对象和列表构造的角色；悄悄覆盖会使动作、建造项或后续引用指向不确定目标。

| 情况 | 不要做 | 应做 |
|---|---|---|
| 想调整隐藏动作 | 在同一文件再写一个同名 `[hiddenAction_x]` | 找到原定义并原地修改，或给新动作唯一名称 |
| 想覆盖模板建造项 | 复制一个同名 `[canBuild_x]` | 在子层明确修改可覆盖键，或重新设计条目名称/模板边界 |
| 自动生成配置 | 无条件拼接所有片段 | 在生成前建立节名唯一性索引 |
| 合并外来补丁 | 只按文本拼接 | 先识别 `hiddenAction_`、`canBuild_` 前缀并冲突报告 |

注意“区段名称重复”“同一节内键重复”“两个模板导入同一键”是三种不同冲突。它们的表现和修复不一样。静态审计工具至少应分别报告：源文件重复、模板继承后碰撞、节级复制后的缺失/冲突，以及前缀命名空间的重复。

### `strictLevel`

`[core] strictLevel` 是加载严格性的一部分，其允许范围应按目标版本核对；已知有效的严格等级范围包含 `0` 与 `1`，超出边界会被拒绝。`strictLevel: 1` 会把某些宽松场景提升为更严格的错误，例如某些格式、标签或重复相关问题。它不是“发布时随手打开的质量开关”。

使用建议：

| 阶段 | 建议 | 理由 |
|---|---|---|
| 新建最小单位 | 尽早在严格模式验证 | 早暴露拼写、空白和重复问题 |
| 维护旧包 | 先不盲改，建立错误清单 | 直接提高严格度可能一次暴露大量历史债务 |
| 自动迁移 | 迁移前后分别运行审计 | 区分原有问题与迁移引入问题 |
| 发布前 | 用目标版本进行严格验证 | 不让宽松开发环境掩盖交付错误 |

不要把 `strictLevel: 0` 当成规避错误的长期解决方案。它只能改变部分诊断强度，不能让不存在的字段、错误路径、无效引用或版本不足变为有效功能。

## 5. 类型化读取与“未使用键”审计

INI 解析器支持按预期类型读取值，例如文本、整数、浮点、布尔、时间、资源、标签、逻辑表达式、颜色、文件引用或对象引用。类型转换发生在消费字段的加载器中，而不是仅凭文本存在就完成。代理应该把每个字段的“类型”和“消费者”同时查清。

### 常见值类别

| 值类别 | 典型风险 | 审计重点 |
|---|---|---|
| 布尔 | 拼写、大小写、把条件表达式当布尔 | 查字段是否接受 LogicBoolean 而非 bool |
| 整数/浮点 | 单位、范围、负值、隐式转换 | 查默认值和边界；不要把显示单位当引擎单位 |
| 字符串 | 空白、转义、可本地化文本 | 查是否允许多行、是否会替换 `\n` |
| 路径 | 相对根、压缩包、大小写、扩展名 | 在目录版和 `.rwmod` 版各验证 |
| 标签/列表 | 分隔符、空格、重复项 | 查是否允许空项、是否在严格级别报错 |
| 资源表达式 | 冒号、逗号、局部/全局资源范围 | 不要用通用字符串替换破坏内部语法 |
| LogicBoolean | 引用对象、版本能力、求值时机 | 拆分复杂条件进行最小复现 |
| 对象引用 | 声明顺序、名称唯一性、跨节依赖 | 查引用的是单位、炮塔、投射物还是动作 |

### 键消费的含义

加载器在读取已知字段时会标记键已被消费。完成单位构造后，未被消费的普通键会造成错误或诊断。这是防止“拼错字段却静默失效”的重要机制。不要通过给未识别键塞 `IGNORE` 来掩盖拼写错误；`IGNORE` 应只用于已确认需要保留但由当前阶段故意不消费的兼容或生成场景，而且必须留下注释与证据。

未使用键检查有明确豁免：

- `template_` 前缀的模板区段不按普通运行区段要求全部消费。
- 以 `@define`、`@global` 开头的定义性键可作为变量机制存在。
- 值为 `IGNORE` 的键可以绕过普通未使用键错误。

豁免不是无限宽容：模板被复制后进入真实区段的字段仍须在目标用途上可消费；变量名称、引用语法和最终展开值仍可能失败；`IGNORE` 不能让被其他专门检查捕获的重复动作或无效引用安全化。

### 未使用键诊断流程

1. 记录报错的完整节名、键名和来源文件。
2. 在字段目录中查精确拼写、前缀和所属区段。
3. 在原始引擎材料中确认目标版本是否读取该键，且是否处于你使用的区段。
4. 检查键是否因模板合并、变量展开或区段复制进入了意外位置。
5. 检查是不是把另一个区段的字段写进了当前区段。
6. 检查是否为版本限定字段而 `minVersion` 未满足。
7. 只有证实该键是应保留的兼容占位时，才考虑 `IGNORE`；否则修正拼写、位置或设计。

不要在第一步就删除报错键。删除有时能让加载继续，但也可能移除真正所需功能，导致更晚、更难诊断的行为偏差。

## 6. 三类复用机制不可混淆

Rusted Warfare 单位配置中至少有三种常被称作“模板”的机制，它们的作用域和优先级不同：

| 机制 | 入口 | 作用域 | 主要用途 | 风险 |
|---|---|---|---|---|
| 文件级 `copyFrom` | `[core] copyFrom` | 整个 INI 文件跨文件补缺失键 | 复用基础单位或共享文件 | 路径、链深、父项顺序 |
| 节级 `@copyFromSection` | 任意节的控制键 | 当前 INI 内指定节之间补键 | 复用炮塔、动作、投射物或模板节 | 节名、递归、跳过标记 |
| `all-units.template` | 单位目录 walker 发现的祖先目录文件 | 该目录下所有后代单位的自动公共层 | 目录级默认值和公共设置 | 隐式作用域、根扫描误解、近层覆盖 |

它们都遵循“本地已有键不被父来源覆盖”的核心方向，但触发时机、来源位置、错误上下文和可维护性不同。不要把一个文件级父路径写进 `@copyFromSection`，也不要期待 `.template` 文件仅因扩展名存在就自动变成独立单位。

## 7. 文件级 `copyFrom`

### 基本行为

在 `[core]` 使用 `copyFrom` 指定逗号分隔的父文件。加载器会对列表进行反向应用：从右到左递归读取父文件，并把父文件中子文件尚未拥有的键填入子文件。因此本地子文件永远优先；多个父文件之间，**最右侧父文件优先于其左侧父文件**。

自写示意：

```ini
[core]
copyFrom: chassis.template, weapon-defaults.template
name: harbor_probe
```

这表示先以 `weapon-defaults.template` 为较高优先父层填充缺失，再以 `chassis.template` 补仍缺失的键；当前文件中 `name` 则不被任何父项替换。不要根据左到右阅读习惯反过来理解优先级。

### 优先级表

| 来源 | 相对优先级 | 当同一键已存在时 |
|---|---|---|
| 当前子文件显式键 | 最高 | 保留当前值 |
| `copyFrom` 列表最右父文件 | 高于它左边的父文件 | 先填入缺失键 |
| 列表中间父文件 | 依位置而定 | 只填仍缺失键 |
| 列表最左父文件 | 最低 | 只能填最后剩下的缺口 |
| 更深层祖父 | 先在其直接子父内完成递归，再参与 | 不覆盖更近层已有值 |

若希望 A 的默认值被 B 覆盖，应写 `copyFrom: A, B`，而不是 `B, A`。不过，两个父模板写相同键通常是设计信号：它让优先级依赖列表顺序，维护者很容易误改。更可维护的做法是让每个父模板负责明确的字段域，例如底盘、视觉、武器，或者在子文件显式写出冲突字段。

### 路径规则

`copyFrom` 的目标路径有三类解析方式：

| 写法 | 相对基准 | 用途 | 注意 |
|---|---|---|---|
| `common/base.template` | 当前加载文件所在目录 | 同目录或子目录的局部复用 | 不依赖外层项目结构 |
| `ROOT:templates/base.template` | 模组逻辑源根 | 跨单位目录的模组内共享模板 | 根是发现后的源根，不一定是宿主安装对象 |
| `CORE:...` | 游戏核心文件位置 | 只在确有内置兼容需求时使用 | 依赖游戏版本和内置资源，需格外审计 |

任何包含 `..` 的 `copyFrom` 路径都不支持。不要尝试用 `../` 绕过局部路径限制，也不要让自动化重写器生成它。正确方案是：将共享模板移动到可由 `ROOT:` 访问的模组根内，或调整目录结构，使局部相对路径保持向下或同级。

`CORE:` 是到游戏文件的语义入口，不是“任意电脑的核心目录”。只有在目标版本已经证实某个核心模板存在且允许引用时才使用；它会把模组兼容性绑定到游戏资源布局。新设计优先将可控的公共模板放在自己的 `ROOT:` 路径下。

### 深度与循环

文件级继承最大嵌套为 `10` 层。超过上限会被当作疑似循环或过深链而失败。以下情况都应在静态审计中阻止：

```text
A -> A
A -> B -> A
A -> B -> C -> ... 超过十层
不同路径字符串实际指向同一逻辑文件
```

不要把“最多十层”当成可以设计九层继承树的许可。每增加一层，排错成本、版本差异和未使用键来源都会显著增加。建议把常规 `copyFrom` 深度控制在二至三层：一个领域模板、一个可选变体模板、一个具体单位。超过三层时，应画出键来源图并逐项说明不可折叠的理由。

### 文件级继承的审计步骤

1. 从每个单位的 `[core] copyFrom` 建立有向图。
2. 标注每条边使用局部、`ROOT:` 还是 `CORE:` 路径。
3. 拒绝任何 `..`、无法解析的目标、循环和超过十层的路径。
4. 将逗号列表按实际右到左顺序展开，而不是按原文本顺序展示。
5. 对每个高风险键输出最终来源：子文件、右父、中父、左父或更深父。
6. 对来自 `CORE:` 的字段加版本证据，不能因本机存在就假定所有用户都有。
7. 复核合并后的 `hiddenAction_`、`canBuild_` 命名空间，避免隐含重复。
8. 在目标游戏版本重新加载，静态展开结果不替代引擎验证。

## 8. 节级 `@copyFromSection`

### 用途与方向

`@copyFromSection` 在当前 INI 的一个节内列出要复制的目标节。它用于复用节内的默认字段，例如多个炮塔、多个投射物或多个动作共享一组自写参数。和文件级继承一样，它是“只补当前节缺失键”的合并，而非把父节完整覆盖到子节。

自写示意：

```ini
[template_scanner]
turnSpeed: 2.2
canShoot: false

[turret_sensor]
@copyFromSection: template_scanner
x: 0
```

此例的意图是让 `turret_sensor` 继承尚未声明的转动和射击默认值，再自行声明位置。它不是对字段目录的可运行保证；具体哪些键允许出现在哪个节，必须核对目标版本。

### 多目标、递归与优先级

`@copyFromSection` 可引用逗号分隔的节名，处理顺序同样应按实际反向应用理解；每个目标节还能继续引用其他节，最大递归深度为 `10`。当前节显式键优先，较晚在原列表右侧的目标节优先于其左侧目标节。若目标节不存在可复制键，会产生明确错误，而不是静默空操作。

推荐结构：

```ini
[template_motion]
turnSpeed: 1.4

[template_short_range]
@copyFromSection: template_motion
limitingRange: 90

[turret_guard]
@copyFromSection: template_motion, template_short_range
x: 3
```

这里应先展开右侧 `template_short_range`，它本身先取得 `template_motion` 的缺失项；随后左侧 `template_motion` 只能补仍然缺失的项目。不要把这种层级写成难以看懂的菱形图。若两个模板都定义关键字段，应在最终节明确覆盖或拆分模板职责。

### `@copyFrom_skipThisSection`

当前节可用 `@copyFrom_skipThisSection: true` 阻止从文件级父来源复制该节。它是精确的节边界工具，而不是删除父文件或禁用一切继承。适用例子包括：子单位保留父文件的大部分默认值，但必须完全自定义某个动作节或炮塔节。使用前应确认：

- 该节的必要字段将在当前文件或其他明确机制中补齐。
- 跳过后不会留下对父节对象的悬空引用。
- 这个控制键本身会被加载流程识别，不应因为未使用键审计而误判。
- 注释说明为什么必须隔离，避免后续维护者删掉它后意外重新引入父字段。

不要把 `@copyFrom_skipThisSection` 用作处理重复动作或建造项的绕过工具。若目标命名空间本身重复，仍要消除重复定义。

### 节级继承的失败模式

| 报错或症状 | 常见原因 | 修复方向 |
|---|---|---|
| 找不到目标节 | 节名拼写、前缀、变量展开或顺序假设错误 | 检查实际节列表与精确名称 |
| 目标节没有可复制键 | 引用了空节、纯注释节或错误节 | 删除无效引用或补上真正模板键 |
| 超过十层 | 模板互相引用或层次过深 | 压平链路，保留少数领域层 |
| 子字段未按预期覆盖 | 把父/子优先级理解反了 | 显式写子字段并检查逆序应用 |
| 未使用键错误 | 模板键最终进入不被消费者读取的节 | 移动到正确节或改为有效字段 |
| 特定动作重复 | 多层导入了相同 `hiddenAction_` 名称 | 重新命名或消除一个来源 |

## 9. 目录级 `all-units.template`

### 它是什么

`all-units.template` 是目录 walker 识别的特殊文件名。当 walker 在某个目录上下文遇到它，该目录下的后代单位会自动合并这份模板。它解决“一个子树内多数单位需要同一基础默认值”的问题，例如统一版本约束、共同视觉开关或公共行为基线。

它不是普通 `.ini` 单位，也不是“所有 `.template` 自动被当作单位”的例外。实际 `.template` 文件不会仅凭扩展名被发现为独立单位定义；只有被 `copyFrom` 引用、作为 `all-units.template` 被目录机制采用，或被其他明确加载逻辑读取时才有作用。

### 祖先与近层覆盖

若一个单位位于多个含 `all-units.template` 的祖先目录之下，祖先模板会形成由远到近的默认层，较近的下层模板对同键具有更接近单位的优先级，最终单位显式键仍优先。可用下面的概念图理解：

```text
units/
  all-units.template          <- 远层公共默认
  aircraft/
    all-units.template        <- 近层飞行单位默认
    scout.ini                 <- 最终具体单位
```

对于 `scout.ini`，应把优先级理解为：具体单位显式键最高；`aircraft/all-units.template` 的同名缺失填充高于 `units/all-units.template`；远层模板只补近层和单位均未声明的项。不要把多层自动模板和文件级 `copyFrom` 的实际调用先后想当然混排。若同一关键键同时出现在自动模板与 `copyFrom` 父文件，必须在目标版本运行验证并记录最终来源；复杂组合应尽量避免。

### 根扫描的细微点

必须谨慎描述“根”：

- 直接对模组单位扫描入口调用的目录，会枚举该扫描根下的直接文件，并按 walker 规则递归其子目录。
- 元数据发现时为了找到 `mod-info.txt` 进行的向下搜索，是确定模组源根的动作，不是一次单位扫描，也不会因为它看过某个目录就自动把其中 `.ini` 作为单位载入。
- `all-units.template` 的自动作用取决于单位 walker 的目录上下文与祖先关系；不要仅因文件在模组源根附近就断言它覆盖所有文件，需按实际扫描入口和目录树验证。
- 普通 `.template` 不是独立单位候选。把一个完整单位写入 `my-unit.template` 并放在目录里，不会因为后缀存在而自动生成单位。

这四句避免了两种相反错误：一是以为根目录永不扫描；二是以为任何被元数据发现碰到的目录都会自动加载单位。真正的载入范围要跟随单位 walker，而不是跟随安装对象或文件管理器视图。

### 何时用、何时不用

| 情况 | 适合 `all-units.template` | 更适合其他机制 |
|---|---|---|
| 一个目录下几十个单位共享明确基础值 | 是，且目录就是有意义的领域边界 | 无 |
| 两个分散目录共用模板 | 否 | `ROOT:` 文件级 `copyFrom` |
| 仅两个炮塔共享参数 | 否 | `@copyFromSection` |
| 只想让一个单位继承 | 否 | 明确 `copyFrom` |
| 希望新文件自动获得规定约束 | 是，但要审计隐式影响 | 同时提供目录说明和测试 |
| 正在修复神秘覆盖 | 暂停新增 | 先画出祖先模板链 |

目录模板的优势是减少重复，缺点是影响隐式。它适合稳定、低变更、高共性的默认项；不适合每个单位都需要阅读才知道来源的武器、价格、行为触发和资源逻辑。高风险玩法字段应宁可显式写在可见父模板或子文件中。

## 10. 单位目录 walker：文件、地图与递归

单位加载器会递归遍历相关目录，处理 `.ini` 与 `.tmx`，并忽略诸如 `desktop.ini` 的系统文件。递归深度上限为 `10`。这与元数据发现的“最多四层、目录条目限制”不是同一个规则，不能相互替代。

### walker 规则摘要

| 项目 | 行为 | 工程含义 |
|---|---|---|
| `.ini` | 作为单位配置候选进入加载流程 | 必须经完整字段解析与审计 |
| `.tmx` | 作为地图候选处理 | 地图发现不证明单位字段正确 |
| `.template` | 不会只因扩展名被单独加载为单位 | 需由继承或特殊模板机制显式消费 |
| `desktop.ini` | 被作为系统文件忽略 | 不要将其误报为无效单位配置 |
| 子目录 | 递归扫描 | 目录结构会影响自动模板作用域 |
| 递归深度 | 最大 `10` | 深层项目树可能截断，需压平 |

文件名大小写、文件系统和归档虚拟目录仍可能影响实际列举。统一小写扩展名和简短目录名，不要依赖某平台把 `.INI`、`.ini`、多余空格或隐藏扩展名自动纠正。

### 递归深度的设计建议

深度上限是保护机制，不是鼓励把资源树堆到第十层。单位文件推荐在源根下二至四层内，例如：

```text
units/
  land/
    scouts/
      harbor_probe.ini
```

相对路径更短，自动模板链更易读，打包后也更容易核查。如果目录层级来自分类需求，应在目录名表达领域，而不要把版本、作者、导出日期、备份和发布渠道全部串进路径。将“归档版”“旧版”“实验版”放在版本控制或发布文件名中，不要嵌入单位扫描树。

## 11. 合并顺序的可视化审计

复杂继承出问题时，不要靠阅读文本猜最终值。建立每个键的来源表。以下是自写示意：

```text
当前文件 scout.ini
  显式：price = 120
  copyFrom：hull.template, sensor.template
  祖先目录：units/all-units.template
  近层目录：units/air/all-units.template
```

审计表应至少包含：

| 键 | 当前文件 | 文件级父列表（实际应用顺序） | 目录模板链 | 最终值来源 | 证据状态 |
|---|---|---|---|---|---|
| `price` | 120 | sensor -> hull | 近层 -> 远层 | 当前文件 | 已证实/待验证 |
| `moveSpeed` | 缺失 | sensor -> hull | 近层 -> 远层 | 需按目标版本运行核对 | 待运行验证 |
| `image` | 缺失 | sensor -> hull | 近层 -> 远层 | 需检查资源路径 | 待运行验证 |

不要把表中的“最终值来源”写成猜测。静态工具可以在已知合并规则内计算一部分结果，但自动目录模板和复杂字段读取的实际顺序仍要用目标游戏复核。只要有跨文件、跨目录和节级机制同时碰撞的高风险键，优先把该键显式下沉到具体单位，换取可读性和确定性。

## 12. 面向生成器与格式化器的要求

编写会自动产生或修改 INI 的代理时，应遵守以下约束：

### 生成前

- 收集现有节名、键名、模板边、文件级父图和目录级模板链。
- 读取字段目录确定候选名称，再按目标版本原始引擎确认关键字段。
- 检查用户指定的版本，避免生成需要 `1.15p11` 的内存数组却保留较低 `minVersion`。
- 明确每个生成值的来源是用户需求、显式默认、模板继承还是推导；没有来源的值不要臆造。

### 生成时

- 每节每键只输出一次；对 `hiddenAction_`、`canBuild_` 执行全局唯一检查。
- 不生成 `..` 型 `copyFrom` 路径。
- 对多父 `copyFrom` 以实际右到左优先级排序，并在生成记录里输出最终顺序。
- 不把任意 `.template` 当成单位文件输出到扫描目录后期待自动加载。
- 使用统一的冒号风格、UTF-8 与小写路径；不要改写值内部的语法分隔符。
- 长说明文字使用经审查的三引号结构，保证终止符存在。

### 生成后

- 解析并列出所有未消费键，不能只检查是否可打开文件。
- 展开或至少报告文件级和节级继承链、最大深度、循环与重复。
- 在目录版重新扫描所有递归 `.ini`、`.tmx`，再在 `.rwmod` 版重复核心测试。
- 区分文本解析失败、类型失败、对象引用失败、重复错误和运行期异常。
- 只在目标版本写出“已验证”；其他版本使用限定语言。

## 13. 典型故障的因果树

### “模板字段没有生效”

```text
字段没有生效
  -> 模板文件没有被任何机制引用？
       -> 普通 .template 仅放在目录中：不会自动载入
       -> 修复：使用 copyFrom、@copyFromSection 或正确命名的 all-units.template
  -> copyFrom 路径解析到了错误根？
       -> 检查本地相对、ROOT、CORE 与禁止的 ..
  -> 子文件已有同键？
       -> 子值优先，父值不会覆盖
  -> 多父顺序理解错误？
       -> 最右父先应用，优先级更高
  -> 自动目录模板作用域不如预期？
       -> 检查 walker 入口和祖先模板链
  -> 键其实未被目标区段消费？
       -> 查字段路由与未使用键错误
```

### “修改后出现重复动作或建造项”

```text
重复错误
  -> 是否同一源文件重复定义？
       -> 删除遗留行，不要依赖最后值
  -> 是否文件级模板与子文件都定义同名 hiddenAction_ / canBuild_？
       -> 重新命名、隔离或让只有一个层负责定义
  -> 是否自动生成器重复拼接？
       -> 对节名建立唯一集合并在生成前失败
  -> 是否节级复制把控制键或同名定义带入意外节？
       -> 审查 copyFromSection 图和 skip 标记
```

### “未使用键错误”

```text
未使用键
  -> 键是否拼错或写在错误节？
  -> 字段目录是否只列候选、未被目标版本读取？
  -> 模板是否把它带入不消费的节？
  -> 是否应为 template_、@define、@global 或已证实的 IGNORE？
  -> 是否混淆了元数据键与单位键？
  -> 是否需要提高版本，或根本不存在该版本能力？
```

## 14. 继承设计的可维护性标准

一个可维护的单位不只是“最终值正确”，还应让未来代理能在不启动游戏的情况下理解大部分来源。建议用以下指标自检：

| 指标 | 健康范围 | 红旗 |
|---|---|---|
| 文件级继承深度 | 0 到 3 层 | 接近 10 层或出现环 |
| 多父模板数量 | 0 到 2 个且职责分明 | 三个以上互相重叠 |
| 自动目录模板层数 | 0 到 2 层 | 目录结构变化就改变关键玩法 |
| 同键多来源 | 高风险字段最多一个明确父来源 | 依赖右到左顺序决定价格、武器或资源 |
| 模板命名 | 领域名清晰，如 `template_airframe` | `template_new2_final` 之类时间序列名 |
| `IGNORE` 数量 | 接近零并有理由 | 用于压住大量未知键 |
| 严格模式 | 发布前可通过 | 只能靠宽松模式加载 |

当指标变红时，优先压平配置：把共同、稳定、低风险项放入一个模板；把单位身份、关键数值和独特行为写入子文件；把少量节内复用放入命名清楚的模板节；不要追求“零重复”到牺牲可验证性。

## 15. 最终审计清单

### 文本层

- [ ] 文件以目标工具链一致的 UTF-8 保存，开头 BOM 已作为兼容因素而非设计依赖处理。
- [ ] 每个节头、键名和路径都没有不可见字符、无意义空白或隐藏扩展名。
- [ ] 键值只用一个明确分隔符，复杂值未被机械替换破坏。
- [ ] `#` 注释没有被误当成普通值的一部分；多行文本内部内容得到保留。
- [ ] 每个三引号文本都有匹配终止符，且没有吞掉后续节。

### 结构层

- [ ] 一个节内不存在无理由的重复键。
- [ ] `hiddenAction_` 与 `canBuild_` 的定义没有重复，生成器也做了唯一性检查。
- [ ] `strictLevel` 的值在目标版本允许范围内，严格错误已被逐项解决而非回避。
- [ ] 变量、模板和 `IGNORE` 豁免都附有明确用途，未用作拼写错误的遮罩。
- [ ] 每个未消费键都有修复、删除或已证实豁免的决定。
