# 行动、逻辑、资源、效果与状态

> 入口：先阅读 [SKILL.md](../SKILL.md)。本章与 [03-单位架构与字段目录路由](03-unit-architecture-and-field-catalog-routing.md)、[05-素材、音频、本地化与地图](05-assets-audio-localization-and-maps.md)、[06-交叉引用、验证与调试](06-cross-references-validation-and-debugging.md) 配套使用。
>
> **来源与权威性。** 本章是面向编码代理的内部工程指南，不是游戏官方规范，也不把任何样本模组当作规范。结论以目标游戏版本实际加载、错误信息和运行结果为准。`W:\mao\tx\tools\decompilers\game-lib-src` 的目标版本行为优先于内部摘要；`W:\mao\tx\模组实例\` 中观察到的路径和写法只可作为内部核验线索。不要复制其中的单位配置，更不要把受保护的加载器反编译内容搬入模组或文档。 

## 本章目标

Rusted Warfare 的 `[action_*]`、`[hiddenAction_*]`、资源、标签、内存和效果不是互不关联的功能开关。更可靠的理解是：它们共同构成由事件和条件驱动的配置状态机。单位处于某个状态；条件读取可观察状态；行动在满足前置条件后产生有限且可追踪的状态转移；转移再触发效果、队列、炮塔或后续行动。

把它当作状态机有四个直接收益：

| 目标 | 具体做法 | 可检查的结果 |
|---|---|---|
| 可读 | 给状态、事件、资源和动作起稳定前缀 | 代理能按名称定位转移边 |
| 可观测 | 在调试构建中为关键转移显示短消息、动态文本或可见标签 | 能回答“什么时候、为何发生” |
| 有界 | 资源计数、递归触发、生成数量和冷却都设上限 | 不会随时间无限膨胀 |
| 幂等 | 同一事件重复到达时，结果保持正确 | 存档恢复、重复点击或事件重入不损坏状态 |

本章不重列全部字段。字段名与基础语义以 `SKILL.md` 为索引；这里说明怎样组合字段、怎样降低配置状态机的不可维护性，以及怎样让验证者可以定位问题。

## 一、先画状态，再写节

### 1. 用状态表代替“想到一个 action 就加一个 action”

在创建任何行动前，为每个单位写一张小状态表。它可以放在变更说明、任务注释或本地设计笔记中，不必成为发布包文件。至少应包含状态变量、取值范围、拥有者、写入者和可见证据。

| 状态 | 存储候选 | 合法范围 | 写入事件 | 读取位置 | 玩家证据 |
|---|---|---|---|---|---|
| 建造阶段 | 局部资源或内存数值 | `0..3` | 建造完成、升级、受损恢复 | 行动可见性、炮塔条件 | 名称后缀、信息行动 |
| 超载开关 | 标签或内存布尔值 | 开/关 | 玩家点击、自动保护 | 射击条件、图像可见性 | 可点按钮、状态图标 |
| 脉冲次数 | 局部资源 | `0..N` | 定时器、发射、补给 | 触发条件、文本 | 动态库存或数值 |
| 队伍科技 | 全局资源或全局队伍标签 | 文档化上限 | 研究完成 | `canBuild`、锁定条件 | 解锁项和提示 |
| 冷却闸门 | 行动冷却或内存时间戳 | 非负、有限 | 成功执行 | `isActive`、触发条件 | 灰化按钮或计时文本 |

若一个状态既影响 UI，又影响战斗，又影响生产，必须明确唯一的权威存储位置。不要同时以“一个标签 + 一个局部资源 + 一个内存布尔值”表示同一事实，除非其中两个是可从权威状态机械推导的缓存，并且存在同步与恢复策略。多份真相是模组状态机最常见的漂移源。

### 2. 状态转移的最小规格

每一条转移用一句话描述，格式建议为：

`事件 E 到达；若守卫 G 成立且资源 R 足够，则执行一次 T；T 将状态 S 从 A 改为 B，并留下观测 O。`

例如：

`玩家启用护盾；当能量不少于阈值且未处于锁定时，设置 shield_on 标签并扣除一次启动费用；同时写入短提示和冷却。`

这个描述应先于 INI。它明确了“何时发生”“何时不能发生”“发生多少次”“重复发生是否安全”。随后再把守卫、结果、冷却和表现拆入行动字段。

### 3. 事件不是轮询的替代品

`autoTriggerOnEvent` 适合由生命周期或命令明确产生的边界：创建、完成激活、销毁、队列变化、传送、队伍变化、运输变化等。对于一次性初始化、完成后发放、销毁清理，优先事件而不是持续 `autoTrigger`。

`autoTrigger` 是条件轮询。它适合“条件从假变真后应尽快收敛”的情况，例如低能量时关闭模式、计数到阈值时释放蓄能、受损后进入保护。但轮询必须接受：条件在多次检查中都为真；检查频率不是业务语义；实际运行中可能与其他事件交错。因此它必须有闸门和幂等结果。

| 需求 | 首选 | 需要的保护 |
|---|---|---|
| 单位创建时初始化一次 | `autoTriggerOnEvent: created` | 初始化动作可重复执行而无害 |
| 建造完成时解锁一次 | `completeAndActive` 事件 | 重复完成通知不重复发奖 |
| 玩家主动切换模式 | 可见 `[action_*]` | `isActive`、价格、冷却、互斥标签 |
| 能量耗尽时关机 | `autoTrigger` | 仅在“当前确实开启”时执行关闭 |
| 每隔一段时间积累一格 | 有冷却的行动链或低频检查 | 上限、不可重复增量、掉帧容忍 |
| 弹药命中后短暂标记 | 投射物或行动事件链 | 明确生效对象与清理条件 |

## 二、命名、分层与可查性

### 1. 为 action 建立命名空间

节名本身是引用 ID。重复行动、抛射体、炮塔、资源名会在加载时失败，因此名称必须在单位可见范围内稳定且唯一。建议采用 `类别_对象_意图_阶段`，并用 ASCII 小写与下划线。例如：

| 前缀 | 用途 | 示例意图 |
|---|---|---|
| `ui_` | 玩家可见命令 | 开启、关闭、升级、修复 |
| `evt_` | 生命周期或外部事件处理 | 创建初始化、队列完成、运输变化 |
| `guard_` | 不产生直接玩法结果的安全收敛 | 能量不足关机、计数截断 |
| `fx_` | 只负责视觉或听觉表现的中转 | 播放一次提示、生成短效果 |
| `flow_` | 一条多步骤业务流程的节点 | 预检、扣费、提交、收尾 |
| `dbg_` | 仅开发期使用的诊断动作 | 显示资源、重置试验状态 |

不要把按钮文字当 ID；本地化会变，而引用 ID 应不变。不要复用同名行动来承载互斥流程，例如既做“开机”又做“升级完成”，因为错误栈只会报告节和键，语义混杂会大幅增加定位时间。

### 2. 分开命令、规则与表现

一个大型行动若同时扣资源、写内存、转换单位、生成单位、播放声音、改变路径、显示消息，通常已经超过人类和代理可安全审阅的尺度。可以按三层切分：

1. **命令层**：按钮是否可见、是否锁定、价格、队列时间、玩家目标。
2. **规则层**：前置条件、状态修改、资源扣加、上限、互斥、转换、后续行动。
3. **表现层**：效果、声音、动画、短提示和动态显示。

拆分不等于无条件连锁。行动链要保持一条明确入口、一个业务提交点和有限数量的后续节点。若结果只影响表现，可由规则层触发一个 `fx_` 节；不要让表现节反过来决定核心资源是否扣除。

### 3. 合法的小型示例

下例是新写的抽象示例，名称、数值和效果均不对应任何样本单位。它演示两个互斥模式如何通过标签和守卫保持收敛。实际字段是否适用于当前版本，仍必须在目标游戏中验证。

```ini
[action_ui_enable_pulse]
text: 启动脉冲
isVisible: if not self.tags(includes='mode_pulse')
isActive: if self.energy(greaterThan=24)
addEnergy: -25
temporarilyAddTags: mode_pulse
alsoTriggerAction: fx_pulse_enabled

[action_ui_disable_pulse]
text: 停止脉冲
isVisible: if self.tags(includes='mode_pulse')
temporarilyRemoveTags: mode_pulse
alsoTriggerAction: fx_pulse_disabled

[hiddenAction_guard_disable_empty]
autoTrigger: if self.tags(includes='mode_pulse') and self.energy(empty=true)
temporarilyRemoveTags: mode_pulse
alsoTriggerAction: fx_pulse_disabled

[hiddenAction_fx_pulse_enabled]
playSoundToPlayer: interface_click
showMessageToPlayer: 脉冲已启动

[hiddenAction_fx_pulse_disabled]
showMessageToPlayer: 脉冲已停止
```

这里的关键不是文字或音效，而是 `guard_disable_empty` 只有在“模式已开启且能量为空”时修改状态。即使轮询多次命中，第一次移除标签后守卫失效，因而结果幂等。若临时标签的生命周期不能满足设计，应选择更适合持久化的状态载体，不要假定任何状态会跨转换、死亡或存档自动保留。

## 三、LogicBoolean：把条件视为带类型的表达式

### 1. 先判类型，再写表达式

引擎会对逻辑布尔、数值、单位引用、标记和文本动态值进行类型解析。一个看似合理的字符串如果被放入预期为 `LogicBoolean` 的键，或表达式返回了错误类型，加载会带着源键上下文失败。不要以“INI 没有语法高亮”为理由猜测类型。

写条件前回答四个问题：

| 问题 | 示例 | 常见错误 |
|---|---|---|
| 该键需要布尔、数值还是单位引用？ | `isVisible` 需要布尔结果 | 用数值资源直接填入布尔键 |
| 左右两侧是否是可比较类型？ | 数值与数值比较 | 把单位引用和字符串比较 |
| 条件读取的是当前单位、事件源还是动作目标？ | `self`、事件引用、目标引用 | 默认以为所有引用都指向自己 |
| 空引用如何处理？ | 无目标时保持安全分支 | 对可能为空的引用继续取属性 |

把长表达式拆成可命名的业务条件。虽然配置未必支持自定义逻辑函数，但你可以用行动名称、注释和状态表表达语义：`guard_low_energy`、`flow_has_capacity` 比 `hiddenAction_17` 更能提示审阅者它在保护什么。

### 2. 条件应有单调性或明确反转点

好的自动条件会把系统推向稳定状态。例如“处于充能模式且能量为空则退出”是单调的：执行后条件不再成立。危险条件会在同一阈值附近来回切换：能量大于十开机、小于十关机，若自然再生很快，就可能持续抖动。

对可能抖动的设计加入滞回、冷却或显式确认：

| 问题 | 不稳写法 | 稳定策略 |
|---|---|---|
| 阈值反复穿越 | `energy > 10` 开，`energy < 10` 关 | 开阈值高于关阈值，例如二十与八 |
| 多个事件重复入队 | 每次创建都加入同一动作 | 以标签或计数器记录“已初始化” |
| 每次检查都加资源 | 条件为真就加一 | 用冷却或计时闸门限制周期 |
| 异步链路失序 | 先表现、后扣费 | 先检查和提交状态，再表现 |

### 3. `%{logicBoolean}` 是运行时显示，不是配置模板

本地化文本或 UI 字段中使用的 `%{logicBoolean}` 会在运行时重新求值。它适合展示当前资源、阶段、目标距离等，而不应被误认为一次性展开的常量。动态文本读取应尽量便宜，避免每帧触发广域搜索或多层复杂引用。

建议为动态显示写出读取预算：它应读取自身资源、标签、内存或已维护的数值，不要在字符串中嵌入全图扫描。对长文本也不要假设会自动适配所有语言和窄屏 UI。

```ini
[action_dbg_status]
displayType: infoOnly
text: 阶段 %{memory.stage}，储备 %{self.resource(type='charge')}
isVisible: if self.isControlledByAI() == false
```

这只是显示结构示例。若 `memory.stage` 未定义或表达式类型不正确，必须回到加载错误中的源键上下文处理，而不是用多个后备表达式掩盖错误。

## 四、资源模型：区分队伍货币与单位状态

### 1. 两类资源的职责

`[global_resource_*]` 表示模组范围的全局货币或队伍经济概念；`[resource_*]` 表示每个单位实例各自拥有的状态。源模组中能看到这两类写法，但那些具体经济设计只是示例，不能直接推导为本模组的规范。

| 维度 | `[global_resource_*]` | `[resource_*]` |
|---|---|---|
| 所有权 | 队伍或全局经济层 | 单位实例 |
| 合适用途 | 研究点、阵营材料、共享科技货币 | 弹仓、热量、充能、姿态层数、局部库存 |
| UI 影响 | 可作为宏观资源呈现 | 通常用于单位相关状态或条件 |
| 生命周期 | 应在全局经济设计中明确 | 随单位、转换、生成机制而变化，需测试 |
| 典型风险 | 无上限的生产链拖垮平衡 | 多个行动同时改写导致超界 |

不要用全局资源存储“当前这门炮是否装填”，也不要为每个玩家共享科技创建一个隐形单位局部计数器，除非设计明确接受这些生命周期和所有权后果。

### 2. 资源名、量纲和边界

资源 ID 也属于交叉引用命名空间。使用描述性 ASCII 名，避免与未来全局资源混淆；建议局部资源加语义前缀，例如 `charge`、`heat`、`module_level`，而不是 `r1`。在状态表中记录：

| 属性 | 建议填写内容 |
|---|---|
| 量纲 | 次数、点数、百分比基数、秒对应的 tick 数 |
| 最小值 | 通常为零；是否允许负数必须明确 |
| 最大值 | 固定上限，或由单位等级推导 |
| 写入者 | 哪些行动、投射物、生成器可改变它 |
| 消费者 | 哪些条件、UI、炮塔或升级读取它 |
| 复位 | 创建、转换、死亡、升级、存档后各怎样处理 |

若要实现“最多三层”，不应只依赖“每次加一且相信不会多触发”。应同时有正常路径和防御路径：正常路径只在 `< 3` 时加；防御路径在任何意外组合导致 `> 3` 时恢复到上限或阻止后续效果。防御路径不替代测试，它是配置在事件交错下维持不变量的最后一道闸门。

### 3. 价格、资源修改与原子性思维

行动的 `price` 或资源使用字段通常承担“是否足够与扣除”的入口语义，结果字段再承担状态更新、生成、转换等后果。无论具体字段的结算顺序如何，设计上应把它当作一个小事务：

1. 读取前置状态和资源是否满足。
2. 判定是否已经完成过同一业务意图。
3. 提交唯一权威状态与费用。
4. 触发可重试或无害的表现、辅助效果和后续检查。

不要让一个后续动作在资源扣除之后仍可能因缺引用、无目标或错误条件而中途失败，却又没有补偿策略。对于会生成单位、转换载体、转移资源的复杂操作，先在最小隔离模组中测试“成功”“资金不足”“无可放置空间”“连续点击”“存读档后继续”五种路径。

### 4. 1.15p11 与内存支持

1.15p11 提供与 memory 相关的支持能力。它适合表达结构化的单位局部状态，尤其是一个状态不等同于货币、弹药或开关时。但版本兼容性不能通过文档推断：针对 1.14 与 1.15 的发布目标，需在目标版本分别加载、创建单位、触发写入、读取动态文本、进行转换和存读档。

内存不是无限日志。不要每帧附加字符串，不要把可从资源或标签得出的信息重复塞入内存，不要将玩家输入不加约束地拼成展示文本。为每个 memory 字段列出名称、类型、默认值、写入点、最大长度或范围。

## 五、效果、音效、生成和投射物作为副作用

### 1. 先定义游戏结果，再定义表现

一个状态改变要先回答“游戏规则上发生什么”，再回答“玩家看见和听见什么”。例如护盾状态切换的规则结果是标签或数值变化，表现结果可能是动画、音效、视觉效果和短消息。把两者混为一体时，很容易发生“音效播放了但状态没变”或“状态变了但玩家没有任何证据”的问题。

| 副作用 | 必须说明的约束 |
|---|---|
| `spawnEffects` | 是否允许屏幕外产生、是否会高频堆积、引用是否存在 |
| 声音 | 作用范围是单位、玩家还是全局；连发是否扰民；文件可否解码 |
| `spawnUnits`/`produceUnits` | 数量、所有权、位置失败、上限、是否会递归 |
| 炮塔发射 | 炮塔和投射体引用、目标或地面语义、次数上限、友军伤害 |
| 转换单位 | 当前标签、资源、运输、附件、内存等状态如何保留或重置 |
| 路径点 | 失败分支、目标是否可达、是否会覆盖玩家命令 |

### 2. 递归的每一层都必须有预算

行动可以触发行动，投射物可以生成投射物，效果也可再发出效果。任何一条边一旦形成环，就必须写出至少一个自然终止条件：最大生成数、递归层数、资源消耗、一次性标签、冷却、寿命或事件仅发生一次。不要用“理论上不可能同时满足”作为终止证明。

审阅时画一张副作用图：节点是 action、projectile、effect、spawnUnit；边是 `alsoTriggerAction`、生成、开火、死亡或队列回调。若图中有环，给每条环写出耗尽量或闸门。以下清单可直接用于代码审阅：

- [ ] 每条生成链都有最大数量或不可重复的状态变化。
- [ ] 每个循环至少有一项单调减少或一次性标记。
- [ ] 事件触发与条件轮询没有共同无条件地启动同一链。
- [ ] 失败路径不会继续生成“补偿生成物”而再次进入原链。
- [ ] 特效与声音的频率在单位群集时仍可接受。

### 3. 看得见不等于正确

视觉效果、光、声音或动画出现，只能证明表现字段某个分支执行过，不能证明费用、权限、目标、队伍归属或资源边界正确。反过来，静默的后台维护行为若没有合适的可观察点，会使测试者无法区分“没有触发”和“触发后被立即覆盖”。

为每个关键状态机至少安排一种非侵入观测：

| 场景 | 低侵入观测办法 |
|---|---|
| 初始化 | 开发期信息行动显示阶段和资源 |
| 玩家命令 | 按钮可见或锁定状态与简短结果消息 |
| 自动关机 | 状态图标消失或局部资源归零 |
| 高风险生成 | 临时计数或沙盒日志提示，不在正式版保留刷屏消息 |
| 转换 | 转换后单位名称、标签驱动的 UI 与资源显示 |

正式发布前删除或隐藏 `dbg_` 入口，但不要删除提供玩家反馈的正常表现。调试功能必须与玩法按钮区分，避免玩家在多人局中意外重置状态。

## 六、低频检查、CPU 与稳定性

### 1. 检查频率是设计的一部分

自动触发可配置检查频率和冷却；高频选项会增加 CPU 压力。把每帧检查视为稀缺预算，尤其是单位数量多、条件包含广域查询、动态文本频繁求值或副作用会扩散时。低频检查不是“变慢”，而是必须被设计为容忍延迟。

| 条件类别 | 通常的设计方向 | 原因 |
|---|---|---|
| 创建、完成、销毁 | 使用事件 | 不需要轮询 |
| 资源耗尽保护 | 低频轮询加幂等关机 | 允许少量延迟，结果单调 |
| 临界射击条件 | 由炮塔条件直接判断 | 不另起全局扫描 |
| 范围内目标搜寻 | 限制范围、标签和调用频率 | 单位多时成本放大 |
| UI 数字 | 读取本地已有值 | 避免动态全图搜索 |
| 粒子尾迹 | 降低产生率且限制生命周期 | 防止视觉对象堆积 |

`autoTriggerCooldownTime_allowDangerousHighCPU` 不是为了绕开设计工作。只有在已有量化需求、最小化条件、明确单位数量上限并完成目标设备测试时才考虑高频路径。默认先采用事件、冷却、`every4Frames` 或 `every8Frames` 一类较低频检查，或采用可延迟收敛的规则。

### 2. 去抖与状态收敛

若某个条件由浮动资源、移动、目标可达性或短暂事件决定，就会在连续检查中翻转。以“触发一次”为目标时，加入以下至少一项：

- 状态标签：只允许尚未处理的对象进入流程。
- 冷却：动作成功后一定时间内不再执行。
- 双阈值：进入与退出使用不同阈值。
- 计数阈值：连续满足若干次再提交。
- 事件边缘：由明确事件启动，轮询只负责故障兜底。
- 有界队列：若通过队列行动延迟执行，限制可累计数量。

设计时明确“最多延迟多久”和“漏掉一次检查会怎样”。如果答案是“会永久错误”，说明该逻辑不适合依赖低频轮询，应当寻找事件、状态持久化或更稳健的恢复机制。

## 七、典型模式矩阵

### 模式 A：一次性初始化

适用于单位创建后设定默认状态、补齐派生标签、初始化局部资源。

1. 用创建事件进入 `evt_init`。
2. 在守卫中检查“尚未初始化”。
3. 写入唯一权威状态和一次性标记。
4. 仅在需要时触发表现。
5. 用显式复位路径处理转换或重建后的语义。

反模式：创建事件无条件加资源。重复创建通知、转换过程或脚本生成路径一旦重复进入，资源会不断累积。

### 模式 B：可切换模式

适用于武器模式、姿态、生产模式、隐身开关。

1. 一个权威标签或有限枚举资源表示模式。
2. 每个模式有唯一进入和退出动作。
3. 进入条件包括费用、冷却和互斥模式。
4. 自动保护只做“退出危险模式”，不要悄悄重进模式。
5. UI 同时展示当前模式、不可用原因和下一步动作。

反模式：两个按钮都只是“添加标签”，却没有移除对方标签；最终两个模式并存，后续条件变得不可预测。

### 模式 C：有限蓄能

适用于三段充能、有限弹仓、任务进度。

1. 资源写明最大值 `N`。
2. 增加动作仅在 `< N` 时执行。
3. 消费动作仅在 `> 0` 时执行。
4. `guard_cap` 防止异常路径突破 `N`。
5. 文本读取该资源，便于测试者观察。

反模式：一次攻击触发两个后续 action，两者都加一，但只在入口检查是否小于上限。并发或连锁时仍可能越界。

### 模式 D：事件驱动的奖励

适用于完成建造、击杀、队列项目完成后发放一次效果或资源。

1. 事件节只收集上下文并进入规则节。
2. 规则节使用一次性标记或资源条件确认资格。
3. 提交奖励和标记的顺序按可恢复原则设计。
4. 奖励表现与资源提交分离。
5. 多人、盟友、AI、取消、死亡和转换分别测试。

反模式：只依赖消息或特效作为“已经奖励”的证明；表现可能被关闭、被覆盖或根本不面向正确玩家。

## 八、行动与交叉引用的加载边界

解析阶段会创建并校验行动、效果、资源、炮塔、投射体和逻辑布尔。未知字段、未使用键、拼错的逻辑类型或重复命名都可能带着源节或源键上下文失败。随后加载后的解析还会处理跨文件关系，例如 `overrideAndReplace`、`canBuild`、`builtFrom` 和升级关联。不要因为一个行动节写法“看起来像 INI”就认为它可用。

行动文档审阅至少覆盖以下引用：

| 引用类别 | 核验方式 |
|---|---|
| `alsoTriggerAction`、队列行动 | 被引用 action 唯一存在，链无无界环 |
| `spawnEffects`、动画、声音 | 名称或路径可解析，表现频率合理 |
| 炮塔和投射物 | 两端 ID 存在且语义匹配目标类型 |
| 资源 | 声明位置、拼写、全局或局部所有权一致 |
| 单位转换与生成 | 目标单位能加载，状态保留策略有测试 |
| 本地化锁定消息与动态文本 | 语法、回退与长度经过目标语言检查 |

因为错误会带源键，排错时优先记录完整错误文本、单位文件路径、节名、键名、当前目标版本和最小复现包。不要直接改几十个键“试到能加载”；这会掩盖第一个错误并引入更多未使用键。

### 编写时

- [ ] 以最小单位加载确认字段、逻辑类型和 ID 解析。

## 十、提交前的状态机审阅问题

1. 这个状态由谁拥有，唯一真相保存在哪里？
2. 事件或条件重复出现三次，最终状态和资源是否仍正确？
3. 条件在阈值两侧抖动时，会不会反复扣费、刷特效或切换？
4. 任何行动链、投射物链或效果链是否有图上的环？若有，预算是什么？
5. 一百个同类单位同时存在时，轮询、搜索、文本和特效是否仍然可接受？
6. 玩家能否从正常 UI 分辨当前状态、不可用原因和成功结果？
7. 加载器指向的源键出错时，是否能从命名和状态表快速定位？
8. 这些规则在目标版本、存读档、AI、多人和转换场景是否都测试过？

对前六题不能给出明确答案的配置，不应直接进入完整模组。先把它缩为一单位、一资源、一入口、一退出和一条观测，再逐步扩展。这样的最小验证比在大型内容包中猜测状态流转更快，也更容易留下可维护的工程证据。

## 十一、故障注入与状态机验收证据

正常路径测试只能说明“在一次幸运的事件顺序中它曾经成功”。配置状态机的实际风险来自重复事件、条件翻转、资源边界、引用为空、单位转换和多个副作用交错。故障注入不需要修改引擎；它是有意构造这些边界条件，观察设计的不变量是否还成立。

### 1. 为每个状态声明不变量

不变量是任何合法运行时刻都必须为真的短句。它应能被玩家可见状态、调试信息、资源值或单位数量证明，而不是只写成主观感受。一个状态变量至少写出值域、互斥关系和单调关系。

| 设计对象 | 合格不变量 | 不合格描述 |
|---|---|---|
| 三段蓄能 | `charge` 始终在零到三之间 | “充能一般不会太高” |
| 两种模式 | `mode_attack` 与 `mode_guard` 不同时存在 | “两个按钮通常不会一起点” |
| 初始化奖励 | 每个单位实例最多获得一次 | “创建事件应该只来一次” |
| 自动保护 | 能量为空后不能保持高耗能模式 | “过一会儿会自己关” |
| 生成物 | 每次合法触发最多生成 N 个，且不会反向重启入口 | “生成链理论上会结束” |
| 冷却 | 成功操作后在指定间隔前不会再次提交费用 | “点击很快应该没反应” |

不变量要和存储载体对应。例如“模式互斥”如果依赖两个标签，就需要检查二者；如果依赖一个枚举资源，就检查其取值集合。不能在描述中使用一个状态，在实际条件中读取另一个状态，然后认为两者天然同步。

### 2. 事件重入试验

对每个事件型 `hiddenAction`，连续制造其可能重复出现的入口。实际构造方法取决于事件类型，但测试意图固定：事件若重复到达，提交是否仍安全？

| 入口 | 重入构造 | 应保持的结果 |
|---|---|---|
| `created` | 批量生成、转换后重建、地图重开 | 初始化不叠加，默认状态一致 |
| `completeAndActive` | 取消后重建、读取建造中存档 | 奖励和解锁不重复 |
| 队列完成 | 连续加入同类项目、队列取消再加入 | 计数、资源、生成量不超界 |
| `teamChanged` | 多次更换所属、载具/附件关系变化 | 标签和所有权不残留旧队伍语义 |
| 运输事件 | 装入、卸出、强制移除、死亡 | 不重复发放或删除资源 |
| 传送或路径点成功 | 连续下令、目标失效再找到 | 不建立无界行动链 |

若某事件根本不可能在目标玩法中重复，也要记录这个前提和引擎版本，而不是把它作为未说明假设。最稳的动作仍应能重复运行而保持同一正确状态。

### 3. 资源边界试验

资源边界应在正常动作、自动动作和异常路径都被验证。测试不仅测试零、最大值，还测试相邻值以及多个写入者同时满足条件时的组合。

| 初始值 | 操作 | 应观察 |
|---|---|---|
| `0` | 执行消费 | 行动不可提交，费用和状态都不改变 |
| `1` | 消费一次 | 恰好到零，表现不重复，保护逻辑可收敛 |
| `N-1` | 增加一次 | 恰好达到上限，UI 与规则一致 |
| `N` | 再增加 | 不超过上限，也不产生重复成功反馈 |
| `N+1`（调试构造） | 触发 guard | 被截断或被阻止，错误状态不扩散 |
| 负数（若可构造） | 读取与消费 | 明确安全行为，不能借此无限获利 |

尤其要检查价格结算和结果动作之间的关系。若费用不足，后续效果、转换或生成是否仍会被错误执行？若费用足够但生成位置无效，业务状态是否被消耗而没有合理结果？这类问题通常不在纯加载阶段暴露。

### 4. 条件翻转与去抖试验

当规则依赖能量、距离、血量、目标存在或队列长度时，让该条件在阈值附近快速翻转。目的不是制造不真实场景，而是确认系统在网络、帧率、移动和多个单位影响下不会发散。

建议记录进入阈值、退出阈值、检查频率、最大允许延迟和预期最终状态：

| 规则 | 进入阈值 | 退出阈值 | 最大延迟 | 预期 |
|---|---|---|---|---|
| 高耗能模式 | 能量不少于二十 | 能量不高于八 | 两次低频检查内 | 只在边界各切换一次 |
| 蓄能释放 | 计数达到三 | 释放后归零 | 一次冷却窗口 | 只释放一轮 |
| 低血量保护 | 血量低于阈值 | 血量恢复到更高阈值 | 可接受的检查间隔 | 不闪烁、不刷音效 |
| 目标锁定 | 目标存在且可达 | 目标为空或不可达 | 不跨越玩家新命令 | 状态安全回退 |

若规则必须即时反应，则不要用低频自动触发假装即时。应改用更接近实际事件的触发点，或明确设计一个可接受的等待状态与玩家反馈。

### 5. 转换、死亡、存读档的状态契约

状态迁移最容易被忽略的三种边界是 `convertTo`、单位死亡和存档恢复。对每个状态写一条契约：保留、重置、转移、销毁或重新计算。没有写出的行为就是测试缺口，不是“引擎应该处理”。

| 状态类别 | 转换后常见可选策略 | 死亡后策略 | 存读档验证 |
|---|---|---|---|
| 临时模式标签 | 明确保留或重置到默认 | 随单位销毁 | 恢复后不出现双模式 |
| 局部弹仓/热量 | 保留、按新单位容量截断或清零 | 销毁 | 数值不越界、不丢失语义 |
| 全局研究资源 | 不因单单位转换而意外改变 | 不因单位死亡回滚 | 队伍经济一致 |
| memory 阶段 | 指定可否迁移，按版本测试 | 销毁或用于死亡结果 | 1.15p11 与目标版本分别验证 |
| 运输/附件状态 | 主从关系重新建立或解除 | 明确载员/附件命运 | 读取后引用不悬挂 |

对 1.15p11 的 memory 相关支持，尤其不要从“写入时能显示”推断“转换和存读档都保留”。测试每个承诺的生命周期阶段，并将结果记录在版本矩阵中。

### 6. 副作用预算表

把副作用总量与时间窗口写出来，可以在发布前发现许多肉眼难见的爆发。预算不是为了精确模拟引擎内部帧，而是给审阅者一个上界。

| 路径 | 一次入口上限 | 每秒上限 | 停止条件 | 观测方式 |
|---|---|---|---|---|
| 蓄能完成 | 一次效果、一条声音、一次发射 | 受冷却限制 | 资源归零或标签移除 | 资源文本与单位数 |
| 命中链 | 每命中最多一个后续动作 | 受投射物寿命限制 | 递归层数或 `maxSpawnLimit` | 效果和投射物计数 |
| 自动保护 | 最多一次关机提示 | 直到重新手动开启 | 模式标签已移除 | UI 状态与日志 |
| 地图对象初始化 | 每对象一次生成 | 地图重开时重新开始 | 一次性标记 | 起始单位数量 |
| 音效反馈 | 每玩家操作一次 | 受按钮冷却限制 | 操作完成 | 听觉和消息记录 |

若无法写出上限，说明触发图中存在未处理的循环、全局扫描或外部事件前提。先回到状态表和引用图处理，而不是以“实际运行看着没卡”为结论。

### 7. 验收记录模板

每个高风险状态机可用下列短模板存档。它比堆积截图更便于后续代理重新验证：

```text
功能：脉冲模式
权威状态：单位标签 mode_pulse
不变量：模式开启时能量非空；同一时间只存在一个模式标签
入口：玩家 action_ui_enable_pulse
退出：玩家 action_ui_disable_pulse；guard_disable_empty
边界：能量 0/1/24/25；连续点击；重开；转换；读档
版本：1.15p11 已测，1.14 未测
证据：最终 rwmod、测试地图、错误日志或状态截图位置
```
