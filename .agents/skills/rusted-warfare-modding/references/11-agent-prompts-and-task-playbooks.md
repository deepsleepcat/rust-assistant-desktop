# 代理提示词与任务剧本：Rusted Warfare 模组工程

> 导航：本页依赖 `SKILL.md` 的总原则；案例事实参考 `08-case-study-abyss-stars.md` 和 `09-case-study-aseu.md`；压缩包分类参考 `10-instance-mod-compatibility-matrix.md`；语义边界、勘误与无引擎流程参考 `12-known-limitations-and-errata.md`。这些模板用于内部代码代理，不是对任何第三方模组源文件的复制。

## 1. 使用说明

本页的目标是让代理在处理 Rusted Warfare 1.14/1.15 内容时，把“先读证据、再动手、最后给出可复核结果”变成可执行的提示词约束。提示词不是权限替代物，也不会自动补足引擎语义。调用代理前，任务发起者仍需说明工作根、目标版本、是否允许写入、是否有真实引擎、是否允许打包、验收重点和不可触碰的外部目录。

所有提示词都遵循同一条硬规则：**代理不能把目录印象、搜索命中或模拟器显示写成运行时事实。** 若没有读到相应文件，不能声称已经读到；若没有实际执行命令，不能声称已执行；若没有目标引擎，必须把运行验证标为未执行，并给出静态替代证据和剩余风险。

### 1.1 调用前的任务卡

在提交具体提示词前，先填一张任务卡。字段缺失时，代理应暂停在澄清，而不是自行扩大范围。

| 字段 | 示例值 | 为什么必填 |
| --- | --- | --- |
| 工作根 | 某个解包根或项目根 | 避免误扫外部源和兄弟项目 |
| 目标版本 | 1.14 / 1.15p11 / 未知 | 决定字段语义和测试矩阵 |
| 任务模式 | 新建、修改、审查、调试、打包、迁移 | 决定允许的输出和风险 |
| 写入范围 | 指定文件列表 | 防止代理做无关格式化 |
| 外部源 | 只读来源根 | 明确不可写边界 |
| 引擎条件 | 有/无、可否启动、版本 | 决定证据等级 |
| 验收标准 | 行为、静态检查、档案可读性等 | 防止只完成文本改动 |
| 停止条件 | 遇到未知语义、覆盖冲突、缺失入口时 | 让代理在危险点停下 |

可直接复制的任务卡：

```text
工作根：<绝对路径>
目标版本：<版本或未知>
只允许修改：<绝对路径列表>
只读参考：<绝对路径列表>
禁止触碰：<目录/文件>
任务类型：<一种>
期望行为：<可观察结果>
验证条件：<命令、引擎、日志或静态证据>
未知时：保留未知，列出最小澄清问题，不猜测
交付：精确 diff、验证命令、结果、未覆盖风险
```

## 2. 通用代理系统提示词

下面的文本可作为任务前置约束。尖括号内容由调用者替换，方括号内容是可选条件。

```text
你是 Rusted Warfare <目标版本> 模组工程代理。
工作根是 <工作根>，你只能修改 <文件白名单>。
外部来源 <来源根> 仅可读，不得在其中创建、删除、重命名或格式化文件。

执行顺序必须是：
1. 先读取任务相关的现有文件、相邻模板和入口文件；列出实际读到的路径。
2. 再搜索引用、继承、资源、动作、标签、资源名和地图/音频路径；说明搜索范围。
3. 在写入前给出你理解的行为、可能影响和停止条件。
4. 只做任务要求的最小变更；不顺手升级格式、不重命名无关文件、不删除历史副本。
5. 运行可用验证；无法运行时给出静态证据和明确未验证项。
6. 最终报告必须包含精确 diff 摘要、实际命令、实际结果、未覆盖范围和证据等级。

证据规则：读到的事实写“观察到”；由静态引用推断的写“静态推断”；没有目标引擎的写“未执行运行时验证”。不得虚构读取、命令、日志、截图、打包成功或游戏内行为。遇到重复段落、多个入口、版本字段冲突、未知模板语义或路径不确定时暂停并标记，不得按常识替换。
```

这段约束应与工具权限同时使用。它不能阻止一个拥有过大文件权限的代理，因此调用者还必须使用实际的文件白名单、只读挂载或版本控制检查。

## 3. 新建模组任务剧本

### 3.1 新建最小单位

**适用**：从零添加一个单位、建筑、资源节点或逻辑实体。

```text
先读以下文件并列出路径：根入口、一个同类已知定义、其继承模板、局部资源约定、相关枚举或建造入口。
不要先写新文件。先回答：同类对象的最小段落是什么？它由哪一条入口被发现？资源路径相对于哪个根？目标版本是否有该字段的权威来源？

设计要求：
- 使用一个新写的最小定义，不复制第三方完整配置。
- 身份、显示资源、建造入口、行为和机制状态分开说明。
- 若使用模板，说明每个父模板的来源和覆盖字段。
- 若使用标签、资源、隐藏动作或事件，先给出写入/读取/清理表。

写入后：
- 检查新文件的段落闭合、路径、编码和命名冲突。
- 搜索同名对象、同名动作、资源名、标签名和资产引用。
- 若有引擎，测试发现、建造、可见动作、基础行为、受击/销毁和重新加载。
- 若无引擎，执行静态引用检查并明确无法证明的行为。

交付：文件 diff、引用图摘要、验证命令和未验证项。不要声称新单位已经可玩，除非有目标版本运行证据。
```

**审查要点**：新建任务最常见的失败不是语法，而是对象没有进入入口、贴图路径相对根错了、模板字段被覆盖、逻辑状态没有回收，或新名字与旧名字只差大小写。代理必须先回答“谁会发现它”，再回答“它长什么样”。

### 3.2 新建共享模板

```text
先读取至少三个现有同类对象，比较重复字段、差异字段、路径习惯和已知例外。不要因为两个文件相似就立刻抽模板。
请建立字段分级：稳定公共字段、允许子类覆盖字段、必须由具体对象声明字段、禁止通过隐式继承改变的字段。

只创建一个最小共享模板和一个消费方示例。对所有潜在消费方输出影响半径，不自动迁移全部对象。检查：
- 父模板是否有唯一且可追溯身份；
- copyFrom/copyFromSection 的语法是否有目标版本证据；
- 多重来源声明顺序是否被保留；
- 同名段落是否产生覆盖冲突；
- 模板链是否循环或过深；
- 资源、标签、动作和资产是否被无意共享。

没有原始加载器或引擎验证时，不要输出“最终合并值”，只输出声明层和冲突候选。
```

**停止条件**：如果模板语义只能靠猜测；如果一个模板需要包含大量对象专属数值；如果迁移会同时影响地图、事件和外部来源；如果同名模板在多个领域中存在而无法确定作用域。此时交付分析和小型实验，不继续重构。

### 3.3 新建事件或机制闭环

```text
请先把需求改写成状态图：入口、前置、进行中、成功、失败、取消、超时、销毁/复位。
为每个状态列出局部内存、全局/队伍标签、自定义资源、动态对象和动作入口。

实现只允许先完成一个闭环：
- 初始化只发生一次或明确幂等；
- 每次写入都有读取者或说明它是外部接口；
- 每个资源/标签/内存都有清理或明确长期生命周期；
- 事件结束、对象转换、对象死亡和玩家取消都考虑；
- 周期动作有频率、上限、候选搜索范围和回收条件。

先写静态状态表，再写最小配置。若某个动作字段或条件语义未知，保留抽象占位并列入待验证项，不用相似字段冒充。
```

### 3.4 新建本地化和媒体引用

```text
先读取一个已有文本键/描述/图像/音效引用的同类对象和它的加载根。列出实际使用的编码、引号、换行、路径分隔符、大小写和命名约定。

新内容只添加一组最小文本与一个最小媒体引用。检查：
- 文本是否会被换行或注释规则截断；
- 中英文和符号是否按目标字段允许的形式保存；
- `/n`、反斜线或其他换行写法是否有权威证据；
- 媒体相对路径在解包根和打包根都能解释；
- 未使用资产与缺失资产是否分开报告。

没有运行时就不要声称字体、音频、缩略图或地图能在游戏中显示/播放。
```

## 4. 修改任务剧本

### 4.1 修改现有单位参数

```text
先读目标文件、直接模板、所有显式继承来源和至少一个引用它的入口。检索目标字段的所有声明，标出本层、父层和重复段落。

修改前输出：
- 当前值的证据来源；
- 目标值和原因；
- 可能影响的对象、建造入口、事件和动作；
- 是否涉及版本差异或未确认的覆盖顺序。

只改指定字段，不做格式化重排。修改后重新搜索：同名字段、同名对象、资源/标签依赖、地图或本地化引用。若参数影响性能，补充单位数量、触发频率、搜索范围和动态对象数量的检查。

验证优先顺序：静态 diff -> 语法/引用检查 -> 目标版本最小场景 -> 受影响机制。最终报告不得把“数值写入成功”写成“平衡正确”。
```

### 4.2 修改模板继承

```text
本任务涉及继承边。先读取所有被修改模板、直接消费者、同名模板和相关入口；生成修改前祖先链和受影响消费者列表。

禁止：
- 按 basename 合并同名模板；
- 重新排序多重 copyFrom；
- 将重复段落自动折叠；
- 把无引用文件直接删除；
- 未验证就输出最终字段值。

允许：为一个明确对象增加一条显式继承边，或修正一个有权威证据的相对路径。每次修改后记录路径、段落、字段、影响对象和验证状态。若无法确定目标版本合并语义，停止在冲突报告，不继续批量迁移。
```

### 4.3 修改资源、标签或动作链

```text
先建立资源/标签/内存/动作的写入-读取-清理表，再动配置。对每一处新增或删除分别列出：入口、作用域、生命周期、失败分支、并发/重复触发风险。

删除任何状态写入前，搜索全部消费者和动态字符串候选；添加状态写入后，搜索无读取、无清理和名称冲突。隐藏动作不能因为不可见就省略测试。

如果任务只要求修复拼写，优先做精确替换并保留行为；如果任务可能改变作用域或触发频率，必须升级为机制审查，并在报告中列出影响半径。
```

### 4.4 重组目录和文件

```text
这是迁移任务，不是格式化任务。先递归清单化配置、模板、资产、地图、音频、元数据、备份、复制和未知文件；对每个路径建立入边和出边。

先选一个最小闭包进行演练：定义、直接模板、直接资产、入口条目和测试夹具。模拟新旧根的路径解析，确认差异后才移动。所有移动必须伴随引用更新和可回滚 diff。

严禁：仅按文件名移动；只更新文本而不查地图/媒体；把同名文件当副本删除；顺手清理弃用目录；在外部源目录写入。

完成后分别验证：目录可枚举、入口可识别、文本可解析、模板边可达、资产路径存在、打包布局正确、目标版本最小场景可加载。任何未覆盖步骤明确写出。
```

## 5. 审查任务剧本

### 5.1 常规代码/配置审查

```text
你是审查者，先读变更 diff，再读每个变更文件的上下文、直接模板、入口和引用者。审查顺序为：运行时阻断 -> 数据/状态错误 -> 兼容性 -> 资产/路径 -> 可维护性 -> 风格。

每个 finding 必须包含：严重度、绝对路径、行号或最小定位、触发条件、实际风险、证据、修复建议和未验证项。不要把“我不喜欢”写成 bug。若只是未知语义，写成待验证问题而不是确定性缺陷。

优先查：入口是否仍能发现；相对路径是否以正确根解析；模板/段落覆盖是否改变；动作/资源/标签是否断链；重复段落是否新增；版本字段是否与目标版本冲突；文本、音乐、地图、缩略图是否仍可达；历史/备份文件是否被误纳入。

最后列出未发现的问题、未运行的测试和剩余风险。没有目标引擎时不要声称行为通过。
```

### 5.2 迁移前审查

```text
请审查这项目录/模板迁移是否保持行为。先建立 old_root 与 new_root 的路径映射，再比较：入口、模板边、继承顺序、段落集合、动作名、标签、资源、局部资产、地图和音乐引用。

输出三张表：
1. 明确保持的边；
2. 发生变化但有证据支持的边；
3. 变化原因不明、需要引擎或人工确认的边。

把删除和重命名单独审查。没有无入边证据就不接受删除，没有全局引用结果就不接受重命名。对于包装目录和直接根，分别保留候选，不替任务作者做未经授权的根选择。
```

### 5.3 兼容性矩阵审查

```text
请审查一份 .rwmod 样本矩阵。确认分母包含全部样本，且不可读、无 manifest、包装根、直接根、元数据变体没有被合并成“未知”一行。

逐行检查：档案摘要、读取结果、候选根、manifest 状态、传统 units/目录状态、配置/模板/资产/地图计数、静态引用错误、引擎版本和运行结论是否有证据。文件名只能作为展示，不得推断内部结构。

重点查选择性报告：是否只展示可读档案？是否将没有入口误写成无 manifest？是否将模拟器空白误写成真实引擎失败？是否以一次启动通过代替功能验证？
```

## 6. 调试任务剧本

### 6.1 单位不出现

```text
请调试“单位/对象不出现”，不要先修改配置。先确认复现条件：客户端版本、档案/解包根、地图、阵营、入口动作和日志。

按路径追踪：
入口/枚举 -> 配置文件 -> 段落 -> 模板祖先 -> 资源引用 -> 建造/生成条件 -> 资产。
对每一段标记：存在、可解析、被入口引用、运行时已观察、未知。

分别测试：
- 根布局是直接根还是包装根；
- 入口名称/段落/版本字段是否被识别；
- 定义是否在正确的显式列表或模板入口；
- copyFrom、copyFromSection 或相对路径是否断裂；
- 同名文件、重复段落、大小写和编码是否造成候选冲突；
- 资源缺失是否阻止对象注册；
- 目标条件是否隐藏了对象。

只提出最小修复。若没有引擎，报告“静态可见/静态不可见”，不要声称游戏中不可见。
```

### 6.2 动作、事件或资源不触发

```text
先画出实际状态链：触发源、前置条件、动作、写入状态、读取状态、目标选择、成功、失败、清理。搜索所有相同标签/资源/内存/动作名和动态拼接候选。

检查：初始化是否发生；条件是否永远假；作用域是否错误；动作是否被隐藏但没有任何入口；多个入口是否重复；资源是否不足或永不归零；目标过滤是否为空；死亡/转换是否提前清除；结束路径是否缺失。

如果怀疑版本字段语义，先查原始加载器和最小测试，不把相邻版本的常识当证据。修改后至少验证一次正路径和一次失败/取消路径；无引擎时生成静态闭包和待测用例。
```

### 6.3 打开崩溃或载入失败

```text
先保存可复现条件和完整错误上下文，避免立即编辑。把错误定位到：档案读取、候选根、manifest、文本编码、段落语法、模板路径、资产解码、地图/音乐、运行时动作中的一类。

采用二分隔离：复制一份只读样本到隔离工作目录，逐批移除或禁用最小内容闭包，每批只改变一类输入，并记录档案摘要和结果。不要对原始来源写入。

报告必须区分：
- 工具无法读取；
- 模拟器无法理解；
- 目标引擎拒绝入口；
- 目标引擎解析错误；
- 运行到某功能后失败。

如果日志不可用，给出最小静态假设和需要的下一条证据，不要编造崩溃位置。
```

### 6.4 资源路径、地图或音乐问题

```text
先收集所有引用者及打包后条目，不要只搜索文件名。检查大小写、相对根、扩展名、路径分隔符、空格/中文/符号、包装目录、压缩条目和同名资源。

分别回答：文件存在吗？引用能解析吗？打包后还在吗？目标版本支持吗？运行时已加载吗？
每个问题单独给证据。缺失文件、未引用文件、运行时未覆盖文件不能合并为同一种失败。
```

## 7. 性能追踪剧本

性能任务必须避免“看起来复杂所以一定慢”的推断。静态分析能找出可能的放大器，不能代替测量。

```text
先确认目标：加载时间、对局帧率、内存、档案大小、地图打开时间或动作延迟。记录客户端版本、地图、玩家数、单位量、可复现步骤和基线。

静态阶段统计：
- 每周期/自动动作数量；
- 每实体执行的次数及实体上限；
- 搜索半径、目标过滤和全局扫描；
- 动态生成、复制、投射物和特效的创建/销毁；
- 多重模板和重复资产带来的加载量；
- 地图、音乐和大文件的读入位置。

运行阶段只改变一个变量，至少做三次同条件观察并记录波动。优先使用计数、日志、帧率图或可重复时间，而不是主观感觉。优化候选按收益、行为风险、回滚难度排序；先加上限、缓存或降频，避免直接删掉状态链。

若无引擎，交付静态热点清单、建议插桩点和无法量化的指标，不写“性能已优化”。
```

## 8. 打包、测试与发布剧本

### 8.1 打包前检查

```text
先读发布入口和打包脚本/规则，确认输入根、输出档案路径和允许的临时目录。不要把输出写回只读源目录。

打包前生成清单：相对路径、文件类型、入口、模板、地图、音乐、图像、配置、历史/备份排除项。对每条排除规则给出理由。
打包后重新列档案条目，不相信打包工具的成功退出码；检查入口、包装层、路径大小写、条目数量、摘要和关键资源。
在隔离目录把成品重新解包，使用成品根做第二次静态引用检查。若有引擎，用目标版本测试入口和最小场景。

交付输出档案位置、摘要、清单差异、检查命令、结果和未测试功能。不得把“档案生成”写成“模组兼容”。
```

### 8.2 回归测试矩阵

```text
请为本次变更建立回归矩阵，列出受影响入口和最低必要场景：
入口识别、对象发现、建造/生成、资源收支、可见动作、隐藏动作、标签/内存状态、地图、音频/图像、本地化、销毁/转换、重新加载。

每格填：未执行、静态通过、模拟器观察、目标引擎通过、失败或阻断，并附证据。不要用一格“启动成功”覆盖其他格。
```

### 8.3 版本迁移剧本

```text
这是版本迁移，不是全局替换。先读取目标版本原始加载器、现有项目入口和受影响语法；把每个字段分为已证实等价、可能等价、未知和已知不等价。

先挑一个最小机制做双版本对照，记录文本 diff、解析日志、资产、地图和动作结果。保持旧版本副本不变。未能证明等价的字段用兼容层或实验夹具隔离，不批量改写。

最终报告包含：迁移规则来源、变更路径、已测功能、未测功能、版本漂移风险和回滚方法。不能因为目标版本号更高就声称旧字段仍兼容。
```

## 9. 无引擎访问变体

### 9.1 统一无引擎前置语

```text
当前没有可用的目标 Rusted Warfare 引擎，禁止输出运行时通过、游戏内可见、音频可播放、地图可进入或性能改善等结论。
请把任务改写为静态可证明目标：路径闭包、段落索引、继承图、引用图、资源存在性、入口候选、重复/冲突检测、编码和打包结构。
每个结论标记 E0-E3 静态证据等级，并生成一份 E4 所需的最小运行测试计划。
```

### 9.2 无引擎调试单位不出现

代理可以完成：验证档案可读、枚举候选根、找到 manifest 候选、定位配置文件、建立模板和入口引用边、检查资源路径、列出条件表达式和未知字段。代理不能完成：证明引擎注册、建造按钮出现、单位渲染、动画、AI、动作顺序、多人同步和性能。

交付应使用“静态可达性”一词。例如：“从候选入口到定义文件的文本引用边存在，直接模板路径可解析，图像文件存在；由于没有目标引擎，无法证明对象被注册或在 UI 中显示。”这句话比“单位没有问题”更可靠。

### 9.3 无引擎打包检查

即使没有引擎，也可以执行：输出档案条目清单、重新解包、候选根比较、入口识别、路径大小写检查、文本编码检查、模板循环检测、静态资产存在性和变化前后清单差异。输出仍须写明这些是包结构证据，不能代替真实加载。

## 10. 提示词中的常见失败和修正

| 失败提示 | 为什么危险 | 修正提示 |
| --- | --- | --- |
| “把这个模组修到能运行” | 目标版本、范围和行为没有定义 | 先列入口、版本、最小复现和验收格 |
| “扫描所有单位” | 把单位等同于固定目录 | 递归扫描配置、模板、机制、事件和资产，并分类 |
| “自动整理配置” | 可能改变继承和段落语义 | 只做白名单字段的精确修改，保留声明顺序 |
| “找到问题就修” | 会越过未知语义和权限边界 | 先报告证据、最小复现和待确认点 |
| “看起来是旧版，升级到新版” | 版本字段与目录和引擎可能冲突 | 按字段建立版本映射和对照测试 |
| “删掉无用文件” | 动态引用和历史依赖不可见 | 先生成无入边证据，单独申请删除 |
| “模拟器显示空白” | 模拟器覆盖不完整 | 写模拟器局限，转为静态证据和真实引擎测试计划 |
| “manifest 不见了” | 工具可能未识别包装根或变体 | 先列候选根并报告识别规则 |
| “全部测试通过” | 一次启动不能覆盖功能 | 逐格填写回归矩阵并附日志/观察 |


### 11.2 审查型任务


### 11.3 “没有发现问题”的最低标准

不能只写“未发现问题”。至少要说明读取了哪些文件、扫描了哪些引用、检查了哪些入口、执行了哪些静态/运行命令、哪些功能未覆盖以及为何不能证明。没有引擎时尤其要写清“未发现静态断链”而非“运行正常”。

## 12. 安全和协作边界

多个代理共享工作区时，提示词必须要求先读工作区状态，区分自己创建的变更和协作者变更。代理不得用重置、回滚、覆盖写、批量格式化或清理命令消灭他人工作。写入前检查白名单，写入后检查文件集合。外部源根始终只读，复制到隔离目录才可实验。

在任务完成前，代理应确认：新文件确实是任务要求的文件；没有修改 README、技能入口、脚本或外部源；临时输出不在源码树；测试生成物未污染工作区。若发现不属于本任务的变更，保留并在报告中指出，不擅自恢复。

- [ ] 已搜索入口、模板、继承、段落、动作、标签、资源、地图、音乐和本地化引用。

## 14. 收束

高质量提示词不是把任务描述得更长，而是把代理必须经过的证据门槛写得更具体。对 Rusted Warfare 模组，最重要的门槛是：真实加载根是什么，入口如何发现，模板如何继承，段落如何合并，状态如何写读清理，资产如何在打包后可达，目标版本如何解释字段，当前有没有引擎证据。只要这些问题被逐项记录，代理即使无法完成运行验证，也能交付有用且诚实的静态结果；若可以运行，则能把测试集中在影响最大的功能，而不是用一次启动成功掩盖大量未知。

## 15. 多代理协作交接剧本

共享工作区中的代理不能假设自己是唯一写作者。交接提示必须包含工作区状态、自己拥有的文件白名单、已读路径、未处理问题和验证结果。下一代理应先读取交接，再读取实际文件和版本控制状态，确认内容没有在等待期间改变；若发生变化，以当前文件和最新用户要求为准，不用旧 diff 覆盖新工作。

### 15.1 交接模板

```text
交接任务：<名称>
当前工作根：<绝对路径>
我只修改了：<绝对路径列表>
我只读了：<来源列表>
已完成：<事实>
未完成：<事项>
关键假设：<每条带证据等级>
已知冲突：<路径、版本、语义>
验证命令和结果：<实际内容>
下一代理必须先读：<文件>
禁止：<外部目录、他人文件、删除/重排范围>
```

交接内容不应只写“基本完成”。它要让下一代理知道哪些结论是 P1/P2，哪些是 P4，哪些命令没有执行。尤其要把“没有发现”改写成带范围的负面结论，避免下一代理重复同一误读。

### 15.2 并行任务边界

可并行的任务应按文件或只读分析边界划分：一个代理读取案例树，另一个统计档案，另一个审查提示词；写入时每个代理只负责白名单文件。不能让两个代理同时改同一个 Markdown 章节，也不能把“只读外部源”理解成可以在那里生成索引或临时解压。临时输出放在隔离目录，并在交付中说明其位置。

如果任务必须修改同一个文件，先由一个代理完成读取和编辑，再由下一代理以新状态为基线做精确编辑。禁止用整文件覆盖解决冲突，因为这会删除协作者刚加入的章节、统计或勘误。

## 16. 工作流：从接单到可复核交付

这里的“工作流”不是泛泛的项目管理词，而是代理执行 Rusted Warfare 模组任务时必须经过的一组证据门。它把读文件、确定范围、分析依赖、实施最小修改、验证结果和交接责任连接起来。任何一步缺失，都可能让一个局部正确的文本改动在错误的加载根、错误的版本或未覆盖的运行时语义中失去意义。

### 16.1 工作流阶段图

```text
接单
  -> 锁定工作根/版本/白名单
  -> 读取入口与相关上下文
  -> 建立路径、模板、状态和资产证据
  -> 评估影响半径与停止条件
  -> 写入最小 diff
  -> 静态检查与打包检查
  -> 目标引擎测试或无引擎降级
  -> 报告事实、结果、缺口
  -> 交接/回归/勘误
```

每个箭头都应有可观察产物。接单阶段产出任务卡；读取阶段产出实际路径列表；分析阶段产出引用或状态表；实施阶段产出精确 diff；验证阶段产出命令和结果；交付阶段产出 provenance 和未覆盖项。不能用“最后统一总结”替代中间证据，因为代理一旦在早期误判根布局，后面的漂亮报告也会建立在错误输入上。

### 16.2 接单门

代理先确认任务属于新建、修改、审查、调试、性能、打包、测试或迁移中的哪一类。若一个请求同时包含多类操作，拆成编号子任务，分别写白名单和验收条件。确认工作根是解包目录、`.rwmod` 还是项目源；确认外部来源是否只读；确认目标版本是 1.14、1.15、具体补丁还是未知。

接单门还要问“什么算完成”。例如“单位不出现”可能需要静态入口分析、目标版本运行日志或两者；“整理目录”可能只允许生成索引，不允许移动；“兼容性扫描”可能要求 48 个样本全部入表，而不是抽查几个。完成标准不清时，代理只应请求最小澄清，不应自行选择高风险解释。

### 16.3 阅读门

阅读门要求先读任务相关文件、相邻模板、入口和直接引用者，并在报告中列出实际读取路径。搜索命中不能替代读取；读到一行也不能假装理解整份文件。对于大型文件，代理应说明读取的行区间和为何足以支撑当前结论。

阅读时同时检查协作工作区状态，识别已有变更。若目标文件在等待期间变化，重新以当前内容为基线；不使用旧的整文件快照覆盖新内容。外部源码根保持只读，实验副本与生产路径分开。

### 16.4 建模门

建模门把文本变成四种可审阅对象：路径图、继承图、状态图和资产图。路径图说明入口、包装层和相对根；继承图说明 `copyFrom`、段落复制和覆盖候选；状态图说明动作、标签、资源、内存和事件的写读清理；资产图说明配置、地图、音乐、图片和本地化引用。

不要求代理一次理解所有字段，但要求它标记未知。若字段无法按目标版本解析，就把它放到“原始声明/静态候选/待验证”表中。建模门的目标不是创造一个看似完整的模拟器，而是让风险和下一条证据需求可定位。

### 16.5 变更门

变更门检查任务是否真的需要写入。如果只需要审查或清单，不写文件；如果需要修改，只改白名单和最小闭包。涉及共享模板、全局状态、入口、版本字段、包装根或批量资产重命名时，自动升级影响分析和回归范围。

变更前写下行为假设和停止条件，变更后重新读取 diff 上下文并搜索受影响引用。不要因为变更内容是 Markdown 就忽略验证：导航链接、版本说明、限制措辞和统计数字都可能影响后续代理的判断。

### 16.6 验证门

验证门按证据等级分层。先执行文本/路径/引用的静态检查，再执行成品重新解包检查，最后才是目标引擎。每个通过只能填对应格：静态通过不填运行通过；档案可读取不填入口可载入；进入地图不填事件、动作和音频全覆盖。

无引擎时，验证门不可跳过，而是转换为静态交付和 E4 测试计划。计划应包含档案、候选根、客户端版本、场景、操作、预期观察和日志位置。这样下一代理获得引擎后可以直接复跑，而不必重新猜测你的假设。

### 16.7 交付门

交付门要求报告回答五件事：改了什么，依据什么，实际运行了什么，发现了什么，仍不知道什么。事实和推断分段；聚合统计带分母和规则版本；启发式命中带上下文敏感限制；没有运行时证据就明确写未执行。

交付前检查只修改了任务文件，临时产物没有污染源码树，外部根没有被写入，协作者变更没有被覆盖。交接时附上任务卡、实际读取路径、精确 diff、验证命令、结果和下一步最小证据。

### 16.8 工作流异常处理

工作流不应遇到错误就自动重试到成功。解包失败先区分工具、权限、损坏和格式；入口缺失先区分候选根、manifest 识别和旧式内容；模板冲突先保留顺序和段落；运行空白先区分模拟器覆盖和引擎行为。每次异常只改变一个诊断变量，并记录前后结果。

如果异常涉及外部源码、他人变更、删除文件、版本漂移或未知动作语义，暂停并请求证据。高质量工作流的停止动作不是失败，而是保护结论免于超过证据范围。

### 16.9 工作流快速核对表

- [ ] 接单时已定义根、版本、白名单、只读边界和完成标准。
- [ ] 先读了实际文件，并记录入口、模板、引用者和协作状态。
- [ ] 已建立所需的路径图、继承图、状态图或资产图。
- [ ] 未知语义、动态引用和启发式命中没有被伪装成确定结论。
- [ ] 写入前有最小 diff 计划，写入后有引用反查。
- [ ] 已分开执行静态、成品档案和目标引擎验证。
- [ ] 无引擎时提供 E4 测试计划，不写虚假的运行通过。
- [ ] 交付包含事实、来源、命令、实际结果、缺口和回滚/交接信息。

## 17. 提示词质量检查

提示词本身也需要审查。一个可用提示词应能回答：代理要先读什么，哪些文件可改，证据从哪里来，遇到未知怎么办，如何验证，如何报告未覆盖。下面的检查表可作为发布前门槛：

- [ ] 是否明确绝对工作根和外部只读根？
- [ ] 是否明确目标版本，或明确版本未知时的停顿策略？
- [ ] 是否要求先读文件并列出实际读取路径？
- [ ] 是否规定不以目录名、文件名或相邻版本常识替代语义证据？
- [ ] 是否要求显式记录模板、段落、动作、状态和资产引用？
- [ ] 是否要求最小 diff，不做无关格式化、重命名和清理？
- [ ] 是否有无引擎变体，且禁止虚构运行结论？
- [ ] 是否有真实命令、实际结果、回滚方式和未覆盖范围？
- [ ] 是否定义多代理交接和工作区冲突处理？
- [ ] 是否把静态启发式命中和引擎不兼容分开？

如果提示词不能让代理回答这些问题，就算措辞再专业也不够安全。优先补充停止条件和交付格式，而不是继续增加术语。

## 17. 任务完成的证据包

对于有影响的任务，建议代理交付一个小型证据包而不是只有口头摘要。证据包可包含：精确 diff、读取文件清单、静态检查输出摘要、打包前后条目差异、目标引擎日志或“未执行”声明、回归矩阵、未解析路径清单和 provenance。不要把第三方完整配置、媒体或受保护反编译复制进证据包；保留必要的路径、短键名和新写的抽象片段即可。

证据包的每一项都有范围。例如一张截图只能证明某个客户端和场景在某时刻的画面；一份档案清单只能证明条目存在；一次静态搜索只能证明当前规则命中。代理报告应在证据旁写“支持什么”和“不支持什么”，使审阅者不必猜。

## 18. 何时把任务从修改升级为审查

修改任务一旦触及共享模板、全局状态、全量入口、地图/音乐路径、打包根、版本字段或多重继承，就不再是单字段修改。提示词应自动升级为审查模式，增加影响半径、回归矩阵、回滚和运行测试计划。这样不会阻止小修复，只是防止一个看似简单的替换改变整个内容库。

升级信号包括：修改者无法说明字段来源；同一字段在祖先链重复；动作有多个触发源；资源名在多个领域出现；路径跨包装层；变更会影响超过一个入口；目标版本未知；或检查器报告上下文敏感启发式命中。代理可先给出分析，不应在用户未授权的情况下批量推进。
