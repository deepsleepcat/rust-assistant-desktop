# 证据、权威与版本边界

导航：先阅读 `../SKILL.md` 的任务入口；模组识别与封包见 [01-mod-discovery-rwmod-and-metadata.md](01-mod-discovery-rwmod-and-metadata.md)，解析和继承见 [02-ini-parser-templates-and-inheritance.md](02-ini-parser-templates-and-inheritance.md)，单位字段的定位方法见 [03-unit-architecture-and-field-catalog-routing.md](03-unit-architecture-and-field-catalog-routing.md)。

本参考面向需要生成、修改、审阅或诊断 Rusted Warfare 自定义单位模组的编码代理，范围锁定在游戏 `1.14` 与 `1.15` 线。目标不是把零散教程拼成“看起来能用”的语法表，而是让每一次改动都能回答五个问题：结论来自哪里、覆盖哪个版本、是否已经由引擎行为证实、是否依赖外部条件、还有哪些未知量。

本技能的核心约束是：**运行时语义由原始反编译引擎材料裁决；可读说明只帮助定位，不推翻引擎。** 一项字段即使在旧教程、模组样例或字段目录里出现，只要在当前目标版本的引擎路径中找不到对应解析或使用链路，就不能把它写成已证实的兼容特性。

## 1. 使用前的证据纪律

将一次模组任务拆成可验证断言，而不是笼统地说“支持某字段”。例如：

| 断言 | 合格证据 | 不合格证据 |
|---|---|---|
| `[mod]` 的显示名读取 `title` | 元数据读取路径明确取该键 | 某教程把 `name` 写在示例里 |
| 两个 `copyFrom` 父文件的优先级 | 引擎对列表反转、递归和合并的顺序 | 根据文件名推测先后 |
| `ROOT:` 从哪里解析 | 路径分支和调用上下文 | Windows 目录层级的直觉 |
| 一个字段可以用于 1.15p11 | 目标版本实现和版本守卫 | 其他模组“似乎能加载” |
| 一个错误是解析错误还是运行期行为 | 日志阶段、加载生命周期和最小复现 | 只看游戏界面缺少现象 |

编码代理在动笔前应记录：目标游戏版本、目标平台或运行器、模组是目录还是 `.rwmod`、问题是加载失败还是行为异常、可用本地证据的路径、用户是否指定必须兼容的旧版。未记录的版本不得被悄悄假定为“最新”。

### 强制规则

1. 不把“字段表中存在”当作运行时保证。字段表是导航索引，精确拼写、默认值、排斥关系和版本门槛必须二次核对。
2. 不把实例模组的写法反向当成规范。实例可能依赖旧版宽容解析、私有前置资源、未启用的文件，或者包含未被读取的键。
3. 不从反编译材料直接搬运大段源码、类内容或配置原文到对外发布物。它们只用于内部行为研究和可审计的摘要。
4. 不把反编译符号名当作稳定公开 API 名。说明“哪个路径解析了什么”，不要承诺混淆或反混淆名称在其他构建中相同。
5. 当证据只覆盖 1.14 或只覆盖 1.15 时，显式标记覆盖范围；不得把单点证据扩展成整个版本带。
6. 只有在用户明确批准时，才把兼容性基线提高到会排除其旧版本用户的版本。否则维持用户指定基线并说明无法安全使用的特性。
7. 所有路径、键名、区段名和资源标识均按引擎语义处理，不按宿主系统“自动纠正”的习惯处理。
8. 对修改作出最小可验证假设。不要同时改字段名、模板链、资源路径和版本门槛，否则失败后无法归因。

### 冲突裁决表

| 冲突情形 | 处理结果 | 记录方式 |
|---|---|---|
| 原始引擎与加载器注释不一致 | 采用原始引擎行为 | 标明“已由原始实现覆盖旧摘要” |
| 字段目录有键、引擎读取链未找到 | 不承诺支持；继续检索或标为未证实 | 写明已查范围和缺口 |
| 深渊系列样例与引擎不同 | 不复制样例语义，优先引擎 | 只把样例列为复现线索 |
| 不同引擎版本表现不同 | 以用户指定版本为准，分版本陈述 | 用版本矩阵而非笼统“支持” |
| 反编译难以判定控制流 | 降级为待验证假设，构造最小测试 | 标记 `待运行验证` |
| 用户要求与引擎边界冲突 | 说明不可能或需提高最低版本 | 不伪造兼容实现 |

冲突不是文档质量问题，而是任务事实的一部分。应保留冲突本身：例如“字段目录或旧说明写 `name`，但目标运行时读取 `title`”。这种记录比“统一改成看起来常见的键”更有价值，因为它防止后续代理重新引入已排除的错误。

## 3. 证据标签与结论强度

每一个非平凡结论使用下列标签之一。标签应出现在任务笔记、审阅说明或生成注释中；无需塞进最终给玩家的模组说明。

| 标签 | 含义 | 可以执行的动作 |
|---|---|---|
| `已证实` | 目标版本或直接相邻实现中可追踪到读取与作用 | 可据此改配置，并附路径证据 |
| `跨版本已证实` | 至少在目标范围两端或明确兼容分支中行为一致 | 可作为 1.14/1.15 共用规则 |
| `版本限定` | 只证实某个精确版本、构建号或版本线 | 只在对应条件满足时使用 |
| `样例观察` | 在本地实例中看见，但未证明为引擎规则 | 仅用于提出检索或测试假设 |
| `待核查` | 字段目录或用户描述提出，尚未找到权威链路 | 不应写进生产配置 |
| `待运行验证` | 静态实现可推断，但资源、平台或时序仍可能改变结果 | 可做隔离试验，不能声称已验证 |
| `不兼容` | 目标版本明确拒绝或缺少所需前提 | 提供替代方案或要求升版 |
| `已弃用或遗留` | 可被部分旧版接受，但当前路径不建议依赖 | 迁移时替换；保持时单独标注风险 |

不要用“可能”“应该”“大概”替代标签。自然语言的模糊性会在自动化编辑中放大：代理可能把“可能支持”变成生产字段。正确做法是把未知点转换为一个可检索问题，例如“内存数组在 1.15p11 前是否有解析分支”，并在没找到分支前阻止写入。

## 4. 版本模型：从用户请求到 `minVersion`

Rusted Warfare 的版本字符串不是可随意比较的普通文本。元数据 `minVersion` 会被规范化并与当前游戏构建进行比较；版本解析接受特定的 `v`、`a` 到 `h`、以及 `p` 变体。错误格式、过低基线或要求高于当前游戏的版本都可能在元数据加载阶段被拒绝。不要使用字符串排序，例如把 `1.15p2` 与 `1.15p11` 按字符比较会得出错误结果。

### 用户指定版本的处理算法

1. 提取用户显式约束。区分“仅在 1.15p11 测试”“需兼容 1.14 与 1.15”“服务器固定 1.15p11”和“玩家大多使用 1.15”这四种不同陈述。
2. 若用户给出精确构建，精确构建就是基线；不因字段看似老旧而降级，也不因开发机较新而悄悄升版。
3. 若用户给出范围，采用范围的最低端作为默认配置基线。需要较新特性时，列出两条分支：保守替代和提高 `minVersion` 的实现。
4. 若用户未给版本，询问一次；若任务必须继续，默认声明“目标为 1.15 系列，未承诺 1.14 兼容”，并避免仅在已知后期构建才存在的能力。
5. 若使用单位内存数组，要求 `minVersion: 1.15p11` 或更高。不能以“玩家大概够新”替代这个门槛。
6. 修改 `minVersion` 前检查整包实际依赖，而不仅是本次新增字段。较低声明会允许游戏进入后续解析，再以难读错误失败；较高声明会无谓拒绝原本可运行的客户端。
7. 在交付说明中报告声明版本、测试版本和推定可兼容版本。三者不相同也要分别写清。

### 版本决策矩阵

| 需求 | 推荐声明 | 实施策略 | 审阅重点 |
|---|---|---|---|
| 只修文本、图片路径、既有字段值 | 保持现有声明 | 不因无关改动提高门槛 | 检查现有包的真实依赖是否已高于声明 |
| 新单位只用双方均已证实的核心能力 | 用户要求的最低版本 | 优先保守字段组合 | 在 1.14 与 1.15 分别加载 |
| 用到已确认的 1.15 特性 | 至少 `1.15` 的适当变体 | 明确放弃 1.14，文档说明原因 | 旧客户端能否给出可理解的版本拒绝 |
| 用到内存数组 | `1.15p11` | 统一把相关动作和逻辑限制在该基线 | 声明、服务器与测试客户端一致 |
| 维护未知旧模组 | 暂不猜测 | 先建立字段与版本证据清单 | 禁止“为了加载成功”批量删键 |

### 版本声明示例

以下是结构示意，不是可复制的完整模组文件：

```ini
[mod]
title: 轨道试验单元
minVersion: 1.15p11
description: 使用需要后期构建的内存数组\n不承诺 1.14 兼容
```

此例中的换行是元数据描述中的两个字面字符 `\` 与 `n`；读取后显示为实际换行。`title` 是展示字段；写成 `name` 不能满足当前运行时的显示名读取。不要因为一些旧说明使用 `name` 就同时写两个键来“兼容”，除非已查明额外键会被忽略且不会触发未使用键诊断；元数据与单位 INI 的容错规则不应混为一谈。

## 5. 版本兼容性不是单一开关

一次成功加载仅证明“该客户端在该时刻接受了该包”，没有证明网络对战、存档恢复、不同平台文件系统或资源压缩读取都兼容。对编码代理而言，至少区分五层：

| 层 | 要问的问题 | 常见误判 |
|---|---|---|
| 元数据层 | `minVersion` 能否被当前游戏接受 | 把显示标题正常误当成版本通过 |
| 解析层 | 所有 INI 键、区段、模板和路径是否完成读取 | 只检查首个单位，没有遍历递归目录 |
| 构造层 | 单位、炮塔、动作、资源引用是否能完成交叉解析 | 静态文本无错误却在引用解析时报错 |
| 运行层 | 触发、AI、投射物、图像和生命周期是否实际工作 | 只在编辑器预览而未进入战局 |
| 联机层 | 两端模组识别和数据是否一致 | 认为单机加载等于联机一致 |

每层有不同的最小测试。元数据层只需启用状态和版本报告；解析层需要重新扫描全部单位目录；构造层需要打开包含每个单位类型的场景；运行层需要触发关键路径；联机层需要双方包内容、启用状态和版本一致。不要用高成本联机测试替代基础解析诊断，也不要在解析失败时从玩法平衡入手。

### 兼容性声明的推荐句式

| 实际证据 | 可以写 | 不应写 |
|---|---|---|
| 只在 1.15p11 单机加载 | “已在 1.15p11 单机解析与运行检查。” | “全面兼容 1.15。” |
| 1.14 与 1.15 分别完成同一测试 | “已在 1.14 和 1.15 的该测试路径复核。” | “兼容全部旧版。” |
| 只知道字段要求后期版本 | “该实现要求至少 1.15p11。” | “所有玩家均可使用。” |
| 尚未联机 | “联机一致性未验证。” | “多人无问题。” |

## 6. 内部材料的使用边界

`W:\mao\tx\tools\decompilers\game-lib-src` 和可读加载器材料用于内部研究。输出到模组、公开文档、提交说明或聊天答复时，应该产出**行为摘要、文件路径、版本范围、测试方法和最小自写示例**，而不是转载反编译源码、长方法片段、类成员表或原始第三方配置。

允许的写法：

- “内部引擎元数据读取路径表明 `[mod]` 使用 `title`。”
- “单位加载路径对 `copyFrom` 列表先反转再合并，因此右侧父项先填充，左侧父项在缺失键上更接近子文件。”
- “压缩包虚拟文件系统会在单一包装目录情形下把内层暴露为根目录，仍应把归档结构做成扁平根目录以降低歧义。”
- “内存数组需要较新的构建门槛，应让 `minVersion` 反映这项真实依赖。”

不允许的写法：

- 整段反编译方法、完整类、可重建实现的连续源码摘录。
- 从 DeepStar 或兼容性实例复制完整单位、完整模板或大量资源清单。
- 通过模糊改名掩盖来源后把第三方配置当作自创内容。
- 使用“官方源码”字样暗示材料可公开再分发；本技能仅称其为内部反编译研究材料。

如果用户直接要求提供或复制这些内部材料，暂停该部分请求，改为提供功能层级的解释、检索建议或自写最小示例。不要把“已经在本机”误解为“可再发布”。

## 7. 事实、推论与建议必须分层

好的技能文档不把三种句子混在一起：

| 类型 | 示例表达 | 证据要求 |
|---|---|---|
| 事实 | “读取元数据时展示字段是 `title`。” | 直接行为路径 |
| 推论 | “因此将 `name` 作为唯一展示键会造成名称缺失或回退。” | 事实加调用语境 |
| 建议 | “创建新包时统一使用 `title`，并在自动检查中验证该键。” | 面向工程稳定性的选择 |

事实可以在版本范围内强断言；推论必须说明前提；建议可以权衡维护成本，但不能伪装为引擎硬规则。比如“将所有素材文件名改为小写”是良好跨平台建议，不等于引擎对目录包处处严格区分大小写；“不要用多层包装目录”是交付建议，不等于引擎永远无法下钻发现元数据。

### 反例审阅

当看到下列句子时，代理应改写或要求证据：

| 原句 | 问题 | 改写方向 |
|---|---|---|
| “这个键在所有版本都能用。” | 没有版本边界和证据路径 | 指定证实的版本与阶段 |
| “样例模组用了，所以可用。” | 样例不能说明解析器接受或消费 | 检索读取链或做最小试验 |
| “把最低版本设低一点兼容更多人。” | 会把失败推迟到解析或运行期 | 让声明匹配真实依赖 |
| “报错说明素材坏了。” | 错误阶段未定位 | 先区分元数据、路径、INI、构造和运行 |
| “旧教程与源码冲突，折中保留两个键。” | 回避裁决，可能造成未使用键错误 | 明确采用高权重来源的行为 |

## 8. 调查工作流

下面的流程适用于新增字段、修复加载错误、解释旧模组、审阅外来补丁和写自动化转换器。

### 第一步：界定问题

记录原始报错、文件相对路径、游戏版本、是否为 `.rwmod`、是否只在特定平台复现、是否禁用或启用状态导致。保留完整错误文本，但不要把它与猜测混在同一行。若用户只给截图，先要求可搜索的错误文本或用最小文件复现。

### 第二步：从字段目录建立检索词

在 `assets/ai/references/rusted-warfare-modding.md` 查字段的精确大小写、所属区段、相近前缀和可能关联对象。例如一个炮塔问题至少联查 `[attack]`、`[turret_*]`、`[projectile_*]`、动作触发和资源引用。目录用于缩小搜索空间，不是停止点。

### 第三步：在原始引擎追踪三件事

1. 键是否被读取，读取类型是什么，默认值和必填性如何。
2. 读取结果在何时被验证、是否会被后续阶段覆写或归一化。
3. 引擎是否在运行期真正消费该值，还是仅保留为过渡或遗留数据。

对于路径、压缩包、模板、版本和重复键，尤其要寻找异常分支和边界值，而非只看正常分支。大量模组故障恰好发生在“找不到文件”“循环深度超限”“键未消费”“版本不足”这些分支。

### 第四步：选择最低风险实现

优先选择在用户基线中 `已证实` 的写法。若存在两种等价设计，选择依赖更少隐式继承、路径更短、版本要求更低且最容易做最小复现的方案。只有当性能、功能或用户明确需求足以抵消维护成本时，才引入复杂模板链、动态逻辑或后期构建特性。

### 第五步：留下可复核的变更说明

每个非直观改动至少说明：改了什么、适用版本、依赖哪个行为、如何验证、还有什么未验证。不要写“修复兼容性”这类无对象陈述；应该写“将错误的展示键替换为 `title`，因为当前元数据读取路径只取 `title`；在目标构建的模组列表中检查展示名”。

## 9. 溯源审计清单

提交、交付或交给下一代理前，逐项检查：

- [ ] 任务有明确的游戏版本、构建号或已说明的未知版本策略。
- [ ] 每个新增的高风险字段都在字段目录和原始引擎材料中交叉检查过。
- [ ] 任何与可读加载器摘要冲突的地方，均采用了原始引擎结论并记录冲突。
- [ ] 没有从 `game-lib-src`、`模组加载器`、DeepStar 模组或 `模组实例` 复制完整源码或完整配置段。
- [ ] 引用本地证据时只给出必要路径和行为摘要，不泄漏长源码片段。
- [ ] 所有版本限定特性都与 `minVersion` 一致，特别是内存数组要求 `1.15p11`。
- [ ] “兼容”一词指出了具体层级：元数据、解析、构造、运行还是联机。
- [ ] 不确定项使用 `待核查` 或 `待运行验证`，没有被包装成确定承诺。
- [ ] 生成的自写示例足够小，且不含第三方资源名、长配置或版权性内容。
- [ ] 修改说明含测试入口与失败回退方案，而非只含结论。

## 10. 面向代理的交付模板

在需要汇报证据的任务中，可使用下面的紧凑结构：

```text
目标版本：1.15p11（用户指定）
结论：已证实。元数据展示名应使用 [mod] title。
证据：内部引擎元数据读取路径；可读加载器摘要仅作定位。
改动：将错误的展示键替换为 title，保留描述中的字面 \n。
验证：重新扫描并在模组列表检查名称、描述换行和版本门槛。
风险：未在 1.14 运行；不宣称向下兼容。
```

该模板刻意把“结论”“证据”“改动”“验证”“风险”拆开。任何一项空缺都不是用更长的解释填补，而是下一步调查工作。对 Rusted Warfare 模组而言，可审计的保守结论通常比无法复现的万能字段清单更有工程价值。

## 11. 证据笔记的最小数据模型

复杂任务不要把调查结果散落在聊天记录、临时注释和提交消息中。即使不创建额外文件，也应在当前任务说明或交付记录中保留结构化条目。一个断言一条记录，避免一个段落同时描述五个相互独立的行为。

| 字段 | 必填 | 内容 | 示例写法 |
|---|---|---|---|
| 断言编号 | 是 | 稳定、简短的追踪标识 | `META-TITLE-01` |
| 断言 | 是 | 可证伪的行为句 | “展示名读取 `[mod] title`。” |
| 目标范围 | 是 | 游戏版本、构建、平台和包形态 | “1.15p11，Windows，目录版与 rwmod” |
| 证据等级 | 是 | 本页定义的标签 | `已证实` |
| 主证据 | 是 | 内部路径和行为位置摘要 | “元数据读取路径取得 title” |
| 辅助证据 | 否 | 目录、可读摘要或最小试验 | “字段目录仅用于定位” |
| 反证或冲突 | 否 | 被排除的旧说法和原因 | “旧摘要写 name，已被原始行为覆盖” |
| 实施影响 | 是 | 改配置、拒绝需求或需提高版本 | “生成器必须输出 title” |
| 验证方法 | 是 | 最小可重复观察 | “模组列表检查标题” |
| 未覆盖条件 | 是 | 平台、联机、构建或状态缺口 | “未在 1.14 测试” |
| 维护触发器 | 否 | 何时需要重新核对 | “升级目标游戏构建时” |

这种数据模型的重点不是形式化文档，而是防止“证据来源”和“结论范围”脱节。比如主证据只证明 Windows 目录版读取路径，却把结论写成“所有平台压缩包均兼容”，记录中的目标范围和未覆盖条件会立刻暴露这个跳跃。

### 一条记录只说一个行为

下面是错误的合并记录：

```text
1.15 兼容：标题、压缩包、模板和内存都可以。
```

它无法审阅，因为四个行为分别由不同组件、版本门槛和运行阶段决定。应拆为：元数据标题读取、ZIP 根透明化、模板合并顺序、内存数组版本守卫。拆分后可以让其中三项已证实、一项待运行验证，而不必把整条结论降成含混的“可能”。

### 证据链的最短充分长度

并非每项都需要阅读整个引擎。高效调查应找到最短但足够的链：

```text
配置键或文件位置
  -> 读取/枚举点
    -> 校验、转换或合并点
      -> 可观察结果或运行消费者
```

例如元数据标题只需证明 `[mod]` 读取了 `title`，再在模组列表验证结果；无需为了这个问题追踪每个单位构造方法。反过来，投射物伤害不能只找到字段读取点，因为还需要知道其运行期命中消费者和与范围伤害、友伤或 mutator 的组合条件。调查范围必须与断言风险相称。

## 12. 版本实验矩阵与最小复现

静态阅读不能覆盖所有版本差异。对于版本限定或疑似版本限定行为，应建立一个小型矩阵，而不是在一个成功客户端上得出广泛结论。矩阵的行是版本，列是同一个最小断言；每格只记录可观察结果和错误阶段。

| 测试项 | 1.14 | 1.15 | 1.15p11 | 结论写法 |
|---|---|---|---|---|
| `title` 显示 | 待测/结果 | 待测/结果 | 待测/结果 | 仅概括实际完成的格 |
| 普通 `copyFrom` | 待测/结果 | 待测/结果 | 待测/结果 | 区分解析与最终值 |
| 内存数组 | 不应假定 | 不应假定 | 必须验证 | 至少要求 p11 |
| `.rwmod` 逻辑根 | 待测/结果 | 待测/结果 | 待测/结果 | 不把目录版结论外推 |
| 特定遗留字段 | 待测/结果 | 待测/结果 | 待测/结果 | 只对实际构建下结论 |

“待测”不是失败，也不是通过。它只是阻止代理在没有证据时作出承诺。若用户只关心一个构建，矩阵可只留一行，但仍要把其他版本明确写作未覆盖。

### 最小复现包的原则

最小复现不是从第三方模组裁剪一个单位，而是以自写、低依赖结构隔离一个断言：

1. 只保留一份元数据和一个需要的单位或资源对象。
2. 不用外部图片时，先验证文本和加载阶段；图片问题另建一个最小资源复现。
3. 不让模板、动作、AI、地图、联机同时参与，除非被验证的正是它们的交互。
4. 用唯一但简单的内部名，避免与安装的其他模组同名。
5. 每次只改变一个变量，例如把 `minVersion` 从普通 1.15 改到 `1.15p11`，而不同时改字段语法。
6. 记录目录版和归档版是否分别复现，避免打包形态混入结论。
7. 测试结束后不把最小复现中的临时文件、内部路径或限制材料打进发布包。

最小复现的输出应包括“预期现象”“实际现象”“游戏版本”“包形态”“完整错误文本或截图位置”。不要只写“失败”，因为同一字段可能在元数据、INI、对象引用或运行期以不同方式失败。

### 版本回归的触发条件

出现以下情况必须重新验证先前结论：

- 用户把目标从 1.15 改为 1.14，或从一个 `p` 构建改为另一个构建。
- 引入或删除内存数组、复杂 LogicBoolean、`CORE:` 依赖、动态动作或遗留字段。
- 目录版转为 `.rwmod`，或改变归档根和包装层。
- 模板链、单位内部名、资源域或对象引用进行了跨文件重组。
- 服务器和客户端实际版本不再一致，或要求联机支持。
- 原始引擎材料或本地字段目录更新，且涉及的字段有版本变化迹象。

不要因为“只是重命名文件”就跳过重验：路径名与 ZIP 虚拟文件系统、大小写和包装根直接相关，属于加载边界的一部分。

## 13. 从冲突报告到可执行决策

发现冲突时，代理不应仅写“资料不一致”。有效的冲突报告至少包含候选说法、各自来源、适用范围、验证计划和暂定实现。下面的表可用于每个争议点：

| 项目 | 说法 A | 说法 B | 裁决或下一步 |
|---|---|---|---|
| 元数据名称 | 旧说明称 `name` | 运行时读取 `title` | 使用 `title`；旧说明降权 |
| ZIP 包装根 | 样例带顶层目录 | 虚拟根可透明呈现 | 仍按扁平根发布，透明行为只作兼容观察 |
| 字段拼写 | 字段表列出候选 | 引擎未找到当前读取 | 标为待核查，不写生产包 |
| 旧动画 | 实例仍在用 | 当前路径标遗留或替代 | 维护时最小改动，新内容不新增 |
| 版本需求 | 用户希望 1.14 | 所需能力要求 p11 | 提供无数组替代或说明不能兼容 |

### 冲突裁决的禁止行为

- 不将两个冲突键同时写入配置，以为“总有一个会被读取”。这常制造未使用键、误导维护者或把错误推迟到运行期。
- 不以第三方样例的规模、作者声望或下载量提升其证据等级。样例只说明某个包曾采用该写法。
- 不以本机“没有明显报错”覆盖版本实现差异。可能未走到相关分支，或被缓存、模板和容错层掩盖。
- 不为结束讨论而把断言写成过度宽泛的“不同版本可能不同”。应具体指出哪个版本、哪个构建、哪个阶段未知。
- 不把阅读困难当作允许臆测的理由。反编译不清晰时，缩小断言、建立最小试验或请求用户指定验证环境。

### 当用户需要立即结果

有时用户要求快速修复，无法完成全矩阵。此时仍可行动，但应选择风险最低且可回滚的路径：采用当前已证实字段、避免提高复杂度、不更改无关模板、保持现有版本声明、做一个最小加载验证，并在交付中列出未覆盖项。速度不是跳过证据，而是缩小声明和改动面。

## 14. 证据审阅中的常见谬误

### 把目录索引当成规范

字段目录为代理提供高覆盖的检索入口，但它可能包含历史字段、简化注释、不同版本内容或无法从单行看出的前置条件。正确链路是：目录给出候选，原始实现确认，最小运行验证观察。只完成第一步时，结论最多是 `待核查`。

### 把可读摘要当成原始行为

`W:\mao\tx\模组加载器` 适合快速理解模块职责和查找关键词，但摘要可能把变量翻译为自然语言、压缩异常分支或保留旧注释。若它与 `game-lib-src` 不同，使用原始行为并记录摘要被覆盖。不要“折中”两者，运行时不会折中。

### 把能打开归档当成能加载模组

ZIP 工具能列出文件只说明归档结构在工具看来可读。游戏还要通过 `.rwmod` 虚拟文件系统定位逻辑根、读取元数据、满足版本、扫描内容和读取资源。归档检查是必要条件，不是充分条件。

### 把没有未使用键错误当成功

未使用键审计只能说明配置键被某些加载路径消费或豁免。它不能证明数值合理、对象引用的运行期行为正确、AI 会使用、投射物会命中或联机一致。解析通过后仍必须按本页和其他参考的生命周期做测试。

### 把严格模式当成唯一质量指标

严格模式有助于暴露部分问题，但它不是覆盖所有运行错误的测试替代。反过来，旧模组在严格模式出错也不自动证明每项历史行为都不可用。应逐项分解：重复、空白、标签、未使用键、版本限制、对象引用和运行期问题都有不同修复策略。

### 把“没有源码”当作“没有证据”

对外不能发布内部反编译材料，不意味着内部工程无法引用行为摘要。正确做法是记录路径、功能、版本和最小测试，而不是复制源码。对外可解释“为什么要求 `title`”“为什么拒绝 `..`”“为什么内存数组需要 p11”，无需泄漏可再分发实现。

## 15. 跨代理交接协议

多人并行维护模组时，最危险的是后一代理把前一代理的已证实结论当成无条件规则，或在不了解工作区脏状态下覆盖无关改动。交接内容应短但结构化：

```text
工作对象：相对源根与文件列表
目标构建：用户指定的版本/构建
已证实：列出带证据标签的三至五项关键行为
已修改：每项改动对应的配置对象
已验证：目录版、rwmod、单机、AI、联机中的实际覆盖
未验证：版本、平台、状态或性能缺口
禁止假设：例如“不要将 title 改回 name”“不要降低 p11 门槛”
工作区边界：哪些文件属于本任务，哪些是其他代理的已有改动
```

交接者不应复制内部源码、整份第三方配置或大量临时日志。接收者首先核对版本与文件边界，再复查高风险断言；不要在未确认源根、继承链和现有工作区状态前进行批量格式化或全局替换。

### 交接后的快速复核

1. 查看目标文件当前内容，确认没有并发改动改变前提。
2. 验证元数据 `title`、`minVersion`、源根和包形态与交接记录一致。
3. 检查新增字段是否落在已列出的对象与区段中。
4. 运行最小、最快的加载测试，确认前一阶段没有因合并而失效。
5. 若结论与当前文件相矛盾，停止扩大改动，先重新建立证据记录。

这个协议尤其适合代理协作：它让下一人继承的是可检查的事实边界，而不是模糊的“已经研究过”。

## 16. 最终发布声明的证据语法

交付信息中的措辞应与证据等级严格对应。以下表述可直接作为审阅标准：

| 证据状态 | 推荐措辞 | 禁止夸大 |
|---|---|---|
| 已证实 | “已在目标构建的加载/运行路径核对。” | “所有版本均已支持。” |
| 跨版本已证实 | “已在列出的 1.14 与 1.15 测试路径复核。” | “永久兼容。” |
| 版本限定 | “该实现要求至少 1.15p11。” | “低版本也应当可用。” |
| 待运行验证 | “静态路径已核对，运行期尚待目标环境验证。” | “已修复。” |
| 样例观察 | “本地样例采用该模式，未作为规范依据。” | “引擎规定如此。” |
| 不兼容 | “在指定基线下不可安全实现；需替代或升版。” | “强行降低声明即可。” |

技术文档的可信度来自边界清楚，而不是每句都显得肯定。只要路径、版本、行为、验证和未知项被清楚区分，代理就能在后续任务中安全地继续调查或实施。

## 17. 证据保鲜、可复现环境与发布判定

证据会随游戏构建、打包工具、工作区结构和模组依赖变化而过期。一次调查的目标不是永久保存“某字段可用”的断言，而是保存足以让下一位代理重新判断的上下文。证据保鲜的最低要求是：写明观察时间、目标版本、包形态、源根、是否包含模板、是否在干净安装环境运行，以及得到结论的最小操作。

### 环境指纹

每次重要验证至少记录以下指纹，而不要只记录“我的电脑能跑”：

| 项目 | 需要记录的内容 | 为什么必要 |
|---|---|---|
| 游戏版本 | 完整主版本、小版本和构建标识 | `p` 构建差异可能改变能力门槛 |
| 模组形态 | 普通目录或 `.rwmod` 文件 | 虚拟文件系统与目录版路径行为不同 |
| 逻辑源根 | 实际被发现的 `mod-info.txt` 所在根 | 包装目录可能使物理根和逻辑根不同 |
| 启用状态 | 已启用、禁用、或诊断模式读取禁用项 | 默认禁用不能被误归因给解析失败 |
| 测试内容 | 最小单位、地图、动作或资源链 | 知道实际走过哪些分支 |
| 模板状态 | 文件级父项、节级复制、祖先目录模板 | 避免把继承结果误判为本地字段 |
| 客户端角色 | 单机、主机、客户端、AI 控制 | 运行和联机结论不可互换 |
| 发布物来源 | 目录工作副本或具体归档构建 | 防止测试了错误的一份同名模组 |

环境指纹并不要求暴露个人绝对路径、用户资料或受限内部材料。可以使用相对逻辑路径和非敏感构建标识；关键是让复现者知道哪些条件必须相同。

### 干净环境的价值

开发目录经常包含旧图片、遗留单位、缓存、同标题模组或其他代理的临时改动。它们会让错误配置看起来正常。例如归档漏掉一张图片时，开发目录中的同路径文件可能被误用；两个同名单位同时存在时，生成菜单可能表现为“新改动有效”但实际引用的是旧定义。发布前至少进行一次干净环境复核：只放入待发布目录或 `.rwmod`，确认没有同标题、同内部名或同资源路径的残留包，重新扫描再运行最小测试。

干净环境不是“安装一个新游戏后随便点一下”。它要与断言匹配：验证元数据时清理同标题模组；验证单位引用时清理同内部名单位；验证图像时确认目录版资源不可被归档版借用；验证联机时双方均使用同一发布物与同一启用状态。若无法建立干净环境，报告中必须把结论降为局部观察。

### 发布门禁

下表给出可执行的发布判定，而不是单纯的推荐：

| 条件 | 可以发布吗 | 处理 |
|---|---|---|
| `title`、源根、版本与归档结构已验证；核心玩法已最小运行测试 | 可以，按验证范围声明 | 记录未覆盖的联机或平台项 |
| 静态字段已查到，但未在目标游戏加载 | 不可以声称修复完成 | 先完成最小加载验证 |
| 依赖内存数组但 `minVersion` 低于 `1.15p11` | 不可以 | 提高门槛或改用替代设计 |
| 只在目录版正常，`.rwmod` 尚未测试 | 可作为开发态，不可作为归档交付结论 | 构建并测试发布归档 |
| 可读摘要与原始行为冲突尚未裁决 | 不应扩大改动 | 回到原始实现或构造最小试验 |
| 包内含内部反编译材料、第三方完整配置或开发垃圾 | 不可以 | 从发布清单移除并重新审计 |
| 用户要求的旧版本未测且实现含新特性 | 不可宣称兼容 | 说明版本限定或提供降级实现 |

### 失败时的回退纪律

验证失败后，最危险的反应是继续叠加“兼容补丁”。正确回退是回到最后一个已证实状态，保留失败的最小复现和错误文本，撤销或隔离本轮唯一变量，再决定是否修改设计。不要同时换字段、提高版本、重打包和改模板；那样即使下一次成功，也无法说明是哪项修复了问题。

对于共享工作区，回退只限于本任务新做的变动，绝不覆盖其他代理已有修改。文档任务同样如此：若发现其他章节同时出现，应只校验自己的四个文件，不对全目录重格式化、重排序或重命名。工程可复现性包含变更边界可复现，而不仅是游戏行为可复现。
