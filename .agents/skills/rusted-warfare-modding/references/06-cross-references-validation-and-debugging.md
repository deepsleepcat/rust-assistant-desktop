# 交叉引用、验证与调试

> 入口：先阅读 [SKILL.md](../SKILL.md)。本章与 [03-单位架构与字段目录路由](03-unit-architecture-and-field-catalog-routing.md)、[04-行动、逻辑、资源、效果与状态](04-actions-logic-resources-effects-and-state.md)、[05-素材、音频、本地化与地图](05-assets-audio-localization-and-maps.md)、[07-打包、发布与回归](07-packaging-release-and-regression.md) 一起使用。
>
> **来源与权威性。** 本文是内部验证手册，不是对任一游戏版本的替代规范。结论以目标游戏实际加载、日志和可复现运行结果为准。`W:\mao\tx\tools\decompilers\game-lib-src` 的目标版本行为优先；`W:\mao\tx\模组实例\`、DeepStar 样本目录只用于内部证据定位和兼容性测试，绝不意味着其中配置是规范或可复制模板。禁止从 `W:\mao\tx\模组加载器` 导出、发布或复用任何内容，因为其 README 将它标为内部且不可公开。 

## 本章目标

Rusted Warfare 模组不是“能打开一个 INI 文件”就算通过。加载器会扫描模块和单位，解析已知字段与带类型的 LogicBoolean，建立炮塔、投射物、效果、资源和行动的符号表，随后再解析 `overrideAndReplace`、`canBuild`、`builtFrom`、升级等跨引用。一个错误可导致单个单位不可用，也可能使模块记录解析错误并在实践中被视为禁用。

因此验证必须分层：

`文件系统/归档 -> manifest -> 文本语法与字段解析 -> 继承与符号唯一性 -> 跨引用 -> 素材/语言/地图 -> 游戏运行时`

前一层通过是后一层的必要条件，不是充分条件。静态审计不能证明 AI、路径、目标选择、存读档、多队伍、帧率压力或多人同步下的玩法正确。

本章提供：

- 用错误上下文快速定位的排错方法；
- 交叉引用的分类、所有权与加载后解析顺序；
- 适用于代理的分层审计流程；
- 可缩小问题的最小复现方法；
- 将验证结果变成可维护工程证据的登记方式。

## 一、先理解失败形态

### 1. 解析错误不是普通警告

模块解析错误会记录在 mod 上，并使该模组在实际使用中等同于被禁用。不要把“地图列表里找不到”“单位没有出现”“模组好像没加载”仅当作 UI 问题；先确认 mod 是否已经处于带错误状态。重新加载会清理状态，因此修复后应执行完整重新加载，而不是只在一个已失败的会话中热试某个文件。

建议把每次失败归入下面之一：

| 类别 | 典型触发 | 第一反应 |
|---|---|---|
| 包/manifest | 根结构不对、manifest 缺失或不可读 | 从最终归档根检查 |
| 单位扫描 | 文件未被发现、递归目录过深、文本编码问题 | 确认扫描路径和层级 |
| 键解析 | 未知键、拼写错误、值类型错误 | 按错误中的节与键定位 |
| LogicBoolean | 函数名、返回类型、参数或引用错误 | 缩成一个带类型的最小表达式 |
| 符号重复 | 同名资源、动作、投射物、炮塔 | 统一命名空间并消除重复 |
| 加载后引用 | `canBuild`、`builtFrom`、升级、覆盖目标不存在 | 按引用图检查目标与加载顺序 |
| 资源读取 | 图像、音频、locale、TMX/TSX 依赖缺失 | 按字段上下文和最终归档路径追踪 |
| 运行时逻辑 | 单位加载但行为、平衡、性能错误 | 编写可观测场景并最小化状态机 |

不要在错误出现后立刻遍历整个模组替换大量字段。一次只针对最先报告的阻断错误建立假设、修改最小范围、重新加载，再处理下一项。批量“修复”常把未知键、废弃键、路径问题和业务回归混为一团，使真正根因不可追踪。

### 2. 错误上下文是主索引

引擎在未知字段、类型错误、逻辑类型错误等情况中通常给出源键上下文。记录完整文本，不要只记录最后一句“failed”。一条合格的缺陷记录至少包含：

| 字段 | 内容 |
|---|---|
| 目标版本 | 例如 1.14、1.15 或特定补丁，不用“最新版”代替 |
| 载入方式 | 源目录、最终 `.rwmod`、单人或多人入口 |
| 模组版本 | manifest 中的可识别版本 |
| 完整错误 | 原样保存，包括路径、节、键和原因 |
| 最小复现 | 最少文件、最少单位、最短操作序列 |
| 预期 | 应加载、应显示、应生成或应拒绝的具体结果 |
| 实际 | 可观察到的精确行为 |
| 变更 | 哪些文件、哪几个 ID 被改动 |
| 结果 | 修复、未修复、版本差异或待确认 |

如果日志指向 `projectile_x` 的一个键，先检查该节和该键，而不是先改调用它的炮塔。若日志指向一个 locale 表达式，先确认表达式类型和存在性，而不是替换整个文本文件。源键上下文可把调试从“模组很大”缩小到“一条解析边”。

### 3. 严格级别改变问题暴露时机

未识别或未使用的 INI 键是严肃问题，不应被视为无害注释。它可能代表拼写错误、已经失效的配置、写错节、复制时残留或目标版本不支持。`strictLevel` 会影响部分问题是错误还是警告；已知例如某些缺失 `builtFrom` 值在 strict 级别零可能是警告，在 strict 级别一成为错误。

| 情况 | 错误的处理方式 | 正确的处理方式 |
|---|---|---|
| strict 0 只出警告 | 忽略并继续发布 | 判断它是否表示缺引用、版本不兼容或死配置 |
| strict 1 出错 | 把 strict 降回零以隐藏问题 | 修引用、删除无效键或记录明确兼容策略 |
| 未使用键 | 认为引擎会忽略 | 将其视为可能没有任何效果的缺陷 |
| 未知 LogicBoolean | 改成常量 `true` 让包加载 | 修类型或用可验证的正确表达式 |

严格模式不是“开发难度档”。它是提高错误可见性的工具。对新内容，优先在高严格度下修到清洁，再明确记录确实必须为兼容而保留的例外及其目标版本。不要把警告清单藏在发布说明外。

## 二、交叉引用：符号表和加载后图

### 1. 两个阶段，不要混为一谈

第一阶段主要是每个单位或配置文件内部的解析：节、键、值类型、资源、投射物、炮塔、行动、效果、动画等被创建。该阶段会拒绝重复命名的资源、投射物、炮塔和行动，也会拒绝未知字段和不符合类型的 LogicBoolean。

第二阶段在加载后解析跨单位、跨文件或全局关系，包括但不限于：

- `overrideAndReplace`；
- `canBuild` 与可生产目标；
- `builtFrom` 的来源与位置；
- 升级关系；
- 单位转换、生成和地图中的单位引用；
- 资源、locale、素材、TSX 与地图依赖。

一份文件在第一阶段“解析成功”不代表第二阶段“可用”。例如 `canBuild` 指向不存在的单位会出错；某些 `builtFrom` 缺失在低 strict 下可能只警告，但绝不意味着玩家可以忽略构建菜单是否正确。

### 2. 引用类别矩阵

| 源字段或概念 | 目标类型 | 解析阶段 | 必须验证 |
|---|---|---|---|
| `[turret_*] projectile` | 投射物 ID | 单位内部 | 目标唯一存在，伤害/目标语义匹配 |
| `altProjectile` | 投射物 ID | 单位内部 | 条件类型正确，备选存在 |
| 效果字段 | effect ID 或内建效果 | 单位内部 | 拼写、生命周期、频率、可见性 |
| `alsoTriggerAction` | action ID | 单位内部 | 无重复、无无界递归、触发条件正确 |
| 资源价格/修改 | local/global resource ID | 单位或全局 | 声明、所有权、范围、单位生命周期 |
| `copyFrom` | 文件或节 | 文件加载 | 相对路径、覆盖顺序、循环和内容意图 |
| `overrideAndReplace` | 单位 ID | 加载后 | 目标版本存在、替换范围与兼容性 |
| `canBuild` | 单位 ID | 加载后 | 所有目标存在；缺目标为错误 |
| `builtFrom` | 构建来源 | 加载后 | 目标来源、菜单位置、strict 下结果 |
| 升级关联 | 单位 ID | 加载后 | 双向语义、转换后状态和 UI |
| `spawnUnits`/`convertTo` | 单位 ID | 加载或运行 | 目标可加载、所有权、位置失败策略 |
| 图片/声音 | 文件或内建名 | 加载/运行 | 字段支持、格式、归档路径、解码 |
| `i:`/locale key | 翻译键 | 加载/显示 | 键存在、回退和动态参数 |
| TMX/TSX | 文件与图块资源 | 地图加载 | 递归依赖均在包内 |

将表格中的每一类看作不同的“链接器”。不能用字符串搜索替代类型检查，也不能因为一个名字在文件中出现就断言它是有效目标。

### 3. 重名为什么必须在首次发现时修

重复 named resource、projectile、turret 或 action 会失败。此处“后来定义覆盖前面定义”的想象不可靠，也会让审阅者无法判断引用到底指向哪个实体。重名的来源通常是：

- 从模板复制后未改 ID；
- `copyFrom` 后又重复声明同名节；
- 合并两个单位版本时保留了两套内部定义；
- 以 UI 文本而不是逻辑命名组织 action；
- 在大小写、下划线和序号上制造近似重复；
- 生成脚本在同一输出中追加，而不是替换。

对每个单位建立局部符号清单可提前发现这一类错误：

| 类别 | 建议命名 | 唯一性检查 |
|---|---|---|
| 炮塔 | `turret_main`、`turret_aux` | 名称精确唯一，不依赖显示文字 |
| 投射物 | `projectile_pulse` | 不与模板或备用弹冲突 |
| 行动 | `ui_enable_pulse`、`guard_disable_empty` | 一个业务节点一个 ID |
| 效果 | `effect_pulse_ring` | 能从调用点反查 |
| 资源 | `charge`、`research_token` | 记录全局或局部所有权 |
| 动画 | `animation_charge` | 调用点与目的清楚 |

命名检查不要只用“所有节名去重”替代分类，因为不同节类别可能有不同规则。它也不能替代引擎加载；它的价值是让问题在提交前更早出现。

### 4. `canBuild`、`builtFrom` 和升级关系

生产与建造形成跨单位图。`canBuild` 的缺目标会报错；`builtFrom` 的缺失值在不同 strict 级别下至少可能从警告升级为错误。代理应把这两类都当作发布前必修项，而不是只在菜单里“看起来差不多”即可。

审阅一个新增单位时反向和正向各走一次：

1. **正向**：本单位能建什么？所有 `canBuild` 目标是否存在、在目标版本是否可加载、锁定条件和价格是否正确？
2. **反向**：谁能建本单位？每个 `builtFrom` 来源是否存在、位置是否有冲突、strict 级别下是否干净？
3. **升级**：升级前后单位是否都存在，AI/菜单/状态保留是否明确？
4. **替换**：`overrideAndReplace` 是否在目标游戏版本中真正有目标，替换是否会让地图、旧存档或其他单位失去预期入口？

不要假设存在模组依赖或加载顺序特性来解决跨包目标。对所检查的引擎，不应宣称它支持模组依赖或加载排序功能。若一个单位必须来自另一个模组，当前工程应把它视为不可保证的外部前提，而不是宣称有可靠的自动依赖解析。

### 5. 继承与引用图的检查方式

将配置看成有向图，而不是文件夹列表：

- 文件节点通过 `copyFrom`、模板和共享配置连接；
- 单位节点通过生产、升级、转换、生成和替换连接；
- 单位内部节点通过 action、projectile、effect、turret、resource、animation 连接；
- 资源节点通过图像、声音、locale、TMX、TSX 和音乐连接。

审计时从变更点做两类遍历：

| 遍历 | 目的 | 例子 |
|---|---|---|
| 向下依赖 | 新节点需要什么才能成立 | 新 action 引用 effect、sound、resource、turret |
| 向上影响 | 谁依赖变更点，可能被破坏 | 改 projectile 后所有炮塔和生成链 |

对 `copyFrom` 还要查环、覆盖顺序和隐式继承。一个目标文件存在不表示复制结果符合意图；必须比较最终有效的关键字段或用最小单位加载验证。针对大型继承树，优先改最靠近行为所有者的节点，避免在通用模板上做会改变大量单位的偶发性修补。

## 三、分层审计流程

### 第 0 层：隔离与基线

开始前先记录当前工作区状态，避免把其他代理的改动误认为本任务产物。若仓库本来是脏的，不能重置、还原或删除不属于自己的文件。明确本次计划修改的路径、目标游戏版本、发布目标和可运行基线。

| 项目 | 基线证据 |
|---|---|
| Git 状态 | 已记录本任务前的修改与未跟踪文件 |
| 模组版本 | manifest 中的版本字符串 |
| 游戏版本 | 目标 1.14/1.15/补丁版本 |
| 加载媒介 | 源目录与 `.rwmod` 中的至少一种 |
| 测试地图 | 稳定、可重复进入的地图 |
| 最小单位 | 可独立加载的控制单位或空白测试单位 |

没有基线时，后续“修复后不报错”不能证明不是因为测试条件改变、旧模组被禁用或加载了错误路径。

### 第 1 层：文件系统与归档边界

目标是证明源文件和最终包没有明显不可达路径。

- 核验 manifest 位于预期模组根，根目录没有被意外再套多层；
- 检查文本、图片、音频、地图、TSX、预览和 locale 文件的相对路径；
- 拒绝任何逃离模组根的引用；
- 在 ZIP 内查同样的条目，而不只查源目录；
- 排除 `.git`、`node_modules`、编辑器缓存、备份、重复导出等发布垃圾；
- 检查归档使用 UTF-8 条目名，尤其是中文显示名或文件名；
- 记录是否有一层兼容包装目录，仍以“一个预期 mod root”为构建目标。

此层不解析游戏语义，但能消灭“本地能用，打包后找不到”的大部分问题。

### 第 2 层：manifest 与模块发现

目标是证明游戏识别的确是当前模组，而不是另一个旧目录、旧归档或缺 manifest 的包。

检查 manifest 的名称、版本、描述、最小/目标版本声明、地图与音乐相关路径。历史实例可能显示新旧包结构以及缺 manifest 的遗留包；使用它们作为兼容性测试数据，不要把它们升格为新项目规范。对于每种发布结构，都需在目标游戏中确认显示名、版本、启用状态和错误信息来自正确的实例。

### 第 3 层：文本、节、键与类型解析

目标是让加载器扫描每个单位并完成基本解析。

重点包括：

- INI 节名、分隔符、编码和多行值完整；
- 无未知或未使用键；
- 数值、布尔、枚举、颜色、时间、资源表达式格式正确；
- `LogicBoolean` 的函数、参数、引用和返回类型与字段预期一致；
- 必需的 `[graphics]image` 可加载，`total_frames >= 1`；
- 图片着色模式合法，没有与 `teamColorsUseHue` 的不兼容组合；
- 声音文件为 `.ogg` 或 `.wav`，或明确为内建名；
- action、turret、projectile、effect、resource 等命名不重复。

单位扫描目录递归深度为十层。不要设计需要第十一层或更深才能被发现的单位树；即使开发环境能通过手工引用它，扫描发现和打包可维护性都会变差。目录组织要让可扫描单位位于合理深度，并用一个干净环境验证扫描结果。

### 第 4 层：继承、符号和跨单位链接

目标是完成 `copyFrom`、模板、生产、建造、升级、替换和转换等关系。此层特别检查 `canBuild` 目标，缺失目标应直接修复；对 `builtFrom` 的警告也要在 strict 级别一重测，确定没有把菜单、来源或兼容性问题藏起来。

建立机器可读或人工可审的引用清单均可，关键是每个源 ID 都有明确目标。对于一处改名，不能只改定义点，必须搜索全部调用方、地图对象、效果、队列和升级节点。

### 第 5 层：资产、语言和地图依赖

目标是验证来自 [05-素材、音频、本地化与地图](05-assets-audio-localization-and-maps.md) 的完整资源链：

- 图片字段及特殊前缀在该字段中合法；
- 音频可解码，无非预期回退；
- locale 的直接值、`i:` 键、`_zh`、`_en`、区域回退、动态 `%{...}` 正确；
- TMX 被发现，并递归含有所有 TSX、图块位图、模板、缩略图和音乐；
- 预览图与实际地图均在最终 `.rwmod` 内可用。

### 第 6 层：游戏运行时

目标是证明规则而非仅配置成立。至少覆盖：

| 场景 | 要验证的问题 |
|---|---|
| 创建 | 初始状态、素材、资源、显示、创建事件 |
| 建造/生产 | `canBuild`、价格、队列、建成后的 `builtFrom` 关系 |
| 行动 | 可见性、锁定、费用、冷却、连续点击、取消 |
| 战斗 | 炮塔、投射物、目标类型、效果、声音、伤害与友军逻辑 |
| 状态机 | 自动触发重入、边界计数、去抖、低频延迟 |
| 转换与生成 | 标签、资源、内存、附件、运输和所有权策略 |
| AI | 选择、建造、升级、禁用分支与资源行为 |
| 存读档 | 局部状态、全局状态、队列和地图恢复 |
| 多单位压力 | CPU、声音、粒子、生成上限和 UI 可读性 |
| 地图 | 起始点、对象、图块、音乐、重开和多队伍 |
| 最终归档 | 与源目录测试相同，且未意外依赖开发机文件 |

任何声称“验证完成”的结论都必须说明覆盖到哪一层。若只完成静态检索，应明确写“静态审计完成，运行时未证明”，而不是使用“已兼容”或“已修复”的绝对说法。

## 四、最小复现：把大模组压缩成一个问题

### 1. 何时必须最小化

出现以下任一情况时，停止在主模组中盲改，转为最小复现：

- 错误指向一个键，但上下游引用很多；
- 开发目录成功，打包包失败；
- 仅某个游戏版本、语言、地图或设备失败；
- 行为随着单位数量、存读档或事件顺序改变；
- 修一个错误后又出现不相关错误；
- 不确定问题是字段支持、继承覆盖、资源路径还是业务逻辑。

最小复现不是另起一套相似大工程，而是保留一个 manifest、一个单位、一个资源或素材、一个明确操作。它的目标是确认一个断言，例如：“1.15p11 是否接受此 memory 写入并能被动态文本读取”“此 `ROOT:` 是否在该图片字段中有效”“该 `canBuild` 缺目标在 strict 1 的准确错误文本是什么”。

### 2. 最小复现构造步骤

1. 新建隔离的临时模组根，不从第三方单位文件复制内容。
2. 放入最少 manifest 和一个新写的、无版权负担的测试单位。
3. 只加入待验证的一个字段或一条引用。
4. 先证明空基线可加载，再一次加入一个变化。
5. 记录游戏版本、载入方式、完整错误和截图或可观察结果。
6. 若确认行为，迁回主模组时只带回必要最小改动和测试说明。
7. 删除或隔离开发期测试内容，避免误打进正式包。

最小复现中也必须遵守路径、版权和发布边界。它不是从受保护反编译或第三方配置粘贴大段代码的理由。

### 3. 二分与单变量实验

对于大型变更，用二分法定位：先禁用一半最近改动、观察错误是否消失，再继续缩小。对于字段行为，用单变量实验：保持单位、图片、版本、路径、地图不变，只改变一个键或一个值。避免同时升级资源名、移动文件、改模板、改 LogicBoolean 和重打包；那样无法从结果推断原因。

| 实验问题 | 保持不变 | 仅改变 |
|---|---|---|
| 图片前缀是否可用 | 同一图片、同一单位、同一版本 | 相对路径与 `ROOT:` 写法 |
| action 条件是否解析 | 同一 action 结果和文本 | 一个 LogicBoolean 子表达式 |
| `canBuild` 是否链接 | 同一工厂和目标单位 | 一个目标 ID |
| 音频是否解码 | 同一路径、同一调用点 | 文件编码或扩展名 |
| 地图是否自包含 | 同一 TMX 和安装步骤 | 是否包含一个 TSX/位图依赖 |

## 五、运行时调试：让状态能被观察

### 1. 调试不是增加更多隐藏行为

调试行动和临时显示应观察状态，而非额外改变状态。对于行动状态机，优先显示当前资源、标签驱动模式、阶段、冷却或已初始化标记；不要为了“测试方便”让调试按钮绕过费用、冷却和权限后又把这种行为当作正常路径正确的证据。

| 目标 | 合理诊断手段 | 风险较高的手段 |
|---|---|---|
| 看局部资源 | `infoOnly` 动态文本 | 强行把资源加满再判断正常流程 |
| 看模式标签 | 显示当前模式或切换按钮可见性 | 同时修改多个标签进行猜测 |
| 看事件是否到达 | 一次性本地消息或短效果 | 每帧广播全局消息 |
| 看生成次数 | 有上限的计数展示 | 生成不可见单位作为计数器 |
| 看目标引用 | 显示安全的空/非空状态 | 在空引用上继续取属性导致新错误 |

发布前要移除或不可见化开发诊断入口，但保留正常玩法需要的确认和锁定反馈。若正式玩家不能知道模式是否开启、资源是否不足或行动是否成功，说明可观测性设计本身不足，不应简单归类为“只需调试时可见”。

### 2. 日志与可重复脚本

运行时排错最好使用固定步骤，例如：

1. 启动干净游戏会话，确认只启用目标模组及必要对照包。
2. 进入固定测试地图与固定队伍设置。
3. 生成或建造一个指定单位。
4. 执行按钮 A 两次、等待规定时间、执行按钮 B。
5. 记录资源、UI、声音、动画、单位数量、日志和帧率迹象。
6. 重开地图、重新执行；再从存档恢复后执行。
7. 用最终 `.rwmod` 重复相同序列。

把这些步骤写成测试用例名称，不必把冗长日志纳入模组。关键是后续代理能以相同环境判断回归，而不是“我刚才点了几下看着没问题”。

### 3. 性能问题的排查顺序

性能回归通常来自频繁条件计算、广域单位搜索、粒子/音效爆发、递归生成、过密动态文本或地图图层，而不是一个普通数值字段。排查时按“乘数”优先：单位数、每单位检查频率、每检查工作量、每次触发副作用数量、资源生命周期。

| 症状 | 优先检查 |
|---|---|
| 单位一多就卡 | 自动触发频率、全图搜索、每单位动态文本 |
| 交战时掉帧 | 投射物生成链、效果生命周期、尾迹频率、音效叠加 |
| 长局越来越慢 | 资源/单位/效果是否无界累积，失效对象是否清理 |
| 地图加载慢或失败 | 大图块、外部依赖、图像层、重复音乐扫描 |
| 只有某语言卡顿 | 动态文本是否有昂贵表达式或异常回退循环 |

性能修复后要同时重测行为。将每帧逻辑改为低频检查可能改变自动关机、补给、AI 或状态切换时机；它不是纯优化。

## 六、常见错误模式与修正路径

### 1. “文件在，所以路径没问题”

**错误假设：** 图像或 TSX 在磁盘上，引用必然可用。

**应做：** 确认字段支持的路径形式、相对基准、大小写、根边界、归档条目、目标引擎解码与运行时调用。地图还要递归至二级依赖。

### 2. “警告不重要”

**错误假设：** strict 0 的 `builtFrom` 或未使用键警告可以留到以后。

**应做：** 在 strict 1 重测，判断是否为缺引用、错别字、历史残留或目标版本不兼容。记录真正允许的兼容例外，否则修掉。

### 3. “复制样本能证明写法正确”

**错误假设：** 某实例模组有某段配置，当前项目复制即可。

**应做：** 样本只用于提取检查问题，例如“它有 TMX -> TSX -> PNG 链”“它同时存在全局与局部资源”。重新写最小语义示例，按目标版本验证，不复制受保护或第三方单位配置。

### 4. “能进入地图就是全部通过”

**错误假设：** 地图缩略图显示、单人能进就代表可发布。

**应做：** 检查地图注册、外部 TSX、位图、预览、音乐、单位引用、重开、多队伍、最终 ZIP 与干净安装。预览成功并不能证明依赖图完整。

### 5. “一条 action 能做完所有事情”

**错误假设：** 按钮同时完成资源、转换、生成、效果、声音、全局消息和队列就更简单。

**应做：** 根据 [04-行动、逻辑、资源、效果与状态](04-actions-logic-resources-effects-and-state.md) 分为命令、规则、表现，设计幂等守卫和有界副作用链。

### 6. “重新加载会自动修好”

**错误假设：** 模块失败后编辑文件即可在当前状态下判断修复。

**应做：** 重新加载会清理 mod 状态，因此执行明确的完整重载，并确认载入的是当前包和当前版本。把重载本身作为测试步骤记录。

### 7. “静态搜索没有漏项”

**错误假设：** 搜索不到旧 ID 即表示改名安全。

**应做：** 还要加载后链接、在地图中生成、经过 UI、AI、事件和最终归档测试。动态文本、外部 TSX、内建名和隐式回退不一定被简单搜索覆盖。

## 七、面向编码代理的验证工作流

### 变更设计前

- [ ] 确定目标游戏版本和严格级别策略。
- [ ] 记录工作树基线，不触碰其他代理已有改动。
- [ ] 列出将新增、删除或改名的文件、单位、资源、action、projectile、turret、effect、locale key 与地图资产。
- [ ] 对每个 ID 写出定义点、调用方、所有权和生命周期。
- [ ] 对跨包或核心引用记录假设，不宣称未证实的依赖或加载排序能力。

### 编写后静态审计

- [ ] 文件在合理扫描深度内，单位目录不依赖超过十层递归。
- [ ] 所有键被当前目标版本识别且被实际使用。
- [ ] LogicBoolean 的字段预期、函数、参数、引用和返回类型正确。
- [ ] named resource、projectile、turret、action 等局部命名唯一。
- [ ] `canBuild` 目标都存在；`builtFrom` 在 strict 1 下无未解释警告。
- [ ] `overrideAndReplace`、升级、转换、生成、队列和地图引用的目标存在。
- [ ] 图片、音频、locale、TMX、TSX、位图、预览、音乐依赖均在源树和最终包可达。

### 游戏加载与运行时审计

- [ ] 从干净状态加载并保存完整首个错误；修一项后重载再继续。
- [ ] 创建、建造、生产、升级、行动、战斗、生成、转换和死亡的目标路径通过。
- [ ] 资源边界、重复点击、自动触发重入、低频延迟和长时间运行通过。
- [ ] AI、不同队伍、存读档、地图重开和多单位压力通过或明确未覆盖。
- [ ] 在源目录和最终 `.rwmod` 两种媒介重复关键用例。
- [ ] 不把静态审计结论写成运行时保证。

### 缺陷关闭标准

一个错误可标记关闭，应满足：

1. 有完整错误或可观察失败的原始证据；
2. 根因归属到一个明确层和明确源键、引用或资源边；
3. 最小改动修复，不包含无关格式化或批量猜测；
4. 重载后原错误消失；
5. 至少一个受影响正常场景通过；
6. 最终归档验证未重新出现；
7. 剩余未覆盖风险已记录，例如仅在 1.15 测试、未做多人或未做低端设备压力。

## 八、发布前审计提问

1. 当前模组是否真的被加载，还是错误状态使它实际禁用？
2. 记录的错误是否包含路径、节、键、版本和载入方式？
3. 所有未知/未使用键是否已修，或是否有书面且已验证的兼容理由？
4. 所有 `canBuild` 目标是否存在；所有 `builtFrom` 在 strict 1 是否干净？
5. 是否检查了重复 action、resource、projectile、turret 等定义？
6. 变更后的引用图中是否存在断边、环或未经测试的外部前提？
7. 每个素材、locale 和地图二级依赖是否在最终 ZIP 中，而不是只在开发目录中？
8. 运行时测试是否覆盖状态机边界、AI、存读档、地图和密集单位，而不只是“成功点过一次”？
9. 是否明确指出静态审计不能证明的部分？
10. 是否避免了从内部不可公开目录或受保护反编译内容中复制任何材料？

验证的核心不是让错误信息消失，而是形成可以复查的因果链：哪个文件、哪条配置、哪类解析、哪条引用、哪个运行时场景，以及最终包中是否仍然成立。这样做能把模组维护从依赖记忆和偶然试错，转化为后续编码代理可重复执行的工程流程。

## 九、验证证据、优先级与反例驱动审阅

### 1. 区分事实、推论和假设

配置审阅最危险的输出不是“不知道”，而是把一次观察扩展成未经验证的规则。每条结论应标为事实、推论或假设，并保存其证据来源。

| 分类 | 含义 | 合格表述 | 不合格表述 |
|---|---|---|---|
| 事实 | 由目标版本日志、加载或运行直接观察 | “1.15p11 最终包加载此单位时未报告该键错误” | “所有版本支持该键” |
| 推论 | 由多个事实合理得出，但仍有范围 | “该图片字段在当前单位中按根内相对路径解析” | “所有 image 字段都允许相同前缀” |
| 假设 | 尚需测试的设计前提 | “假设转换保留局部资源，待存读档验证” | “转换一定保留所有状态” |
| 样本线索 | 历史/第三方包用于提出问题 | “样本含外部 TSX，故本图需递归检查” | “样本这样写，所以这是规范” |

在缺陷单、代码评审或发布记录中使用这四类标记，能防止后续代理将内部样本、旧版本行为或一次成功载入误当成稳定接口。对于受保护的加载器反编译内容，只能遵守既定访问/发布限制，不能把它当作可复制的公开证据。

### 2. 风险优先级模型

资源有限时，不可能对每个文本格式化都跑全量地图压力。应按影响面、失败可见性、恢复难度和版本不确定性排序，而不是按文件大小排序。

| 风险因素 | 高风险信号 | 低风险信号 |
|---|---|---|
| 影响面 | 模板、全局资源、通用投射物、地图根或打包脚本 | 独立单位的一条说明文字 |
| 失败可见性 | 模组整体禁用、静默回退、存档损坏、多人差异 | 加载时有精确源键错误 |
| 恢复难度 | 已发布包、公共 ID 改名、资源经济变化 | 未发布的局部图标修正 |
| 版本差异 | memory、特殊路径、旧版兼容要求 | 已在所有目标版本跑过的基础字段 |
| 副作用放大 | 每帧搜索、递归生成、全局声音 | 单次本地 UI 显示 |
| 依赖深度 | TMX -> TSX -> 位图 -> 对象/单位 | 同文件内唯一 action 引用 |

可用简单分级决定回归强度：高风险必须最小复现、最终包测试、定向运行时和必要的全量回归；中风险至少跑最终包和受影响用户路径；低风险仍要跑烟雾，但可不重复无关压力测试。分级是为了透明地分配验证，不是为了豁免阻断错误。

### 3. 反例优先于正例

对每个声明的行为，至少设计一个最接近的反例。正例证明功能可达；反例证明保护确实存在。

| 规则声明 | 正例 | 必测反例 |
|---|---|---|
| “按钮花费二十五能量” | 能量三十时成功 | 能量二十四时不改变状态也不播放成功效果 |
| “最多生成三个单位” | 空状态生成三个 | 已有三或连续触发时不生成第四个 |
| “仅对敌方生效” | 敌方被命中 | 己方、盟友、中立、无目标均不误伤或误触发 |
| “地图自包含” | 源目录可加载 | 仅保留最终 ZIP、删除开发源后仍加载 |
| “中文可回退” | `zh` 正常显示 | 区域语言和缺翻译语言不显示内部键 |
| “自动关机” | 能量耗尽后退出 | 阈值附近不反复开关和刷提示 |
| “替换单位” | 新单位出现 | 地图对象、生产菜单和升级关系未断裂 |

把反例加入回归用例名。这样当未来修改某个 guard、路径或模板时，测试系统不会只重放最顺利的主流程。

### 4. 错误信息到修复范围的映射

错误文本虽然重要，但也会误导修复者过度扩大范围。应把错误类别映射到最小合理修改面：

| 错误定位 | 首要范围 | 不应立刻扩大到 |
|---|---|---|
| 一个未知键 | 同节、当前目标版本字段表 | 整个单位重写或批量删除所有注释 |
| 一个 LogicBoolean 类型错误 | 当前表达式、字段预期和直接引用 | 将全部条件改常量 |
| 重复 action | 同单位 action 命名和调用方 | 全模组重命名所有 action |
| 缺 `canBuild` 目标 | 目标 ID、工厂、目标单位文件 | 所有生产系统整体重做 |
| 缺 TSX/位图 | 当前地图依赖链与归档条目 | 所有地图目录迁移 |
| 音频回退 | 调用字段、扩展名、解码和路径 | 随机替换所有音效 |
| locale 键缺失 | 键定义、使用点、回退语言 | 全部文本重翻 |

修复范围过大不仅制造回归，也会让缺陷关闭证据失去可信度。若一个最小修复不够，按新增证据逐步扩展，而不是一开始假定整个架构有错。

### 5. 审计中的静态工具边界

文本搜索、JSON/XML 解析、ZIP 列表、文件哈希、目录深度和名称去重都很有用，但各有盲区：

| 静态检查 | 能证明 | 不能证明 |
|---|---|---|
| 搜索旧 ID | 已知文本位置不再引用 | 动态解析、内建名、运行时生成引用 |
| INI 键扫描 | 可能的拼写、重复和空值 | 目标版本确实支持该字段语义 |
| ZIP 清单 | 条目存在、根和路径大致正确 | 引擎能解码、加载并正确使用 |
| TMX/TSX 递归 | 文件依赖链存在 | 地图逻辑、对象属性、路径和 AI 正确 |
| 图片元数据 | 尺寸、帧数候选和可读性 | 游戏内层级、队色和缩放正确 |
| 音频元数据 | 扩展名和文件存在 | 目标解码器、音量、混音和触发频率 |
| 版本表 | 已记录的覆盖范围 | 未测版本的兼容性 |

报告静态审计时应明确这些边界。例如“已确认最终 ZIP 包含 TSX 和 PNG”不等于“地图已在游戏内通过”；“未找到重复 ID”不等于“所有加载后引用均存在”。

### 6. 证据保留的最小集合

不必永久保存每次测试的所有临时截图和完整日志，但每个发布候选至少应留下足以重放结论的最小集合：

- 候选 `.rwmod` 的文件名、版本和构建标识；
- 归档条目清单或关键条目的可核验摘要；
- 目标游戏版本、平台、加载媒介和启用包列表；
- 解析错误的完整原文，或“无错误”的加载步骤；
- 定向回归用例、输入操作、预期和实际；
- 地图与资源二级依赖的检查结果；
- 已知未覆盖风险和下一步建议。

证据文件应放在项目的测试/发布记录位置，不应塞入玩家模组根，更不应把内部工具、不可公开 README 或受保护来源一并打包。

### 7. 审阅会议的问题顺序

人工或代理评审高风险变更时，可按下列顺序提问，避免先陷入风格细节：

1. 这次改动的权威行为和目标版本是什么？
2. 新增或改名的定义、调用方、资源和地图依赖各有哪些？
3. 失败会在解析、加载后链接、资源读取还是运行时出现？
4. 最危险的反例是什么，是否已有测试？
5. 最终 `.rwmod` 中是否仍具备所有直接和间接依赖？
6. 静态审计覆盖了哪些，运行时仍未证明哪些？
7. 版本、兼容和外部关系的表述是否超过证据？
8. 是否存在更小的修复范围或需要先做最小复现的未知点？

这种顺序让评审先验证因果和边界，再处理命名、表述和局部风格。对模组配置而言，解析成功和资源可达通常比任何格式偏好更值得优先关闭。
