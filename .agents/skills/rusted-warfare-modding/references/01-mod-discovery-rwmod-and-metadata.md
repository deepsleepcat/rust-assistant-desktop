# 模组发现、`.rwmod` 与元数据

导航：任务边界、证据优先级和版本决策先看 `../SKILL.md` 与 [00-source-authority-and-versioning.md](00-source-authority-and-versioning.md)；INI 与模板语义见 [02-ini-parser-templates-and-inheritance.md](02-ini-parser-templates-and-inheritance.md)；发现成功后的单位字段定位见 [03-unit-architecture-and-field-catalog-routing.md](03-unit-architecture-and-field-catalog-routing.md)。

本页处理“游戏为什么没有发现模组”“压缩后为什么找不到 `mod-info.txt`”“元数据为什么显示错误”“目录版与 `.rwmod` 为什么表现不同”这类问题。它不讨论单位字段本身，也不把压缩包当成普通文件夹。对 `1.14`/`1.15` 目标，发现、元数据、版本检查和单位扫描是连续但不同的阶段；必须按阶段诊断。

## 1. 先建立正确的加载心智模型

从编码代理角度，一个可用模组至少经历如下状态：

```text
候选位置
  -> 注册为模组记录
  -> 确定源根目录
  -> 发现并读取 mod-info.txt
  -> 检查 minVersion 与启用状态
  -> 扫描可加载内容
  -> 构造单位、地图和资源引用
  -> 战局运行或联机校验
```

同一个“没有生效”现象在不同阶段意味着完全不同的修复：

| 表现 | 最可能阶段 | 首先检查 | 不应先做 |
|---|---|---|---|
| 模组列表完全没有条目 | 候选位置或注册 | 安装目录、扩展名、是否把 `.rwmod` 建成目录 | 修改单位 INI |
| 有条目但名称像目录名或为空 | 元数据发现/读取 | `mod-info.txt` 的相对根、`[mod] title` | 调整 `[core] name` |
| 有条目但被禁用 | 启用状态 | 用户设置与新模组默认禁用策略 | 重打 ZIP |
| 显示版本不支持 | 版本检查 | `minVersion` 格式、用户实际游戏构建 | 删除任意单位字段 |
| 可启用但单位不出现 | 内容扫描或解析 | 单位文件位置、后缀、加载错误 | 认为元数据已证明单位正常 |
| 单位出现但图片或行为错误 | 构造/运行 | 相对路径、字段引用和玩法测试 | 重新安排模组根目录 |

这个顺序的重要性在于：元数据读通不等于单位已加载；单位 INI 能通过不等于压缩包资源路径在不同平台相同；列表中可见不等于已启用。诊断日志应先标出当前已到达的最远阶段，再选择下一步。

## 2. 候选模组从哪里来

引擎注册模组时会枚举用户模组位置与内置模组位置。对于开发者，最相关的是用户安装的模组集合和内置目录集合；每一候选条目可成为目录模组或 `.rwmod` 文件模组。注册阶段产生的是“可管理的模组记录”，而不是马上读取全部单位。

### 候选对象的判定

| 磁盘对象 | 是否可作为常规候选 | 后续根目录 | 说明 |
|---|---|---|---|
| 普通目录 | 是 | 该目录或发现后的子目录 | 适合开发、调试和增量编辑 |
| 普通 `.rwmod` 文件 | 是 | ZIP 虚拟文件系统中的根或包装根 | 适合发布；默认不解压 |
| 名称带 `.rwmod` 的目录 | 否 | 无 | 目录伪装成归档是无效结构 |
| 普通 ZIP 但不以 `.rwmod` 交付 | 不应依赖 | 不确定 | 不要假定扩展名无关 |
| 单个 `.ini` 文件 | 否 | 无 | 单位定义不是独立可注册模组 |
| 包含模组目录的更上层工作区目录 | 不作为一个模组根使用 | 取决于枚举位置 | 不要把项目仓库根误当作安装根 |

硬规则：**`.rwmod` 是一个文件，不是以 `.rwmod` 结尾的文件夹。** 发现阶段会把后者视作无效，不要用“先解压到同名 `.rwmod` 目录”替代目录版开发。开发目录使用普通目录名；发布时才把其内容压成一个同名或版本化的 `.rwmod` 文件。

### 新模组默认禁用

引擎的模组管理策略会对新发现的模组设置禁用状态，以避免玩家安装或订阅新内容后自动改变战局。这是安全策略，不是解析失败。编码代理排查时必须区分：

- 条目不存在：尚未注册，检查路径与包装。
- 条目存在且标注禁用：已注册，检查是否由用户启用。
- 条目存在、已启用、带错误：进入了读取或加载，但失败信息需要继续定位。
- 条目存在、已启用、无错误、内容不见：检查具体扫描路径和内容类型。

自动化工具若“扫描所有模组”却未包含禁用模组，不应据此说文件不存在。某些诊断模式可能显式要求读取禁用模组数据；常规加载则跳过禁用项。报告必须写明扫描是否包括禁用记录。

## 3. 模组源根不是永远等于安装对象

“安装对象”“注册路径”“元数据所在目录”“最终源根”可能不同。最常见的变化来自多套了一层文件夹的归档或目录。例如下列两个结构在设计意图上相同：

```text
目录版：
开发模组/
  mod-info.txt
  units/

带一层包装的归档内部：
发布包.rwmod
  发布模组/
    mod-info.txt
    units/
```

发现逻辑会在候选根寻找 `mod-info.txt`；若找不到，会有限度地下钻子目录。找到后，发现到元数据的目录可成为后续的源根。这个行为是为容忍常见的压缩包装层而存在，不应被当作复杂工程布局的许可。

### 元数据发现的边界

已证实的发现限制可概括为：

- 目标文件名是 `mod-info.txt`，比较时不依赖大小写。
- 未直接找到时，递归下钻的最大深度为 `4`。
- 为避免在巨大目录树中误扫，目录条目数超过 `5` 的目录不继续作为递归下钻目标。
- 找到元数据的内层目录可替换原先的模组源目录。
- 这个源根调整是元数据发现行为，不等于任何目录都成为“单位文件自动加载根”。

注意第三点容易被误读。它不是“模组只能有五个文件”，也不是“单位目录只能有五个条目”。它约束的是寻找丢失元数据时的保守下钻策略。若你依赖深层包装，而且上层目录已有较多条目，发现就可能停止，导致模组根本不会注册为可读模组。正确修复是让 `mod-info.txt` 靠近归档根或目录根，而不是去删除有价值的资源文件以凑数量。

### 推荐结构

```text
星港试验包/
  mod-info.txt
  units/
    interceptor.ini
    shared.template
  graphics/
    interceptor.png
  maps/
    trial.tmx
  music/
```

推荐而非硬性要求的原因是：它缩短所有相对路径，避免依赖包装根透明化，也让开发目录与归档内部保持相同布局。`units`、`graphics`、`maps` 只是自组织目录名，具体是否被扫描和何时消费仍取决于对应加载阶段；不要把推荐树当成字段语法规范。

### 不推荐结构与原因

| 结构 | 风险 | 修复 |
|---|---|---|
| `包/甲/乙/丙/丁/mod-info.txt` | 依赖发现深度边界，修改包装后可能越界 | 提升元数据到归档根或最多一层包装 |
| `包/杂项很多/真正模组/mod-info.txt` | 上层条目数可能阻止下钻 | 让真正模组成为候选根 |
| `包/mod-info.txt/` 目录 | 同名但类型错误 | 使用普通文本文件 |
| `包/Mod-Info.TXT` 且资源工具大小写混乱 | 引擎发现可忽略大小写，其他打包工具未必一致 | 统一小写标准名 |
| `包/发布.rwmod/` 目录 | 明确无效 | 改为 `发布/` 目录或 `发布.rwmod` 文件 |
| `包/README/模组/mod-info.txt` | 文档包装混入发布根 | 发布时只压入模组内容 |

## 4. `.rwmod` 是只读 ZIP 虚拟文件系统

`.rwmod` 并非“游戏先解压再按普通目录加载”的约定。它以 ZIP 虚拟文件系统提供文件枚举和读取；正常情况下不需要、也不应依赖落盘解压。由此导出四项工程后果：

1. 打包后的路径是归档内部路径，不是开发机绝对路径。
2. 发布运行时不能写回归档内部；把缓存、日志、生成物设计为写入 `.rwmod` 是错误的。
3. 文件列举、目录存在性和资源读取必须能在虚拟文件系统内成立，不能只在工作目录版成立。
4. 一个在 Windows 目录版“碰巧找到”的大小写错误，在 ZIP 或其他平台上可能暴露为失败。

### ZIP 根与单包装目录透明化

若 ZIP 根只有一个包装目录，引擎可以把内层文件表现为归档根，以兼容一些压缩工具默认创建的顶层文件夹。因此这两种内部形态可能被读取为相似的逻辑路径：

```text
形态 A：归档根直接放文件
mod-info.txt
units/scout.ini

形态 B：归档根只有一个包装目录
星港包/mod-info.txt
星港包/units/scout.ini
```

但“可以透明呈现”不等于“应当依赖”。透明化的行为会使调试者难以通过肉眼区分逻辑根与物理根，而且任意额外根文件都可能改变“只有一个包装目录”的条件。发布前最稳妥的做法仍是让 `mod-info.txt` 位于归档逻辑根，并在压缩工具中检查归档列表，而不是只看资源管理器预览。

### 精确路径、分隔符与大小写

归档内部条目首先按精确文件名定位；随后存在不区分大小写的匹配回退。路径中的 `/` 与 `\` 会规范化。不要把这些容错层当作编码规范：

| 做法 | 引擎可能容忍 | 工程建议 |
|---|---|---|
| 写 `graphics\\ship.png` | 可规范化 | 统一写 `/`，便于 ZIP、跨平台和审阅 |
| 写 `Graphics/Ship.PNG`，真实条目为小写 | 可回退匹配 | 统一资源名与引用名的小写精确一致 |
| 将路径写成绝对盘符 | 不属于归档逻辑路径 | 永不写入模组配置 |
| 依赖 `..` 回退到包装外 | 语义不稳定且对继承明令不支持 | 重组资源或使用规定的根前缀 |
| 在同一 ZIP 放置只差大小写的两个文件 | 某层回退会产生歧义 | 禁止此类条目 |

归档文件名的读取采用 UTF-8，并有 ISO-8859-1 回退以兼容历史 ZIP。该回退只能解释“某些旧归档名可以被读到”，不能保证任意非 ASCII 文件名在所有打包器、平台和版本上无损。新工程推荐 ASCII 小写文件名、以英文连字符或下划线分词；显示给玩家的中文放入文本字段或本地化资源，而不要只依赖归档路径编码。

### `.rwmod` 打包前检查表

- [ ] 归档本身是单一普通文件，后缀为 `.rwmod`，不是同名目录。
- [ ] 归档逻辑根可直接看到 `mod-info.txt`，或明确验证仅有一层包装目录时的透明根行为。
- [ ] 所有内部路径使用 `/`，文件名与引用大小写精确一致。
- [ ] 没有两个仅大小写不同的条目。
- [ ] 不存在开发机绝对路径、临时目录、编辑器备份、版本控制目录或无关说明包装层。
- [ ] 文件名尽量使用 UTF-8 友好的 ASCII 集合；若必须使用非 ASCII，至少在目标平台从归档实际读取验证。
- [ ] 归档内容不是通过“解压后才能生成的文件”才完整；游戏读取时不会替你运行生成步骤。
- [ ] 只读条件下仍能完成资源读取；没有运行期试图修改包内文件的设计。

## 5. `mod-info.txt` 的定位与读取

`mod-info.txt` 是模组元数据入口，而不是单位配置。它通过同一个 INI 类解析器读取，但可读取的键、错误呈现与单位文件不能机械等同。代理应先把它放在逻辑源根，再填充最小必要信息。

### `[mod]` 中当前应使用的展示键

对于当前讨论的运行时，`[mod]` 显示字段是 `title`，不是 `name`。元数据读取会取得下列常用键：

| 键 | 作用 | 处理建议 |
|---|---|---|
| `title` | 模组列表和错误语境的显示标题 | 必填式对待；使用稳定、可区分的简短名称 |
| `description` | 列表或详情中的说明 | 文本可含字面 `\n`，读取后转换为实际换行 |
| `minVersion` | 最低游戏版本声明和兼容性门槛 | 与真实字段依赖一致；由版本解析器验证 |
| `thumbnail` | 缩略图相对路径 | 确认位于逻辑源根可达的资源路径 |

如果某份可读加载器摘要、旧教程或样例说 `[mod] name` 是名称，应视为低优先级旧说法；当前运行时读取 `title` 的原始行为覆盖它。不要为“兼容教程”把 `name` 当作主键。也不要在没有必要的情况下堆入不被元数据消费者读取的键，避免后续维护者误以为它们有效。

### 最小元数据示意

```ini
[mod]
title: 星港诊断包
minVersion: 1.15
description: 用于验证归档根与单位扫描\n不包含额外玩法依赖
thumbnail: graphics/preview.png
```

这是自写的结构示意，不能代替项目的实际版本选择。尤其是 `1.15` 只应在你的实现确实不承诺 1.14 时使用；若加入内存数组，则门槛必须提升到 `1.15p11`。缩略图的存在与格式也要经实际目标版本测试，不能仅因文本路径可见就判定图片已经加载。

### 描述中的换行

元数据读入后会把描述文本中出现的字面 `\n` 替换为换行字符。这是描述字段的显式呈现规则。请区分以下三种东西：

| 写入形式 | 读取后意图 | 适用位置 |
|---|---|---|
| `第一行\n第二行` | 两行说明 | `description` 的紧凑单行值 |
| 实际跨行的 INI 多行文本 | 由 INI 多行规则决定 | 需要按解析器多行语义审查 |
| `\\n` | 可能保留一个反斜杠加换行标记的不同组合 | 仅在确有展示需求时做运行验证 |

描述面向玩家，应说明兼容性、主要内容和必要前提，不应放入反编译路径、长调试日志、代理内部提示或第三方来源。为了日志可读性，标题最好不要与另一已安装模组重复；引擎会对相同标题给出调试困难的提示，但不会因为标题相同自动判断为同一内容。

### 缩略图路径的审计

`thumbnail` 的值会相对源根组合。检查它时不要只验证文件在开发目录存在，应验证以下关系：

```text
逻辑源根 + thumbnail 的相对值 = 归档或目录中实际可读取的条目
```

常见错误：

| 错误写法或布局 | 为什么失败或脆弱 | 正确方向 |
|---|---|---|
| `thumbnail: C:\work\mod\preview.png` | 绝对路径无法随包发布 | 改为源根相对路径 |
| `thumbnail: ../preview.png` | 包装根与虚拟路径语义不应依赖上跳 | 把文件放在源根内 |
| `thumbnail: Graphics/Preview.PNG`，条目全小写 | 可能依赖大小写回退 | 精确写 `graphics/preview.png` |
| 图片只存在于开发目录，压缩时漏掉 | 目录版通过、归档版失败 | 检查归档条目列表 |
| 把图片放进第二层包装外 | 元数据根调整后相对路径失效 | 让元数据与缩略图处于同一逻辑根 |

## 6. `minVersion` 是功能契约，不是营销标签

`minVersion` 不只是展示给玩家的说明。引擎会规范化 `v`、`a` 到 `h`、`p` 形式并检查当前版本是否满足要求。版本过低、格式不合法或当前游戏不足都会在加载早期造成问题。版本比较包括主版本、小版本和构建信息，不能用文本比较代替。

### 声明原则

1. 声明的是包的真实最低要求，而不是开发者正在使用的最高版本。
2. 新增功能若只在后期构建存在，必须提高门槛或改用较旧替代方案。
3. 单位内存数组依赖 `1.15p11`；使用它们时必须把 `minVersion` 设到至少 `1.15p11`。
4. 不要为了让旧客户端“试试看”而故意降低声明。早失败的版本提示优于深层解析或运行期崩溃。
5. 不要为了显得先进而无依据提高门槛。它会拒绝本可运行的用户，且让联机双方的约束更难管理。
6. 用户指定版本优先于代理的默认偏好。用户说“兼容 1.14”时，不能用 1.15 专属写法后只改一个文本声明来假装支持。

### 版本选择流程

```text
用户是否给出精确版本？
  是 -> 以该版本作为验证基线
  否 -> 是否要求区间兼容？
           是 -> 以区间下限为实现基线
           否 -> 标记版本未知，先询问；必须继续时不声称跨线兼容

是否使用后期特性？
  是 -> 查该特性的最小版本；提高 minVersion 或选择替代
  否 -> 保持现有合理下限并执行最小加载测试
```

### 版本门槛的审阅表

| 改动类型 | 是否通常需要重审 `minVersion` | 原因 |
|---|---|---|
| 改 `title` 或说明文字 | 是，但通常不需改值 | 确认没有同时引入版本依赖 |
| 调整已有数值 | 是，快速复查即可 | 某些字段本身可能旧版不同 |
| 新增逻辑、内存、动态表达式 | 是，必须 | 解析能力可能有版本门槛 |
| 复制旧模组的模板 | 是，必须 | 模板可能隐藏后期字段 |
| 换成 `.rwmod` 发布 | 是，检查但未必调整 | 压缩路径与版本声明是不同问题 |
| 增加地图或资源 | 是，检查资源与加载路径 | 不能把素材失败误判为版本失败 |

## 7. 目录发现与单位扫描不是一回事

有一个常见错误：看到元数据发现可以下钻，就假定任何嵌套目录中的 `.ini` 都会自动作为单位加载。事实并非如此。元数据下钻只是在候选模组中寻找 `mod-info.txt` 并确定源根；单位加载有它自己的目录 walker、后缀筛选、递归深度和模板规则，详见 [02](02-ini-parser-templates-and-inheritance.md)。

因此，下面的推理是错误的：

```text
“引擎在三层深处找到了 mod-info.txt，
 所以它肯定会把模组候选根之外所有 ini 都载入。”
```

正确推理是：

```text
“引擎找到了元数据并选择了一个逻辑源根；
 接下来仍要按单位扫描入口验证哪个子目录、哪些后缀和哪些深度被处理。”
```

这一区分会影响打包修复。若元数据在内层而单位仍在外层，源根改变后资源和单位路径可能失配。不要靠“多放一份单位文件”修补；应该把元数据、单位、图像和地图组织在同一逻辑源根之下。

## 8. 诊断剧本

### 剧本 A：目录模组完全没有显示

1. 确认实际安装位置是游戏枚举的用户模组目录，而非仓库、下载目录或上层聚合目录。
2. 确认候选对象是普通目录，不是名为 `x.rwmod` 的目录。
3. 在候选根直接检查是否存在 `mod-info.txt`；若依赖内层发现，检查每层深度和上层条目数量。
4. 将临时最小元数据提升到根目录做隔离验证。不要同时加入单位文件，以免把注册问题和 INI 问题混在一起。
5. 若出现条目，恢复推荐结构并再添加内容。

通过标准是“出现可辨识的模组记录”，不是“单位已出现在建造菜单”。

### 剧本 B：目录版可见，`.rwmod` 版不可见

1. 检查发布物是否真的是一个 `.rwmod` 文件。
2. 列出归档内部路径，检查 `mod-info.txt` 是否在逻辑根或唯一包装根。
3. 检查压缩工具是否把整个上层文件夹、隐藏的版本控制目录或一个空父目录压入了根。
4. 比较目录版和归档版的相对路径，而不是比较宿主绝对路径。
5. 检查归档是否包含所有元数据引用的缩略图和任何必需内容。
6. 用相同的游戏版本、相同启用状态重新扫描，避免把缓存或旧记录误当成当前归档行为。

### 剧本 C：列表有模组但标题不对

1. 打开实际被发现的逻辑源根内的 `mod-info.txt`，不是工作区里另一份同名文件。
2. 确认有 `[mod]` 节和 `title`，不要使用 `name` 作为替代。
3. 检查是否存在多层包装导致读到意外的另一份元数据。
4. 检查是否有同 `title` 的已安装模组；标题冲突会让日志诊断含混。
5. 若描述换行异常，检查是字面 `\n`、真实跨行还是多层转义问题。

### 剧本 D：版本提示与预期不同

1. 记录当前游戏完整版本和 `minVersion` 原文本。
2. 不要通过字符排序自行判断 `p` 构建高低；使用引擎的规范化语义。
3. 检查是否使用了需要更高版本的特性，尤其是内存数组的 `1.15p11` 门槛。
4. 如果用户要求低版本兼容，选择删除后期依赖的实现，而不是只降低 `minVersion`。
5. 若文本格式本身错误，修正格式后先验证元数据加载，再处理单位层错误。

### 剧本 E：缩略图在目录版正常、归档版缺失

1. 用归档内部逻辑根计算 `thumbnail` 的相对位置。
2. 精确比较引用名与条目名，包括大小写和扩展名。
3. 确认图片没有被打包规则排除，也不在包装根之外。
4. 改为一个小写 ASCII 文件名进行最小试验，排除文件名编码与回退匹配因素。
5. 最后才检查图像格式、尺寸或渲染限制；先证明文件能被找到。

## 9. 开发目录与发布归档的双态流程

推荐把开发和发布视为两个必须分别验证的状态，而不是把压缩理解为无意义的最后一步。

### 开发态

- 普通目录，根部就有 `mod-info.txt`。
- 资源和单位都采用源根相对路径。
- 允许编辑器临时文件存在于工作区，但不要让它们参与发布清单。
- 每次调整路径、元数据、模板或单位层级后重扫。
- 使用可读的结构和短路径，便于最小复现。

### 发布态

- 明确的 `.rwmod` 文件。
- 归档逻辑根与开发根同构，最好没有包装层。
- 归档条目经检查，不含开发机垃圾、私密材料、内部反编译内容或第三方未经授权内容。
- 在从未使用开发目录的干净安装环境中验证，避免目录版残留资源掩盖打包遗漏。
- 记录打包时间、游戏版本、`minVersion` 和内容摘要，以便联机问题追踪。

### 发布审计矩阵

| 项目 | 目录版检查 | `.rwmod` 版检查 | 失败后优先修复 |
|---|---|---|---|
| 注册 | 游戏能发现目录 | 游戏能发现归档文件 | 安装位置、对象类型、归档根 |
| 元数据 | `title`、说明、版本正常 | 与目录版一致 | 逻辑源根与实际元数据文件 |
| 缩略图 | 相对路径可读 | 条目已被压入且精确匹配 | 打包清单和大小写 |
| 单位 | 预期文件被扫描 | 预期文件同样被扫描 | 目录同构和后缀/路径 |
| 地图 | 文件枚举正常 | 虚拟文件系统可枚举 | 归档内部路径 |
| 联机 | 本地包稳定 | 双方同一归档内容 | 版本、启用状态、发布物哈希 |

## 10. 与安全和版权有关的发布界限

发布 `.rwmod` 不等于把工作区全部内容压缩。归档应只包含运行所需的自有或已获授权资源、元数据、配置和必要地图。特别禁止将以下内容混入发布物：

- `W:\mao\tx\tools\decompilers\game-lib-src` 的任何源码、反编译文件、长摘录或派生可重建实现。
- `W:\mao\tx\模组加载器` 的内部材料、日志、模拟输出或大段可读摘要。
- DeepStar 或 `模组实例` 中复制来的完整配置、图像、音频、地图或未经许可的资源。
- 访问令牌、个人路径、编辑器缓存、版本控制目录、构建日志和无关测试产物。

对外说明可写“已根据内部行为研究核对路径与版本规则”，但不应公开内部源树细节。审阅者需要的是可复核的行为、版本和测试，不是可再分发的受限材料。

## 11. 发现层的最终检查清单

在认为“模组加载问题已解决”前，完成以下检查：

- [ ] 清楚写出当前诊断在哪个阶段完成，后续阶段是否仍未验证。
- [ ] 模组候选是普通目录或真实 `.rwmod` 文件，不是伪装目录。
- [ ] `mod-info.txt` 位于逻辑源根，未依赖脆弱的深层发现。
- [ ] `[mod] title` 已填写，未以 `name` 替代展示名。
- [ ] `description` 中的 `\n` 预期经过了显示验证。
- [ ] `thumbnail` 以源根相对路径指向实际存在且打包进入的条目。
- [ ] `minVersion` 使用真实需要的版本，内存数组场景至少为 `1.15p11`。
- [ ] 新模组是否启用已单独确认，没有把默认禁用误判成读取失败。
- [ ] 目录版和 `.rwmod` 版分别完成了发现与元数据检查。
- [ ] 所有路径与文件名在归档中精确一致，未依赖大小写回退或宿主绝对路径。
- [ ] 报告没有转录内部反编译源码或第三方完整配置。
- [ ] 任何尚未运行测试的断言标为 `待运行验证`，没有夸大为全平台兼容。

发现层正确后再进入单位扫描和配置语义；不要让字段调优掩盖一个尚未建立的源根或压缩包问题。
