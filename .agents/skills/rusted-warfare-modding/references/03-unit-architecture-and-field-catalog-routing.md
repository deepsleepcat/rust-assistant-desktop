# 单位架构与字段目录路由

导航：任务入口见 `../SKILL.md`；证据优先级、版本与不确定性标签见 [00-source-authority-and-versioning.md](00-source-authority-and-versioning.md)；模组根、元数据与 `.rwmod` 见 [01-mod-discovery-rwmod-and-metadata.md](01-mod-discovery-rwmod-and-metadata.md)；INI、继承和自动模板见 [02-ini-parser-templates-and-inheritance.md](02-ini-parser-templates-and-inheritance.md)。

本页不是完整字段手册。完整候选字段目录位于 `assets/ai/references/rusted-warfare-modding.md`；本页的职责是帮助编码代理把一个玩法需求路由到正确的区段、相关对象、加载阶段、证据路径和测试方案。任何精确字段语法都必须先在该目录检索，再回到 `W:\mao\tx\tools\decompilers\game-lib-src` 的目标版本实现核对，绝不凭记忆补全字段名。

范围是 Rusted Warfare `1.14`/`1.15` 自定义单位。本文不复制内部反编译源码、内部加载器材料或第三方模组完整配置；所有小片段仅表达自写的架构意图，不能替代字段目录和目标版本验证。

## 1. 为什么字段路由比字段背诵重要

单位配置不是一张扁平键值表，而是一个由区段、命名前缀、对象引用和生命周期组成的图。一个“让单位发射炮弹”的需求至少可能涉及 `[core]` 的身份、`[attack]` 的全局能力、`[turret_NAME]` 的发射位置和条件、`[projectile_NAME]` 的伤害与飞行、`[graphics]` 的图片、`[effect_NAME]` 的表现，以及动作、AI 或资源对开火时机的影响。

如果代理只搜索一个看起来像的字段，容易出现四类问题：

| 问题 | 根因 | 正确做法 |
|---|---|---|
| 键拼写正确却无效 | 放在了错误区段，消费者不读取 | 先定位对象类型与区段 |
| 单位能加载但行为错 | 只改了定义层，没有改关联对象 | 沿引用链检查生命周期 |
| 模板覆盖看似失效 | 关键键来自更近层或子层 | 绘制键来源与合并顺序 |
| 旧字段加载告警或表现不稳定 | 使用遗留路径或版本限定能力 | 查字段状态与目标版本实现 |

字段目录的正确使用方式是“索引到证据”，而不是“抄表即结束”。对于每个新增或修改字段，至少回答：

1. 它属于哪个区段或命名前缀？
2. 它读取成什么类型，何时被读取？
3. 哪些字段或对象会引用它，是否有先后或唯一性要求？
4. 它是否被模板、动作、单位转换或版本规则改变？
5. 如何在目标版本证明确实运行，而非仅仅没有报错？

## 2. 单位的架构图

把自定义单位理解为以下层次：

```text
模组源根与版本门槛
  -> 单位文件与继承后的 INI 映射
    -> [core] 建立单位身份和基础能力
      -> 基础区段定义移动、图像、攻击、AI、建造等子系统
        -> 命名前缀区段定义可复用或可引用对象
          -> 动作、触发、投射物、效果、附件、资源和逻辑表达式连接
            -> 运行期状态：生成、选择、移动、攻击、建造、受伤、死亡、转换、联机
```

这是一张依赖图，不是严格的文本书写顺序。配置阅读时可按架构顺序理解，写入时仍要遵循各区段的解析要求和引用约束。不要因为某个定义放在文件后部就断定它不能被前部引用；是否允许前向引用要看具体对象加载方式。但对维护性而言，将相关对象放在相邻区域、统一命名、避免模糊别名，仍然是低风险做法。

### 核心对象类别

| 类别 | 常见区段模式 | 它代表什么 | 典型消费者 |
|---|---|---|---|
| 单位身份 | `[core]` | 名称、分类、生命、费用、版本/严格性等根属性 | 全部后续子系统 |
| 全局外观 | `[graphics]` | 主体图像、阴影、方向帧、界面表现 | 渲染、选择、死亡表现 |
| 总体攻击能力 | `[attack]` | 可否攻击、目标类别、全局距离或瞄准模型 | 炮塔、目标选择、AI |
| 炮塔 | `[turret_NAME]` | 发射器、角度、冷却、目标限制 | 攻击调度、动画、投射物 |
| 投射物 | `[projectile_NAME]` | 直接/范围伤害、速度、命中、分裂和特效 | 炮塔、动作、运行期碰撞 |
| 移动 | `[movement]` | 移动类型、速度、加速、转向 | 路径规划、物理、AI |
| AI | `[ai]` | AI 的角色和目标偏好 | 自动建造、攻击、运输、采集 |
| 生产与放置 | `[canBuild_NAME]`、`[placementRule_NAME]` | 菜单条目、可建造目标、放置限制 | 工厂、建造者、界面 |
| 动作 | `[action_NAME]`、`[hiddenAction_NAME]` | 玩家命令、队列、自动触发和状态变换 | UI、事件、资源、单位状态 |
| 资源 | `[resource_NAME]`、`[global_resource_NAME]` | 单位局部或团队全局资源 | 价格、动作、生产、逻辑 |
| 表现对象 | `[effect_NAME]`、`[animation_NAME]`、`[decal_NAME]` | 特效、骨骼/帧动画、贴花 | 开火、移动、命中、死亡 |
| 结构对象 | `[attachment_NAME]`、`[leg_N]`、`[arm_N]` | 挂接子单位、机械腿/手臂 | 单位构造、移动、渲染、目标关系 |
| 模板对象 | `[template_NAME]` 及模板文件 | 节内或文件级复用 | 解析和合并阶段 |

名称中的 `NAME`、`N` 或类似占位符不是可直接写入的字面值。它们表示你选择的唯一标识。标识应采用小写 ASCII、短横线或下划线的一致风格，避免空格、中文、大小写变体和与现有对象近似的名称。展示名与内部标识分离：玩家可见文本可本地化，内部引用必须稳定。

## 3. 生命周期驱动的路由法

面对一个需求，先问“它在单位生命的哪个阶段发生”，再问“哪个字段能实现”。这样比从字段表顶部向下翻更可靠。

| 生命周期阶段 | 业务问题 | 首选路由 | 关联检查 |
|---|---|---|---|
| 模组进入列表 | 为什么不可见、版本拒绝、标题错误 | `mod-info.txt` | 源根、`title`、`minVersion`、启用状态 |
| 文件加载 | 为什么单位没有被发现 | 单位 walker 与模板 | `.ini`、`.tmx`、递归深度、目录模板 |
| 单位构造 | 名称、成本、血量、身份是什么 | `[core]` 与继承 | `copyFrom`、重复键、版本要求 |
| 出现在地图 | 初始生成、建造完成、附属生成 | `[core]`、动作、附件、地图 | 队伍、建造状态、引用存在性 |
| 被选择和显示 | 图片、选择框、说明、血条 | `[graphics]`、文本 | 资源路径、方向帧、UI 开关 |
| 接受命令 | 移动、攻击、建造、生产 | `[movement]`、`[attack]`、`[canBuild_*]`、动作 | AI 与玩家权限是否冲突 |
| 寻敌与开火 | 目标可否攻击、炮塔怎样转、发射什么 | `[attack]`、`[turret_*]`、`[projectile_*]` | 射程、标签、目标类别、引用名 |
| 弹体命中 | 伤害、范围、效果、分裂、资源变化 | `[projectile_*]`、`[effect_*]`、mutator 类字段 | 友伤、目标过滤、递归生成 |
| 移动和路径 | 地面/空中/水面、速度、转向 | `[movement]`、腿/臂、图形效果 | 地形通行、攻击移动模型 |
| 经济和生产 | 价格、资源、队列、建造菜单 | `[core]`、资源节、`[canBuild_*]`、动作 | AI 使用、锁定条件、单位上限 |
| 自动行为 | 定时、受伤、完成、队列、事件 | `[hiddenAction_*]`、`[action_*]`、LogicBoolean | 名称唯一、事件时机、循环 |
| 受伤/死亡/转换 | 爆炸、生成、队伍变化、替换 | 核心死亡字段、投射物、动作、附件 | 资源释放、附属处理、联机一致性 |

同一个玩法需求经常跨行。例如“建造一个可部署炮台的工程车”至少涉及：工程车的核心身份、移动与 AI 建造者属性、生产或动作入口、建造项及放置规则、炮台独立单位文件、炮台的攻击与投射物、两者资源和版本门槛。把需求拆成生命周期阶段后，每一部分都能独立验证。

## 4. 字段目录的标准检索程序

现有字段目录 `assets/ai/references/rusted-warfare-modding.md` 包含按区段整理的候选字段。使用它时采用以下五步，而不要直接复制第一条匹配：

### 第一步：用功能词找到区段簇

例如：

| 想实现的能力 | 先查的目录章节 | 必须联查的章节 |
|---|---|---|
| 攻击范围和目标类别 | Attack | Turret、Projectile、AI、LogicBoolean |
| 炮口、后坐、预热 | Turret | Attack、Projectile、Animation、Effect |
| 爆炸、穿透、分裂 | Projectile | Effect、Spawn Projectiles、Tags/Logic |
| 造单位、菜单锁定 | CanBuild、Action | Core、Resources、AI、PlacementRule |
| 单位切换形态 | Action | Core、Graphics、Attachment、Animation |
| 自动反应 | HiddenAction/Action | LogicBoolean、Resources、Projectile |
| 自定义货币或能量 | Resources | Core、Action、CanBuild、LogicBoolean |
| 可运输、挂接、子体 | Core transport、Attachment | Action、AI、Movement |
| 图像和方向动画 | Graphics | Animation、Turret、Leg/Arm、Effect |
| 地形移动或悬浮 | Movement | Core、Attack、AI、Graphics |

这一步只给出“去哪一组章节”，不表示一个区段独自足以完成能力。

### 第二步：记录精确候选，而非改写名称

把字段目录中的精确大小写、下划线、前缀、节名和值类别抄到任务笔记。例如记录“候选位于 `[turret_NAME]`，值类别为对象引用”，而不是记成“好像叫 projectile”。字段名很容易因为旧教程、习惯缩写或不同语言翻译而偏离。自动编辑前还要检查项目内是否已有一致写法。

### 第三步：在原始引擎确认目标版本

查找时关注四件事：

1. 该节或前缀是否被枚举。
2. 该键是否被以预期类型读取。
3. 读取后是否受版本、严格级别、对象存在性或组合条件约束。
4. 它是否在运行期有消费者，还是已进入遗留路径。

如果原始材料难以阅读，不要把可读加载器摘要抬升为最终裁决。使用它定位类或方法，然后回到原始路径。结论写为“已证实”“版本限定”或“待运行验证”，并注明检查的版本范围。

### 第四步：追踪邻接依赖

字段不是孤立的。新建 `[turret_main]` 时要确认它所指向的投射物是否存在、攻击全局是否允许该目标类别、图片是否可读、动作是否通过同名引用触发。新建资源时要确认生产、价格和条件表达式使用的是同一资源域。新建动作时要确认动作名称唯一、事件触发不会自循环、需要的目标或动画已声明。

### 第五步：用最小战局验证

不要把“文件不报错”当成功。最小战局应只包含足以触发本次链路的对象，例如：

- 新炮塔：生成单位、放置一个可攻击目标、观察索敌、旋转、开火、命中和效果。
- 新建造项：生成生产者、检查菜单位置与锁定、支付资源、完成队列、检查产物归属。
- 新隐藏动作：制造精确事件，检查是否只触发一次、资源和状态是否按预期改变。
- 新移动类型：在至少两种地形、手动命令与 AI 命令下测试。

用最小战局的优势是把素材、地图、联机和其他复杂脚本从当前断言中隔离。完成后再与完整模组组合测试。

## 5. `[core]`：单位身份、约束与全局根

`[core]` 是单位最先需要理解的区段。它不只是“基础数值”，还承担单位内部名称、类、成本、生命、标签、建造/运输/死亡等跨系统根属性。字段目录中 `[core]` 及其通用分组是审计任何单位时的起点。

### 路由问题表

| 需求 | 优先查看 | 不要误放到 |
|---|---|---|
| 内部单位名、别名、类别 | `[core]` 身份字段 | `mod-info.txt` 的 `title` |
| 基础生命、质量、价格、科技层 | `[core]` 基础数值 | `[attack]` 或 `[graphics]` |
| 初始建造状态、单位上限 | `[core]` 建造/生产相关项 | 独立 `canBuild` 菜单项 |
| 运输容量或载员限制 | `[core]` 运输组 | `[attachment]` 的子体结构 |
| 死亡爆炸、死亡生成、残骸 | `[core]` 死亡组并联查效果/投射物 | 仅在图形区段加死亡图片 |
| 标签、团队与可攻击限制 | `[core]` 与 Attack/AI 联查 | 只靠动作 UI 条件 |
| 版本和严格性 | `[core]` 并联查 `mod-info.txt` | 只改文本说明 |

### 核心审计的八个问题

1. 内部 `name` 是否唯一且稳定？它与 `[mod] title` 是不同层级，前者不是模组展示名。
2. 是否存在 `copyFrom`，且最终身份字段被父模板意外填充？
3. `strictLevel` 是否在允许范围，是否会放大现有历史错误？
4. 成本、生命和质量的数值单位是否来自字段目录和目标实现，而非玩家界面直觉？
5. 单位是否被标记为建筑、移动单位、资源、运输体或其他跨系统角色，角色组合是否自洽？
6. 标签是否有多余空格、大小写变体或与 AI、攻击过滤条件不一致的命名？严格模式下尤其要查。
7. 任何死亡、生成、转换或替换引用是否已定义，并在最小战局触发？
8. 该单位是否隐式依赖后期版本特性，导致 `mod-info.txt` 的 `minVersion` 必须提高？

### 身份与显示分离

代理最容易混淆三种“名字”：

| 名称 | 所在层 | 主要用途 | 不能代替 |
|---|---|---|---|
| 模组 `title` | `mod-info.txt [mod]` | 模组列表展示 | 单位内部名称 |
| 单位 `name` | `[core]` | 引用、生产、替换、网络或内部识别 | 玩家显示文本 |
| 本地化显示名/描述 | 本地化或相关文本字段 | 玩家 UI | 稳定对象标识 |

修改名字前先判断用户到底想改哪一层。把单位 `name` 改成中文来修模组列表标题，或者把 `title` 改成单位内部 ID，都会扩大引用破坏面。

## 6. `[graphics]`：渲染不是纯装饰

`[graphics]` 管理主体图片、阴影、团队色、方向帧、选择与状态条等。它通常与文件路径、方向逻辑、炮塔图像、动画、低血量效果和渲染层产生耦合。图像问题优先按路径与加载阶段排查，不能只从颜色或尺寸猜。

### 图形问题的路由

| 现象 | 首查 | 次查 | 常见误判 |
|---|---|---|---|
| 完全不显示主体 | `[graphics]` 图片字段与相对路径 | `.rwmod` 条目、逻辑源根、文件名大小写 | 以为是移动或攻击字段问题 |
| 朝向不对、帧错位 | 方向帧/步幅字段 | 主体旋转、炮塔/腿锁定、图像表布局 | 修改图片文件名而不查帧参数 |
| 炮塔图像不动 | 炮塔图像和旋转设置 | `[turret_*]` 角度、附着关系、主炮塔 | 只调整 `[attack]` |
| 阴影缺失或偏移 | 阴影字段、资源路径、偏移 | 高度、方向锁定、图层 | 用主体图替代阴影掩盖路径问题 |
| UI 条异常 | 血条/能量/运输/队列显示字段 | 单位实际能力、资源和运输配置 | 只通过隐藏 UI 回避数值错误 |

### 图形资源审计

1. 用模组逻辑源根计算每条相对资源路径；目录版与 `.rwmod` 版都应命中同一逻辑条目。
2. 文件名与引用大小写精确一致，尽量使用小写 ASCII 文件名。
3. 检查单包装目录透明根是否改变了你想象的路径基准。
4. 把主体、炮塔、阴影、特效、动画分开验证，不要因其中一张图片正常就判定整个图形区段正确。
5. 若使用团队色、帧图或方向帧，验证至少两个朝向、两支队伍、移动和静止状态。
6. 在低血量、建造中、运输中、转换形态后也检查图像，因为不同状态可能读取不同资源或层。

### 旧动画字段的谨慎处理

字段目录包含一些已弃用或遗留动画写法。遇到这类字段时，不要因为它们仍被目录列出就作为新实现的首选。先在原始目标版本查是否仍读取、是否有替代的 `[animation_NAME]` 机制、以及是否只保留兼容路径。新内容优先使用当前明确的动画路由；维护旧模组则采用“最小改动、单独测试、标记遗留”的策略，避免为追求新式而改变成熟单位的时序。

## 7. `[attack]`、`[turret_NAME]` 与 `[projectile_NAME]`：一条武器链

武器系统至少有三层，任何一层漏配都可能表现为“不能打”“打错目标”“有炮塔无伤害”或“弹体出错”。

```text
[attack]
  决定单位整体是否具有攻击能力、目标类别和全局限制
    -> [turret_NAME]
         决定从哪里、何时、朝向何处、以何限制发射
           -> [projectile_NAME]
                决定发射物飞行、命中、伤害、效果与后续生成
```

### `[attack]` 的职责

`[attack]` 是总体攻击模型。字段目录在该章节列出攻击开关、射程、目标类别、近战/攻击移动、炮塔旋转相关候选。路由原则：单位层面“能否攻击什么、总距离和总策略”优先在此寻找；某一发射器的例外才放到炮塔。

审阅时问：

- 单位是否整体允许攻击？
- 地面、空中、水下或其他目标类别的允许与炮塔局部覆盖是否一致？
- 射程、攻击移动和固定射击模型是否与移动能力相容？
- 多炮塔是否需要不同目标，还是应共享目标？
- 标签筛选是否与目标单位的标签体系一致？
- AI 是否把该单位当作攻击者，还是被其他设置禁用？

不要在 `[attack]` 堆入单个炮塔的枪口坐标、后坐、冷却或投射物引用；那会导致未使用键或错误行为。

### `[turret_NAME]` 的职责

炮塔对象连接单位攻击意图与具体投射物。常见候选包括位置、方向、附着关系、可否射击、延迟、预热、资源消耗、局部目标限制、炮口、图像、后坐、开火动画和开火触发动作。一个炮塔不是“画在主体上的装饰”，它需要有效投射物与整体攻击语境。

### 炮塔审核矩阵

| 检查项 | 问题 | 常见后果 |
|---|---|---|
| 唯一名称 | `[turret_NAME]` 的 NAME 是否与引用一致 | 动作或附件引用失效 |
| 坐标与高度 | 是否在预期局部坐标与层级 | 炮口漂移、贴图错位 |
| 投射物 | `projectile` 指向存在的 `[projectile_NAME]` | 加载时找不到引用或不开火 |
| 目标限制 | 局部限制是否意外比 `[attack]` 更严 | 单位可攻击却炮塔不发射 |
| 冷却与预热 | 延迟、预热、联动关系是否形成死锁 | 永远预热、连续开火、不同步 |
| 方向和附着 | `attachedTo`、从属、旋转限制是否无环 | 炮塔角度异常或加载失败 |
| 资源 | 能量/资源消耗是否与单位资源定义一致 | 开火后资源异常或永不发射 |
| 表现 | 图像、后坐、光效、动画引用是否可读 | 逻辑开火但无视觉或运行异常 |
| 触发 | 开火触发动作是否唯一且不自循环 | 资源刷取、连锁失控 |

同名炮塔或炮塔引用不应该靠继承顺序“最后覆盖”。把需要差异化的炮塔明确命名，例如 `main_gun`、`anti_air`、`repair_beam`，而不是 `turret1_new` 一类临时名。炮塔数量、索引上限和特定名称保留规则应以目标版本字段目录与引擎为准，不凭旧样例猜测。

### `[projectile_NAME]` 的职责

投射物承担伤害、范围伤害、速度、寿命、目标跟踪、瞬发、抛物、友伤、命中效果、分裂、刷弹和 mutator 条件等。它的路由关键是“弹体行为”，不是单位身份或炮塔位置。一个完整的投射物审阅要看：

| 领域 | 要确认的关系 |
|---|---|
| 基础 | ID 唯一；至少由明确炮塔或动作引用；生命周期可结束 |
| 伤害 | 直击与范围伤害的意图明确；友伤与装甲修正经过目标测试 |
| 运动 | 速度、寿命、引导、重瞄、抛物或瞬发模型一致 |
| 目标 | 目标类别和标签过滤不与炮塔/攻击层冲突 |
| 视觉 | 图片、光线、爆炸和自定义效果均有实际资源或定义 |
| 连锁 | `spawnProjectilesOn...` 类机制不会产生无界递归或版本限定隐患 |
| mutator | 条件、标签和资源副作用有可控最小复现 |

### 武器链最小验证顺序

1. 先让单位在无复杂效果、无连锁、无资源消耗的条件下获得一个可攻击目标。
2. 验证炮塔转向、冷却和发射事件。
3. 验证投射物实际生成并命中，而不是只看到炮口效果。
4. 验证直接伤害、范围伤害、友军、空中/地面类别各自符合意图。
5. 再加动画、特效、预热、资源消耗、标签过滤、分裂、重瞄和动作触发。
6. 最后在 AI 控制、移动中、低资源、运输/附件和联机等组合环境复测。

这种分层能避免“分裂弹不工作”实际是基础炮塔从未发射的情况。

## 8. `[movement]`、腿/臂与移动表现

移动能力是路径规划、地形通行、目标选择、攻击移动、AI 和图形表现的共同基础。`[movement]` 负责单位总体移动类型、速度、加速和转向等；`[leg_N]`、`[arm_N]` 增加机械肢体的局部结构和动画约束。不要把腿/臂 `copyFrom` 与文件级 `copyFrom` 混为一谈：它们有字段特定的引用语义与加载顺序要求。

### 需求路由

| 需求 | 应先查 | 联查 |
|---|---|---|
| 能否走陆地、水面、空中、悬浮或越崖 | `[movement] movementType` 类候选 | 地图地形、攻击移动、AI |
| 加速、最高速度、转向 | `[movement]` 数值 | 固定射击、炮塔旋转、动画效果 |
| 机械脚着地和摆动 | `[leg_N]` | 图形、移动速度、肢体引用顺序 |
| 手臂指向和关键帧 | `[arm_N]`、动画 | 炮塔、附件、渲染层 |
| 移动时的尘土、水花、效果 | `[graphics]` 的运动表现 | Effect、地形与移动类型 |
| 运输体脱离/接载后的移动 | Core transport、Attachment、Action | AI、队伍、路径点 |

### 移动验证格

对每个新移动设计，至少测试：

| 场景 | 目的 |
|---|---|
| 静止、短距离移动、长路径移动 | 检查启动、加速、停下和转向 |
| 预期可通行地形 | 证明移动类型真能使用该路径 |
| 预期不可通行地形 | 防止错误穿越或卡死 |
| 手动移动命令 | 检查玩家交互 |
| 攻击移动/追击 | 检查攻击模型与运动耦合 |
| AI 控制 | 检查角色识别与路线选择 |
| 运输、附属、转换形态 | 检查状态转移后的路径保留 |
| 图像方向、腿/臂、阴影和效果 | 检查表现跟随逻辑 |

不要只在平坦陆地上测试一个空中或水上单位。许多移动错误只在地形边界、目标不可达、攻击中停顿或单位转换后出现。

## 9. `[ai]`：不是玩家逻辑的副本

`[ai]` 指定 AI 应如何使用单位，例如建造者、运输者、攻击者、采集者、禁用使用、升级优先级、建筑目标偏好等。它不替代 `[core]` 的实体能力，也不替代 `[action_*]` 的执行结果。AI 配置必须建立在单位真的拥有相应能力的基础上。

### AI 诊断表

| 现象 | 先查 | 再查 |
|---|---|---|
| AI 从不生产单位 | `[ai] disableUse`、建造入口、价格 | 前置科技、队列、地图资源 |
| AI 生产后不攻击 | 攻击能力与 `useAsAttacker` 类角色 | 射程、目标类别、移动和标签 |
| AI 不修建/回收 | `useAsBuilder`/采集角色与核心能力 | 建造菜单、目标过滤、地形 |
| AI 不运输 | 运输容量与 `useAsTransport` | 可装载标签、路径、卸载动作 |
| AI 行为过于激进或错误目标 | AI 目标优先级和敌方可选性 | `[attack]` 筛选、单位标签、不可攻击设置 |

AI 是运行期消费者，静态字段不报错只能证明其被读取。每当新增单位角色，至少做一场无人干预的 AI 对战或脚本化观察，并把“AI 未验证”与“AI 禁用”区分开。不要为了让 AI 选择单位而把玩家界面锁定条件删掉；应分别审查生产可见性、AI 可用性与资源经济。

## 10. 建造、生产、放置与资源的路由

生产系统由多个层次组成：单位是否可被生产、哪个单位提供菜单项、菜单项锁定条件、价格使用什么资源、产物何时出现、能否放置、AI 是否理解该项。`[canBuild_NAME]` 不是孤立的“造单位字段集合”，它与核心生产能力、资源、动作、放置规则和 AI 相互引用。

### 建造链

```text
生产者或建造者的基础能力
  -> [canBuild_NAME] 菜单/队列条目
    -> 目标单位内部名称或特殊目标
      -> price / resource / lock 条件
        -> 需要时 [placementRule_NAME] 限制位置
          -> 产物的建造状态、队伍与 AI 角色
```

### 两类建造入口

字段目录中既有 `[canBuild_NAME]` 节，也保留一些旧式或内联 `canBuild_#_...` 风格。新实现不要仅凭“目录里都列出”就任选其一。需要：

1. 在目标引擎确认该形式是否仍是当前优先路径、是否有限制或兼容目的。
2. 检查项目既有单位使用哪种已验证风格，避免同一生产者混入两套难审计表达。
3. 对于保留的旧包，先确认其行为再进行最小迁移，不能全局替换后假定菜单顺序不变。
4. 注意 `canBuild_` 前缀属于重复检查的特殊命名空间；同名条目不可依赖最后定义覆盖。

### 建造问题分流

| 症状 | 优先层 | 关键问题 |
|---|---|---|
| 菜单没有条目 | `canBuild` 定义与生产者 | 条目是否被枚举，目标名是否存在，是否被锁定 |
| 条目灰色 | 锁定条件、资源、技术条件 | 是 `isLocked` 还是价格不足，提示是否明确 |
| 点击无反应 | 队列/动作与目标引用 | 是否允许建造、是否有产物、是否被玩家权限限制 |
| 产物生成即消失 | 产物核心/队伍/建造状态 | 是否有错误转换、死亡、资源或地图限制 |
| 建筑无法放下 | PlacementRule 与移动/地形 | 规则是否意外排除所有格子 |
| AI 从不造 | AI 与菜单条目 | AI 是否能用，优先级与资源是否合理 |

### 资源域

资源不仅是 `price` 数字。字段目录区分普通费用、局部资源、全局资源、动作资源、投射物/ mutator 资源和条件表达式。代理必须明确“资源属于单位还是队伍”“变化发生在何时”“AI 是否能评估”“资源为空时动作是否仍能触发”。

| 资源需求 | 首查区域 | 需要追踪 |
|---|---|---|
| 单位造价 | `[core]` 与资源格式 | 生产菜单、AI 预算、建造完成时机 |
| 菜单项覆盖价格 | `[canBuild_*]` | 目标单位基础价格与锁定条件 |
| 动作消耗/奖励 | `[action_*]` | 触发时机、取消、冷却、资源域 |
| 开火消耗 | `[turret_*]` | 能量、局部资源、射击失败条件 |
| 采集/转换 | 核心资源、动作、资源定义 | 目标范围、团队关系、上限 |
| 全局经济 | `[global_resource_*]` | AI 等价映射、界面显示、队伍共享 |

资源漏洞常由“显示资源”和“实际消费资源”不同造成。测试必须记录动作前后数值、AI 与玩家两方、成功/失败/取消路径，而不是只看按钮可否点击。

### 放置规则

`[placementRule_NAME]` 与建造项共同决定建筑能否在特定位置放置。它不是图形特效，也不是移动类型的替代。排查放置失败时先通过极简规则验证生产流程，再逐步加入地形、距离、单位密度、标签或团队条件。若规则复杂，应为每一个规则命名并设计一个“应允许”和“应拒绝”的地图格测试，不要只测一个失败点。

## 11. 动作与隐藏动作：状态机边界

`[action_NAME]` 通常对应可见或可执行的动作，`[hiddenAction_NAME]` 承担自动触发、事件响应、内部状态转移等。两者都可能与资源、生产、单位转换、刷单位、炮塔开火、动画、标签、路径点、附件和消息关联。它们应被当作状态机边，而不是随意堆积的脚本行。

### 首先回答四个问题

1. 谁触发：玩家点击、队列完成、创建、受伤、死亡、定时条件、炮塔开火还是其他事件？
2. 什么前置条件：资源、标签、目标、队伍、距离、建造状态、冷却、版本？
3. 改变什么状态：资源、单位类型、附件、动画、队伍、路径、投射物、可见性？
4. 如何停止或防重入：冷却、一次性标记、条件翻转、删除自身、队列边界、事件过滤？

若无法回答第四项，不应创建自动动作。无限自触发、双动作互相触发、动作转换后再次满足原条件，是最难从玩家现象直接定位的缺陷类型。

### 动作路由表

| 目标效果 | 先查 | 必须联查 |
|---|---|---|
| 显示一个按钮 | `[action_NAME]` UI/可见性/活动条件 | 资源、目标单位、混合选择 |
| 自动开局初始化 | `[hiddenAction_NAME]` 事件/自动触发 | 核心初始状态、资源、附件 |
| 变形或升级 | Action 转换字段 | 目标单位、保留字段、图像、AI、附件 |
| 生产子单位 | Action 生成/队列 | 目标单位 ID、队伍、路径、资源 |
| 触发炮塔朝地开火 | Action 与 turret/projectile | 目标位置、地形、冷却、投射物存在 |
| 修改资源 | Action 资源字段 | 局部/全局域、上限、失败条件 |
| 更改标签/团队 | Action 标签/队伍字段 | AI、攻击筛选、联机一致性 |
| 路径命令 | Action waypoint | 单位移动能力、目标类型、运输状态 |
| 动画与声音 | Action 表现字段 | Animation、资源路径、队列时机 |

### 名称和重复的硬规则

- `hiddenAction_` 前缀的同名定义会触发致命重复检查。无论来源是本文件、文件级模板还是生成器，都必须消除冲突。
- 可见动作与隐藏动作使用相近名称也要避免歧义；虽然语义不同，维护者可能误引用。
- 不要根据文本节在文件中的顺序推断事件顺序。事件时机由引擎生命周期定义，复杂链应实际测试。
- 对动作链引入唯一的、可观察的状态变化，例如一个局部资源或标签，再验证条件是否如期翻转。完成后可保留最小、可审计的防重入机制。

### 动作测试模板

```text
初始状态：资源、标签、队伍、建造状态、附件、动画均记录
触发方式：玩家按钮 / 精确事件 / AI 队列之一
预期一次效果：列出资源变化、单位变化、投射物或动画
预期不发生：列出不应修改的资源、队伍、相邻动作
重复触发：立即、冷却期间、条件失效后各测一次
边界：资源不足、目标不存在、单位被运输、单位转换后
```

动作与 LogicBoolean 的精确表达式语法必须在字段目录后用原始目标版本实现复核。复杂条件不要一次性写成长串；先用一个可观察条件验证，再逐步组合并保留每步测试结果。

## 12. Attachment、Leg/Arm、Effect、Animation、Decal：辅助对象也有主从关系

这些对象常被误认为“视觉细节”，实际上会影响单位关系、目标选择、死亡、移动、性能和状态保持。

### Attachment

`[attachment_NAME]` 表示附属单位/插槽关系。它可能指定生成什么、位置、可见性、可攻击性、选择性、随父旋转、父死后存活、脱离、目标继承和动作展示等。其核心问题是：附属对象是独立单位还是纯视觉？它继承哪一方的队伍、生命、路径、攻击目标和死亡语义？

审计时至少检查：

- 引用的子单位名存在，且子单位可在当前版本构造。
- 父子死亡、转换、运输和队伍变化各有明确预期。
- 子单位是否会被 AI 当作独立战斗单位，是否导致单位上限、资源或目标统计异常。
- 附属可见性与可选择性是否和玩家交互一致。
- 动作从附件显示、附件动态添加或卸载时，是否造成重复对象或悬空引用。

### Leg/Arm

腿/臂的局部 `copyFrom` 是对象级复用，通常要求目标肢体已按适当顺序加载。它不能替代文件级模板，也不适合跨任意文件复用。不要只复制视觉参数却忽略移动、旋转、附着位置和动画关键帧的耦合。验证时应观察静止、移动、急转、攻击、运输和父体转换后的姿态。

### Effect

`[effect_NAME]` 描述视觉效果，包括生命周期、位置、移动、方向、图像、阴影、优先级和颜色等。效果错误通常表现为“逻辑正常但无视觉”或“性能下降/层级错乱”。路由重点：效果由谁引用、在哪个事件生成、资源是否存在、是否被频繁事件无限刷出。不要先把效果加到复杂投射物链；先在单一、低频事件中验证。

### Animation

`[animation_NAME]` 描述状态或动作触发的动画、关键帧、融合、方向帧和关联对象。旧式动画字段在字段目录中可能仍可见，属于需要谨慎核对的遗留区域。新内容应先确认目标版本当前动画对象路径；旧包维护时只做最小、可回退的修改。动画故障要同时检查触发动作、目标对象名称、图形帧和状态是否真的进入。

### Decal

`[decal_NAME]` 管理贴花、基准位置、图像与绘制关系。它可能依附单位、腿、炮塔、标记或其他基准。贴花问题不应通过调整主体图来掩盖；应先验证基准对象存在、图层意图、图片路径和状态更新。高频或大量单位上的贴花还要做性能观察。

### 表现对象的联合测试

| 事件 | 需观察的对象 |
|---|---|
| 创建 | 附件生成、默认动画、初始效果、贴花基准 |
| 选择 | 图层、选择框、附件选择性、UI 动作 |
| 移动 | 腿/臂、阴影、移动效果、贴花跟随 |
| 攻击 | 炮塔、炮口效果、动画、投射物、声音 |
| 受伤 | 低血量效果、附属可攻击性、状态动画 |
| 死亡 | 爆炸、死亡效果、附件清理/存活、贴花残留 |
| 转换/传送/队伍变更 | 父子关系、图层、动画中断或保留 |

## 13. LogicBoolean、内存与版本门槛

LogicBoolean 连接配置与运行期状态，是条件攻击、动作可见性、AI、资源判断、目标筛选和自动触发的常用基础。它强大但高风险，因为错误可能不产生明显语法错误，而是让条件永远为假、永远为真、在错误对象上求值或在不期望的时机重入。

### 条件设计原则

1. 每个条件先有自然语言规格，例如“仅当自身有至少一个空附件槽且团队资源足够时可见”。
2. 拆成单独、可观察的子条件；先验证对象引用、再验证数值比较、最后合并布尔运算。
3. 明确 `self`、动作目标、事件源、父体、运输体、附件和攻击目标分别指谁。
4. 对空对象、单位死亡、转换、运输、队伍变化和联机同步做边界测试。
5. 不要用未证实的函数、缩写或旧教程中的表达式补全。字段目录给候选，原始实现给裁决。

### 内存与数组

使用单位内存数组时，最低版本必须为 `1.15p11`。这是硬门槛，不是优化建议。代理在以下任何情况都要审计版本：

- 动作写入或读取内存数组。
- LogicBoolean 通过数组状态做条件。
- 模板隐藏地引入数组字段。
- 生成器为多个状态自动创建数组。
- 单位转换、附件或队列需要保持数组相关状态。

不要为了兼容 1.14 而只降低 `minVersion`；应设计不使用数组的替代状态模型，或明确宣布提高基线。也不要根据单一运行截图断言数组能跨所有状态保留，需为创建、转换、死亡、运输、保存恢复和联机分别验证或标记未验证。

### 条件和版本的审计记录

```text
条件用途：防止升级动作重复入队
对象上下文：self
证据状态：1.15p11 已证实 / 1.14 未验证
版本门槛：因使用内存数组，minVersion 至少 1.15p11
最小测试：资源足够与不足、升级前后、重复点击、AI 触发
残余风险：联机保存恢复未验证
```

这种记录比只留下一个复杂表达式更有长期价值。代理交接时能知道哪些是逻辑设计、哪些是引擎依赖、哪些还缺运行验证。

## 14. 有限、遗留与高风险字段的处理策略

字段目录包含广泛的候选项，其中一部分可能有数量上限、上下文限制、兼容性目的、旧动画路径或特定对象类型要求。不能因为字段看起来方便就拿来构建新功能。

### 风险分类

| 类别 | 识别信号 | 处理方式 |
|---|---|---|
| 明确遗留 | 目录标为已弃用、旧式、替代方案存在 | 新内容不用；维护时最小改动并单测 |
| 版本限定 | 引擎有 `minVersion` 守卫或新增构建路径 | 提高门槛或提供替代 |
| 数量限定 | 解析器遍历固定索引、对象上限、队列边界 | 记录目标版本上限，避免贴近边界设计 |
| 组合限定 | 字段只在建筑、炮塔、投射物、附件等特定对象有效 | 强制检查区段和前置能力 |
| 运行期敏感 | 高速刷单位、刷弹、效果、自动动作 | 做频率、循环、性能和联机测试 |
| 核心依赖 | `CORE:`、内置单位名、内置资源 | 视为版本绑定，提供降级策略 |
| 容错依赖 | 大小写回退、路径包装透明化、宽松重复 | 重写为精确、显式、严格可过的形式 |

### 遗留字段的决策树

```text
字段目录提示遗留或旧写法
  -> 用户是在维护既有行为吗？
       是 -> 原始实现是否仍读取？
              是 -> 做最小改动，保留行为测试，标记遗留
              否 -> 需要迁移到已证实替代并扩大验证范围
       否 -> 是否有已证实的当前替代？
              是 -> 使用替代
              否 -> 不新增；记录待核查或询问用户
```

“当前游戏没有报错”不足以证明遗留字段适合作为新模板。它可能被读取但只为兼容旧包保留，可能在未来更新移除，或与新版对象组合表现不同。

## 15. 从需求到提交的端到端工作流

以下工作流把四份参考文档连接起来：

### A. 接收需求

记录用户想改变的玩家可见结果、目标版本、是否支持 1.14、是否需要联机、是否必须维持旧存档或旧包结构。若需求说“做一个会自动切换武器的单位”，不要立即写动作；先问触发条件、切换是否可逆、AI 是否参与、资源是否变化、最低版本是否被限制。

### B. 定位模组与源根

按 [01](01-mod-discovery-rwmod-and-metadata.md) 确认目录版或 `.rwmod`、逻辑源根、`mod-info.txt`、`title`、启用状态和 `minVersion`。如果模组未被发现，停止字段修改，先解决发现层。

### C. 建立继承图

按 [02](02-ini-parser-templates-and-inheritance.md) 找出目标单位、所有 `copyFrom`、`@copyFromSection`、`all-units.template` 祖先和特殊重复命名空间。此时确定具体字段是否可能被模板覆盖或隐式引入版本特性。

### D. 设计对象图

使用本页的生命周期和区段路由，为每个需求列出对象：核心单位、炮塔、投射物、动作、资源、效果、附件等。为每个对象指定唯一内部名和最小职责，拒绝“一个动作同时解决全部状态”的设计。

### E. 双重核对字段

先在 `assets/ai/references/rusted-warfare-modding.md` 查精确候选；再在原始引擎材料核实读取、类型、约束和版本。可读加载器用于定位，不覆盖原始行为。把每个高风险字段标为 `已证实`、`版本限定` 或 `待运行验证`。

### F. 最小实现

一次只接入一条链。例如先创建无特效的炮塔和简单投射物，后加资源和动作；先让建造项出现，后加放置规则；先让附件生成，后调整可攻击性和动画。每一步都能回滚并有唯一失败归因。

### G. 静态审计

检查重复键、`hiddenAction_`/`canBuild_` 唯一性、未使用键、继承深度、禁止的 `..`、资源路径、版本门槛、对象引用和遗留字段。不要用 `IGNORE` 批量压掉错误。

### H. 分层运行验证

从模组列表、单位扫描、最小战局、完整单机到联机逐层进行。每一层通过后才进入下一层；失败时回到对应层而不是同时改十个字段。

### I. 发布前归档验证

按 [01](01-mod-discovery-rwmod-and-metadata.md) 在 `.rwmod` 版重复元数据、路径和核心功能检查。确认归档没有内部反编译材料、第三方完整配置、开发缓存或个人路径。

### J. 交付记录

说明修改的对象、版本、证据、验证范围、未验证项和风险。对 `1.15p11` 特性写清最低版本；对遗留字段写清为何保留；对联机未测项明确不承诺。

## 16. 代码审阅与故障定位问卷

审阅单位补丁时，按以下顺序提问，可减少“看起来很复杂”的无效评论。

### 模组级

- [ ] 本次变化是否改变了 `minVersion`、源根、压缩结构或元数据？
- [ ] 使用 `title` 而不是过时的 `name` 作为模组展示字段了吗？
- [ ] 目标版本是否由用户指定，还是只是假定？
- [ ] 是否有 1.15p11 内存数组等强制版本依赖？

### 继承级

- [ ] 新键在当前文件是显式值，还是来自哪个父模板/目录模板？
- [ ] 多父 `copyFrom` 的右到左优先级是否符合意图？
- [ ] 是否引入 `..`、循环、超过十层或不透明的 `CORE:` 依赖？
- [ ] 是否让同一高风险键在多个父来源中竞争？

### 架构级

- [ ] 新能力被放入正确区段和对象类型吗？
- [ ] 攻击链是否从 `[attack]` 到炮塔再到投射物完整闭合？
- [ ] 生产链是否包含菜单、目标、资源、放置和 AI 的必要部分？
- [ ] 动作是否有清晰触发、前置、结果和防重入？
- [ ] 附件、资源、AI 与图形是否被当成独立但关联的系统审查？

### 稳定性级

- [ ] 是否引入重复 `hiddenAction_` 或 `canBuild_`？
- [ ] 是否有未消费键、未证实字段或错误节位置？
- [ ] 是否依赖遗留字段、大小写回退、包装目录透明化或宽松模式？
- [ ] 高速生成、自动触发、投射物分裂是否可能形成性能或循环问题？
- [ ] 路径和图像是否在 `.rwmod` 虚拟文件系统中实际可读？

### 验证级

- [ ] 最小战局是否覆盖本次新链路的成功和失败分支？
- [ ] AI、转换、运输、死亡和资源不足等状态是否按风险范围覆盖？
- [ ] 结论是否区分目录版、归档版、单机和联机？
- [ ] 未验证版本或平台是否被明确标为未知？

## 17. 任务记录示例

下面是一个不含第三方内容的记录格式，展示如何把字段路由变成可审计工作，而不是字段清单：

```text
需求：为移动单位增加一个仅攻击空中目标的副炮。
目标版本：1.15（用户指定）；不承诺 1.14。
对象图：现有单位 -> [attack] 总体目标规则 -> [turret_anti_air] -> [projectile_flak] -> [effect_flak_hit]。
继承：单位从一个底盘模板继承；副炮字段必须在具体文件显式定义，避免父模板覆盖。
字段证据：字段目录用于候选；原始目标版本实现已核对炮塔与投射物的读取路径。
静态审计：无重复 hiddenAction/canBuild；无未使用键；无新增 CORE 依赖。
最小验证：地面目标不应被副炮选中，空中目标应触发转向、发射、命中和效果。
残余风险：AI 多目标分配与联机未测，标为待运行验证。
```

注意这不是配置模板。它描述了“谁依赖谁、如何验证、哪些未验证”，因而可用于审阅任何类似补丁。

## 18. 最终原则

1. 从需求和生命周期路由到区段，而不是从记忆拼字段。
2. 字段目录是起点；原始目标版本引擎行为是裁决。
3. 单位身份、模组标题、显示文本和内部对象 ID 是不同概念，禁止互相替代。
4. 攻击、生产、动作、资源、附件和 AI 都是对象链，任何单点修改都要检查相邻引用。
5. 模板与目录默认值会改变最终字段来源；先展开来源，再判断“字段没生效”。
6. 遗留、有限、核心依赖和版本限定字段要比普通数值字段承担更高证据责任。
7. 内存数组要求至少 `1.15p11`，版本声明必须诚实反映能力边界。
8. 不复制内部反编译源码、可读加载器长摘录或第三方完整配置；用行为摘要和自写最小例子交流。
9. 不把“无报错”写成“可用”；运行测试必须覆盖新链路的成功、失败和边界路径。
10. 每次交付都留下版本、证据、验证范围与不确定性的记录，方便下一代理复核。

当字段选择、来源、对象关系和测试路径都能被解释时，单位配置才是可维护的工程资产，而不只是一次碰巧加载成功的文本集合。
